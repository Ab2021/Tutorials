# T16 — Agentic inference: high-level design

> `T16` · **Transcript coverage:** primary · [LLD](LLD.md) · [Sequences](docs/SEQUENCES.md) · [Runnable core](run.py)

**This blueprint's one sentence:** an agent task is a *superlinear, tool-dominated,
cache-sensitive* workload whose bill and whose latency are governed by different terms,
so an inference platform tuned for chat will be simultaneously too expensive and too slow
for agents and will not be able to say which.

---

## 1. What is actually new here

Chat inference has a stable shape: one prompt in, one response out, both bounded, both
known before the request starts. Everything in T11–T15 is built around that shape —
continuous batching amortises a fixed per-request cost, paged attention bounds a
predictable KV footprint, autoscaling tracks an arrival rate that is external to the
system.

An agent task breaks all three assumptions at once:

| Assumption (chat) | Reality (agent) |
|---|---|
| prompt size is known at admission | prompt size is a *function of the agent's own history* |
| one model call per request | tens to thousands of model calls per task |
| the request ends when the response ends | the task ends when the agent decides it does |
| latency is the product | latency is mostly **tool execution**, which no serving optimisation touches |

The corpus states the operational symptom before it states the mechanism. The panel opens
on it: agents "running sometimes for hours", "12 of them running code overnight for you",
"with massive tool volume and token prefill", and the standing joke that follows — "if
anyone has set up an agent to run overnight and then awoken to discover that they have
auto refilled their favorite token provider, raise your hand. Probably everybody." `[T]`
(`refs/Agentic_AI_Infra_transcripts_2/Panel_Agentic_AI_Infrastructure_Platform.txt`)

That sentence contains the whole design problem. *Overnight* is a duration problem.
*Massive tool volume and token prefill* is a cost problem. *Auto-refilled* is the fact
that the cost accrued while nobody was watching, which means it cannot be controlled by a
human in the loop. This blueprint is about the serving system that has to make those
three things into one design.

## 2. The anatomy: a model plus a harness

The corpus's cleanest definition is Jianfeng Gao's, and it is worth taking literally
because it draws the boundary the rest of this blueprint depends on.

An AI agent is "the combination of the language model, probably multiple language models,
and the agent harness." The reason a harness exists at all is that "the large language
model can not do a lot of things. It's just a talker." The harness is "a bunch of code"
that handles "a lot of things that the current language model cannot handle well." `[T]`
(`refs/Agentic_AI_Infra_transcripts_2/Jianfeng_Gao_-_Agentic_Modeling_via_Internalizing_Agent_Harnesses.txt`)

Gao then decomposes it into layers, and this decomposition is the spine of the LLD:

- an **information layer** — memory, context management, and "a lot of tools and skills
  for the language model to call";
- an **execution layer** — a prompt builder, an action parser, task decomposition
  modules, "and some error recovering mechanisms";
- a **feedback layer** — which "helps the system to collect all the trajectories
  generated by the agents", and which Gao calls "the key of the agentic modeling",
  because those trajectories are what the underlying model is post-trained on.

Two properties of this harness matter enormously for the serving design, and both are
easy to miss:

**It is hard-coded, not learned.** Gao says the modules are "not models by themselves",
and "most of them are hard-coded". A hard-coded module is deterministic, testable,
versionable — and, crucially, it is *re-executed on the client side of the model*, so the
serving system never sees it. The platform's only view of the harness is the token stream
it produces.

**It is asymmetric with the model in a specific way.** The harness compensates for what
the model cannot do. Tworek states the consequence more sharply than Gao does: "the
agents are very good at doing short horizon things and the truth is a lot of long horizon
work can be glued very successfully together from doing smaller and smaller things" —
via `/goal`, plan mode, sub-agents — "There are various ways that are not native to them
all. They are not back propagated through. They are not trained." And then the sentence
that makes internalisation inevitable: "the history of machine learning has always been
that whatever we can back propagate through wins" over the things we cannot. `[T]`
(`refs/Agentic_AI_Infra_transcripts_2/Jerry_Tworek_-_Opportunities_and_Challenges_for_Long_Horizon_Agents.txt`)

So the harness/model boundary is a *moving* boundary, and it moves in one direction. A
capability that starts as harness code and prompt text ends up inside the weights. That is
not a philosophical point for this blueprint — it is a capacity-planning point, because a
capability that lives in the prompt is paid for on **every turn of every task, forever**
(§4), and the same capability inside the weights is free at serving time.

## 3. The two dashboards, and why they disagree

This is the central finding of `run.py` §1, and it is the reason this blueprint exists
separately from T13 (engine) and T15 (SLO).

A 40-turn agent task, modelled with the parameters declared in `sim/agent_cost.py`:

| | cold cache (reuse 0%) | warm cache (reuse 90%) |
|---|---|---|
| tool execution, % of user wait | 37% | **73%** |
| prefill, % of user wait | **58%** | 16% |
| prefill, % of fleet bill | **91%** | **59%** |

Three readings, in increasing order of usefulness.

**First: tool execution is a constant, and it is nobody's problem.** 100 seconds of the
task is the agent waiting for tools — shells, HTTP calls, database queries, file reads.
That time is *exactly zero* of the fleet's cost and *exactly zero* is recoverable by any
technique in T11 (parallelism), T12 (KV transfer), T13 (engine), T14 (routing) or T15
(autoscaling). It is worth having the number in the design document precisely so that a
review does not spend an afternoon optimising a term that a caching layer cannot reach.

**Second: cost and latency are dominated by different terms, and which term depends on
the cache.** At cold cache, prefill dominates both — 58% of the wait and 91% of the bill
— so latency work and cost work coincide and a team can be efficient by accident. At warm
cache they diverge completely: tools dominate the wait (73%) while prefill still dominates
the bill (59%). From that point on, further latency work is invisible to the user and
further cache work is invisible to the latency dashboard. A platform with only a latency
dashboard will conclude that prefix caching stopped mattering exactly when it became the
only thing that did.

**Third: the same lever moves the two numbers by different amounts.** Raising cache
residency from 0% to 90% cuts fleet cost from 172 to 37 GPU-seconds (−79%) while the
user's wait falls from 272 to 137 seconds (−50%). Both improve, so this is not a
trade-off — but a team that measures only one of them will mis-size the investment by a
factor of about 1.6, and will mis-size it in the direction of *under*-investing in the
cache, because the user-visible number is the one on the wall.

**Do not read the absolute numbers as predictions.** These are arithmetic on declared
parameters — 8,000 prefill tokens/s, 800 decode tokens/s, 2.5 s of tool latency per turn.
The wall-clock column sums turns serially, which treats the fleet as if it were serving
this one task, so it is a shape and not a schedule. The *ratios* are the finding; the
seconds are an illustration. No GPU was measured for this blueprint.

## 4. Context growth is the whole ballgame

`run.py` §2. An agent that re-prefills its entire conversation every turn processes
O(N²) prompt tokens over N turns. At 40 turns the gap against a perfect cache is **22.9×**
the prompt tokens, and — the important part — **the ratio grows with task length**:
4.1× at 5 turns, 12.6× at 20, 22.9× at 40, 83.2× at 160.

This is the same mechanism T12 calls KV offload and T13 makes addressable across nodes
and processes. T16's contribution is one of framing: for chat, prefix caching is an
optimisation on top of a design that already works. **For agents, it is the design.** The
difference between no reuse and a working cache is not a percentage of the bill; it is the
difference between a task that is affordable and one that is not.

There is a subtlety in the model that is worth naming because it bounds the optimism. Even
at perfect cache residency, each turn must prefill the tokens that *did not exist when the
cache was written*: the model's own previous output and the tool's result. `run.py` §4
shows the consequence — the improvement is exactly linear in cache residency, so there is
no "diminishing returns" story to tell here and none is told. What is *not* linear is the
capability: prefix caching is close to a discrete step, and the last points of hit rate
are where eviction policy (T12) and placement precision (T14) earn their keep.

### 4.1 The tool-schema tax

A separate, smaller, and much more actionable finding. Tool schemas are re-sent on **every
turn**. In `run.py` §3, a 6,000-token tool catalogue is **19.1%** of all prompt tokens
processed across a 40-turn task, and its share is a function of the number of *turns*, not
of the amount of *work* — so it grows as agents get longer, which is the regime the whole
field is moving into.

The panel's phrase "massive tool volume and token prefill" `[T]` is this term. Three
design consequences follow, and none of them is about prompt quality:

1. tool schemas belong in the **cached prefix** and never in per-turn text, because a
   per-turn re-send is precisely the thing a cache cannot help with if it is not
   byte-stable (see LLD §3 on prefix stability);
2. a large tool catalogue is a fixed per-turn tax on **every** request the fleet serves,
   so *tool selection* — retrieving only the relevant schemas instead of shipping all of
   them — is a cache-and-cost optimisation with a serving-system payoff;
3. the tax is invisible at low load and becomes the whole bill at high load, because it is
   exactly the per-token cost that batching cannot amortise away.

## 5. Multi-agent topology: fan-out is concurrency, not parallelism

`run.py` §5. A parent agent spawning N sub-agents is the corpus's own framing: "this
hierarchy of agents where you have an agent and it spawns sub agents and it spawns sub
agents and maybe an agent spawns a team that works together", and, at the extreme, "an
agent can in an ad hoc way spawn **100,000 sub agents**, all of which need to communicate
in some complicated pattern." `[T]`
(`refs/Agentic_AI_Infra_transcripts_2/Panel_Agentic_AI_Infrastructure_Platform.txt`)

The serving arithmetic of that sentence is brutal. At 100,000 sub-agents:

- the **wall clock** grows by 1.09× — barely more than one sub-agent's own tool latency,
  because sub-agents run concurrently;
- the **fleet cost** grows by 6,106× with an unshared cold cache, and 12,615× with an
  unshared warm one.

Cost scales with N; latency scales with 1. That asymmetry is exactly why fan-out is
attractive and dangerous at the same time, and why it is the failure mode a latency
dashboard structurally cannot see.

Note the second-order effect, which is counterintuitive and worth carrying into design
review: **a warm cache makes the multiplier worse.** Improving the parent's per-turn cost
does not improve the sub-agents' cost by the same amount (they have their own cold start
and their own history), so the fan-out ratio rises from 6,106× to 12,615×. Any change that
flatters the parent alone will magnify the fan-out.

### 5.1 Should a sub-agent inherit the parent's context?

The intuitive answer is yes. The model says: **it depends on how long the sub-agent
lives**, and the crossover is derivable.

Per-sub-agent prefill, cold cache: a two-turn child costs 7.8 GPU-seconds if it inherits
the parent's context and 2.9 if it starts fresh. A twenty-turn child costs 17.2 inherited
against 56.0 fresh. The crossover sits at about **5.6 sub-agent turns** — an algebraic
identity, not a measurement: the parent's context grows linearly with the parent's turns,
while an unshared child's quadratic growth is still negligible early on.

With a warm cache the ordering collapses at every length, because the parent's context is
the only thing that is cached and it is therefore cheap to share from the first turn.

So "sub-agents share the parent's context" is a **conditional whose condition is a
serving-system property** — cache residency (T12/T13) and prefix-aware placement (T14) —
plus the sub-agent's expected lifetime. This matters because the corpus identifies scoped
shared memory as an *open standards* problem: "there are new standards to be developed to
describe these kinds of scoped shared storage systems and access and message passing
between agents", and the reason the old answers do not transfer is that "things we've
built in the past were either services or kind of human scale." `[T]` The design
consequence is that the *scoping* API (§LLD 6) is where the serving cost is decided,
because the scope determines which sub-agents are cache-compatible with which parent.

## 6. Reliability: compounding cost and compounding confusion

The Postman talk is the corpus's account of what actually goes wrong when a team
decomposes an agent into many agents, and it names two failure modes that this blueprint
treats as first-class.

"Those of you that have built a microservices architecture probably recognize this... What
we were recognizing is that we were ending up with both **compounding cost** and
**compounding confusion** and the challenges in terms of the handoffs and testing between
these agents became a much bigger problem." `[T]`
(`refs/Agentic_AI_Infra_transcripts_2/Ankit_Sobti_-_From_Agent_Demos_to_Production_How_Postman_Is_Building_Reliable_AI.txt`)

The team's diagnosis was that this is a *decomposition* problem, and that "the interface
between these systems and the handoff of context that was the biggest challenge". Their
answer was to **collapse the decomposition**: "at the foundation we created a monolith
agent" that "had an understanding of all the knowledge and information that is available"
for the domain.

Compounding cost is the fan-out multiplier of §5 seen from the operator's side. Compounding
confusion is the same multiplier seen from the *quality* side: every handoff between agents
is a lossy re-serialisation of context, and the loss is not a bug that gets fixed — it is a
property of the boundary. The architectural reading, which this blueprint adopts, is:

> A sub-agent boundary should be justified by a **capability** difference (different tools,
> different sandbox, different model tier) or by a **genuine parallelism** opportunity.
> It should not be used simply to make a long context fit, because the fan-out costs more
> (6,106× at the corpus's own scale), the context degrades at each hop, and the tokens
> that were "too many for one prompt" end up being prefilled N times instead of once.

That is a design guideline and it is labelled as such — the corpus reports the failure, it
does not quantify the threshold.

## 7. The internalisation boundary

Put §4 and Tworek's training argument side by side and the direction of travel is
determined.

Tworek's argument `[T]`, reproduced as arithmetic in `run.py` §6: a long trajectory can
only be scored when it *ends*, so gradient steps per day is bounded by completions per day.
His instance is a 12-hour trajectory: "you are able to do full two gradient steps in a day
... roughly 14 gradient steps a week ... like 60 gradient steps a month." The general
identity is `steps/day = 24 / trajectory_hours` and it reproduces his numbers exactly —
which is the point: it is a scheduling consequence, not a measurement.

He then gives the decay: cost is proportional to trajectory length n, and "the information
per token you are getting is roughly one divided by n", so "your learning signal decays
**quadratically** in the length of your trajectory." `[T]`

Now the two curves together. As horizons lengthen, the serving cost of a task grows with
the *square* of the turn count (or linearly at best, §4), while the learning signal per
token *falls* with length. Both curves point the same way `[D]`:

- a harness that glues short-horizon work into long-horizon work buys capability at a
  superlinear token cost and a sublinear training signal;
- moving that capability **into the model** removes it from the per-turn prompt — which
  removes it from the cached prefix *and* from the decay;
- therefore internalisation is a serving optimisation and a training optimisation at the
  same time.

This is why the blueprint treats the harness and the model as one moving boundary rather
than two layers, and why an inference platform should expect the *shape* of agent traffic
to change under it: as capabilities internalise, turns get fewer, prompts get shorter, and
the tool-schema tax falls — without any change to the serving code.

The harness does not disappear. Tworek's own framing is that the harness is where
long-horizon behaviour is *composed* — `/goal`, plan mode, sub-agents `[T]`. What changes
over time is which capabilities are cheap enough to leave in the prompt.

## 8. Failure modes this design must survive

| Failure | Mechanism | Where handled |
|---|---|---|
| Context overflow mid-task | history grows past the window on turn k of N | LLD §5 (compaction as an explicit, logged transform) |
| Prefix instability | a timestamp or a reordered tool block invalidates the whole cache | LLD §3 |
| Runaway fan-out | a sub-agent loops, spawning sub-agents | LLD §7 (budget as a scheduling input, not a billing alert) |
| Overnight spend | the panel's "auto refilled" — cost accrues with no human watching | LLD §9 (per-task budget, hard stop) |
| Orphaned tools | the agent dies, the sandbox keeps running | LLD §4 (lease + reaper) |
| Trajectory loss | the task fails after four hours of work and the feedback layer gets nothing | LLD §8 (stream, don't batch, the trajectory) |
| Cache-hostile tool schemas | catalogue re-serialised per turn | LLD §3, HLD §4.1 |
| Cost mistaken for latency | §3 above | HLD §3, `alerts.yaml` |

Two of these deserve a note on *why they are on a serving blueprint at all*. Budget
enforcement (§LLD 9) is a serving concern and not a billing concern because the decision
it drives — stop, degrade, or continue — has to be made at admission time, in the same
place flow control runs (T14 §5). And trajectory streaming (§LLD 8) is a serving concern
because Gao's feedback layer is the reason the harness exists at all `[T]`: a platform that
loses trajectories on failure is destroying the training signal it was built to generate.

## 9. What this blueprint does not cover

- **Engine internals.** Continuous batching, paged attention, chunked prefill are T13. This
  blueprint takes them as given and asks what they are being asked to serve.
- **The training loop.** Tworek's argument is used as a *constraint on serving design*
  (§7). No training pipeline is designed here.
- **Agent quality.** Whether a harness produces correct work is not modelled. The Postman
  discussion is used for its infrastructure failure modes, not as an evaluation of agent
  capability.
- **Sandbox and isolation design** beyond the interface the harness needs (LLD §4). The
  security model is T18.
- **Pricing.** No dollar figure appears anywhere in this blueprint or its `run.py`. The
  corpus asserts no vendor price; inventing one would be a fabricated benchmark. Every
  cost statement is in tokens or GPU-seconds, and a reader who wants money multiplies by
  their own rate.

## 10. The three things to carry away

1. **An agent task is superlinear in its turns, and the superlinearity is a serving
   property, not a prompting property.** `run.py` §2: 22.9× at 40 turns, 83.2× at 160.
   Prefix caching is not an optimisation on this workload; it is the workload.
2. **Cost and latency are governed by different terms and the terms move under the
   cache.** Cold: prefill dominates both. Warm: tools dominate latency, prefill still
   dominates cost. A platform with one dashboard will size the investment wrong.
3. **Fan-out is concurrency plus a multiplier.** 6,106× cost for 1.09× latency at the
   corpus's 100,000-sub-agent figure. The multiplier appears in the cluster and not in the
   trace, which is why it has to be designed for rather than observed.
