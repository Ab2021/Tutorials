Requirement: Display responses as tokens are generated in a chat interface.
Strategy: Use Converse Stream or Invoke Model with Response Stream APIs.

Requirement: Log prompts and responses for compliance while masking PII.
Strategy: Enable Bedrock Guardrails combined with model invocation logging.

4. Cost Optimization via Prompt Caching (7:14 - 9:46)

Requirement: Reduce token costs when prompts contain static system instructions and few-shot examples.
Strategy: Place static content before the cache checkpoint using Bedrock prompt caching.
Reasoning: Caching static prefixes avoids re-processing identical tokens on every request, which can reduce costs by up to 90% for that portion of the prompt.
5. Hallucination Detection (9:46 - 12:21)

Requirement: Systematically measure response faithfulness to source documents.
Strategy: Use Bedrock model evaluations with RAG evaluation jobs.

Strategy: Enable AWS CloudTrail for API auditing and use AWS Glue Data Catalog to propagate document identifiers to vector store metadata.

Requirement: Optimize costs for mixed traffic (70% simple FAQ, 30% complex tasks).

Why avoid many small vector search shards?
According to the video (11:18 - 13:44), you should avoid having millions of small shards in your OpenSearch vector index because it significantly degrades performance and increases query latency. Here is the breakdown of why this happens:

Coordination Overhead: Each individual shard must independently run an approximate nearest neighbor search. Once these searches are complete, the system must coordinate and aggregate the results from all shards. When you have too many small shards, the coordination overhead becomes the primary bottleneck, dominating the total query time.
Reduced Cache Locality: Fewer, larger shards improve cache locality, which makes the traversal of HNSW (Hierarchical Navigable Small World) graphs much more efficient.
Best Practice: For optimal performance, the video suggests consolidating your index into fewer, larger shards, ideally in the 30 to 50 GB range per shard.
What prevents outdated documents from appearing?
To prevent a RAG (Retrieval-Augmented Generation) system from retrieving factually outdated documents, the focus must be on retrieval configuration rather than the generation model (14:38 - 14:57).

According to the video, the most effective approach is to verify metadata filtering (15:00 - 15:25). You must ensure that:

Proper Metadata Exists: Documents are correctly tagged with relevant metadata, such as timestamps or versioning info.
Filters are Applied: Your retrieval queries are correctly configured to apply these metadata filters at query time.
Exclusion Logic: The filters are effectively set to exclude any documents that do not meet your freshness requirements (15:10 - 15:25).
If outdated documents are appearing in your results, it is typically a sign that your filtering logic is missing, misconfigured, or not being applied correctly during the retrieval process.
How to check AI response accuracy?
Evaluating AI response accuracy, particularly in a generative AI context like the AWS Bedrock scenarios discussed in the video, requires moving beyond simple keyword matching. Here are the professional approaches suggested in the video (0:00 - 2:37) and industry standards:

Ground Truth Comparison: Use model-based evaluation frameworks to compare AI outputs against 'ground truth' answers provided by subject matter experts. This allows the system to judge correctness (is the answer factually accurate?) and completeness (does it cover all key requirements?).
Semantic Evaluation: Avoid relying on cosine similarity or keyword overlap alone. These methods often fail because they cannot detect subtle factual errors or handle natural paraphrasing effectively.
Operational Monitoring: While not a direct measure of factual accuracy, you should maintain separate operational metrics (like latency) to monitor system health, ensuring that evaluation overhead does not compromise the user experience.
For more complex workflows, such as agentic reasoning (18:52 - 21:23), the video suggests explicit orchestration (e.g., using AWS Step Functions). By breaking down reasoning into visible, auditable steps, you create a trail that allows human reviewers to verify the decision-making process at every branch.
What makes embedding similarity unreliable for evaluation?
Embedding similarity is considered unreliable for evaluating generative AI accuracy because it measures semantic proximity rather than factual correctness (1:47 - 1:57).

Key reasons include:

Similarity vs. Accuracy: Two responses can be semantically similar or share a related context while one remains factually incorrect or hallucinated (1:50 - 1:57).
Lack of Precision: Cosine similarity cannot distinguish between subtle factual errors that change the meaning of an answer entirely, even if the surrounding context is related (1:54 - 2:00).
For accurate evaluation against ground truth, the video recommends using Amazon Bedrock model evaluations with metrics specifically designed for correctness (accuracy relative to the ground truth) and completeness (coverage of key points), which are better equipped to handle paraphrasing than simple embedding comparisons.

Why avoid response hashes for RAG testing?
The video explains that response hashing should be avoided because Large Language Models (LLMs) are non-deterministic. Consequently, response hashes will almost always differ, even when the generated answers are accurate and acceptable. (4:11 - 4:20)
Why use regression testing for RAG systems?
The video explains that regression testing is necessary for RAG systems because their behavior changes whenever the underlying content is updated. By maintaining a fixed set of test questions and defining expected outcomes, teams can verify that answers remain consistent and identify potential quality issues before they reach end users. Why does AI output vary for same inputs?
Large Language Models are considered non-deterministic primarily because of how they generate text. Instead of following a rigid, static path, they function by calculating the probability distribution of the next possible tokens (words or word parts) based on the input context.

As explained in the video (4:13-4:23), this probabilistic nature is a core feature of their architecture:

Sampling: When generating text, LLMs use sampling strategies (often controlled by a parameter called temperature). Rather than always choosing the single most likely word, the model selects from a range of high-probability candidates. This introduces variability, which makes the model more creative and conversational but also ensures that the output is not strictly repeatable.
Impact on Consistency: Because of this inherent randomness, two separate requests with the exact same input may result in different phrasings or structure. This is why, as noted in the video, simple techniques like comparing response hashes are ineffective for regression testing in RAG systems; the output content will frequently change even when the factual accuracy remains consistent.

What makes high dimensionality bad for scale?
According to the speaker, high embedding dimensionality becomes problematic at scale because it negatively impacts three key areas: (09:42 - 11:24)

Storage size: Each vector requires more bytes to store, which significantly increases the total storage footprint as the item catalog grows.
Query latency: A higher number of dimensions leads to more complex distance calculations during searches, causing the system to slow down.
Index efficiency: The overall effectiveness of the search index decreases, making it more difficult to maintain performance as you reach millions of items.
