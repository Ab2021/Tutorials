## 📖 Theoretical Deep Dive

### 🔹 Part 1: The Vectorization Pipeline

The `LoopVectorize` pass is one of the most complex in LLVM. It runs late in the pipeline (after inlining, unrolling, and simplification).

**Stages:**
1.  **Legality Checks (`LoopAccessAnalysis`):**
    *   Can we legally widen this loop?
    *   Are there dependence cycles?
    *   Is the trip count computable?
2.  **Cost Modeling (`LoopVectorizationCostModel` - CM):**
    *   For each Width $W \in \{1, 2, 4, 8, ...\}$:
        *   Calculate Instruction Cost.
        *   Determine Register Pressure.
    *   Select Best $VF$ (Vector Factor) and $IC$ (Interleave Count).
3.  **Planning (VPlan):**
    *   Build a VPlan graph representing the vector loop logic.
    *   Optimize the VPlan (e.g., sink scalar operands).
4.  **Code Generation (`InnerLoopVectorizer`):**
    *   Materialize the VPlan into LLVM IR.
    *   Generate Loop Guards (Trip count check, Alias check).
    *   Generate Scalar Epilogue.

### 🔹 Part 2: Handling Reductions

**Scalar:**
```c
sum = 0;
for (i) sum += A[i];
```
In IR, `sum` comes from a Phi node: `%sum = phi [0, entry], [%next_sum, loop]`.

**Vectorized:**
We cannot update one scalar `%sum`. We need a **Vector Accumulator** `%vsum`.
```llvm
%vsum = phi <4 x float> [ <0,0,0,0>, %entry ], [ %next_vsum, %loop ]
%load = load <4 x float>, ptr %ptr
%next_vsum = fadd <4 x float> %vsum, %load
```
*   **After Loop:** We have 4 partial sums in `%vsum`.
*   **Horizontal Reduction:** We must sum the elements of `%vsum` to get the final scalar.
    *   `%res = call float @llvm.vector.reduce.fadd(<4 x float> %vsum)`

**Ordered Reductions:**
For strict FP (no `-ffast-math`), we cannot change order. LLVM serializes the reduction or uses `fadd` with `ordered` flags, effectively preventing vectorization or making it very slow (just vector loads, scalar adds).

### 🔹 Part 3: Interleaving (Unroll-and-Jam)

Vectorization is often memory bound. CPU execution units wait for data.
To hide latency, we use **Interleaving**.

**Concept:**
Instead of one vector per cycle, process **IC** vectors per cycle.
**VF=4, IC=2:**
```llvm
%vec1 = load <4 x float>, ptr %p
%vec2 = load <4 x float>, ptr %p + 16 bytes
%res1 = fadd %vec1, %x
%res2 = fadd %vec2, %y
```
*   The CPU can issue two loads in parallel.
*   While `fadd` 1 is calculating, `fadd` 2 can use the pipeline.
*   Cost Model chooses IC based on register usage (don't spill!) and TTI (Target Transform Info).

### 🔹 Part 4: Predication (Masking)

If the loop has control flow:
```c
if (A[i] > 0) B[i] = ...
```

**Phi-Conversion (If-Conversion):**
LLVM linearizes the CFG.
1.  Compute Condition $C$.
2.  Compute Result True $R_T$.
3.  Compute Result False $R_F$ (if any, or undef).
4.  Select: `%res = select i1 %C, %RT, %RF`.

**Masked Memory Ops:**
For stores, we can't "select" (stores have side effects).
We use intrinsics:
`call void @llvm.masked.store(<4 x float> %val, ptr %addr, i32 align, <4 x i1> %mask)`

### 🔹 Part 5: VPlan - The Future

The Vectorizer used to work directly on IR instructions, which was messy. **VPlan** is a higher-level IR specifically for vectorization.

**Nodes (VPRecipes):**
*   `VPWidenRecipe`: Represents widening a standard instruction.
*   `VPWidenMemoryInstructionRecipe`: Represents a vector load/store.
*   `VPInterleaveRecipe`: Represents an interleaved group.
*   `VPReplicateRecipe`: Represents an instruction that must remain scalar (predicated or scalarized).

**Optimization:**
VPlan allows writing passes *on the vector plan* before generating LLVM IR (e.g., detecting if a mask is all-true and removing it).

## 💻 Implementation: Analyzing the Cost Model

We will write a C program and force the compiler to reveal its cost decisions.

### Source (`cost.c`)

```c
void transform(int *A, int *B, int N) {
  for (int i = 0; i < N; i++) {
    A[i] = (B[i] * 3) + 5;
  }
}
```

### Analysis Command

```bash
clang -O3 -Rpass-analysis=loop-vectorize cost.c -S -o /dev/null
```

**Sample Output Interpretation:**
```text
LV: Checking a loop in 'transform'
LV: Found an estimated cost of 1 for VF 1 For instruction: %load = load i32...
LV: Found an estimated cost of 2 for VF 4 For instruction: %load = load <4 x i32>...
...
LV: Selecting VF: 4.
LV: Selecting IC: 2.
```
*Explanation:*
*   Scalar Load Cost: 1.
*   Vector Load (VF=4) Cost: 2. (Why ~2? Maybe alignment, maybe bandwidth).
*   Efficiency: 4 elements for cost 2 -> 0.5 cost per element. Vector is win.

### Force Factors

We can override the model.

```c
#pragma clang loop vectorize_width(8) interleave_count(4)
for (...)
```

Compile again. Check if it obeyed.
*If it refuses, it's usually **Legality**, not Cost.* (e.g., Register pressure too high, or Dependencies).

## 🧪 Hands-On Lab: Vectorizing "Gather" Patterns

**Objective:** Understand the cost of non-contiguous memory access.

**Scenario:** Indirect access (LUT lookup).

```c
void lookup(float *A, int *Idx, float *Table, int n) {
    for (int i=0; i<n; i++) {
        A[i] = Table[Idx[i]];
    }
}
```

**Hardware:**
*   AVX2 supports `vgather`.
*   NEON (older) does not.

**Task:**
1.  Compile for x86-AVX2 (`-mavx2`). Check assembly for `vgather`.
2.  Compile for generic x86-64 (`-march=x86-64`). Check assembly. It likely generates scalar loads inserted into vectors (`vpinsr`), which is slow.
3.  Check Cost Model output. Does LLVM think Gather is expensive? (Usually yes, gathers are often slower than scalar loads on Intel CPUs before Skylake).

## 🔬 Deep Dive: Runtime Memory Checks

What if `A` and `B` alias?

**Versioning Code Gen:**
1.  **SCEV Check:** Can we prove `(A...A+N)` and `(B...B+N)` disjoint at compile time?
2.  **Runtime Check:** If not, generate:
    ```llvm
    %conflict = ((A_end <= B_begin) || (B_end <= A_begin))
    br i1 %conflict, label %scalar, label %vector
    ```
3.  **Threshold:** If we check too many pointers (e.g., 10 arrays), the `if` condition becomes huge ($N^2$ checks).
    *   `LoopVectorize` has a limit (`-runtime-memory-check-threshold`). Defaults to 8. If exceeded, it declines vectorization.

## 📝 Summary & Key Takeaways

1.  **VPlan:** The abstraction layer that decouples "Planning" (Cost/Decisions) from "Generation" (IR Builder).
2.  **Interleaving:** Often more critical than Widening for masking memory latency.
3.  **Reductions:** Handled via special Phis and horizontal reduction intrinsics. Requires associativity for FP.
4.  **Cost Model:** A "Magic 8-Ball" that queries TTI (Target Transform Info). It is heuristic-based and sometimes wrong.
5.  **Runtime Guards:** Vectorization is rarely free. It often comes with a prologue of checks (Trip count, Aliasing, Alignment).
