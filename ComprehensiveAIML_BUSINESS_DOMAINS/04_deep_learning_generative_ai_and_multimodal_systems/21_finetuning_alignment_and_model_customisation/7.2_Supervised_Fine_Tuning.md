## Learning outcomes

Given a supervised conversation dataset and a causal language model, learners can define the conditional next-token objective; decide which roles and spans contribute loss; distinguish token-average from sequence-average weighting; design data/split controls; build a reproducible SFT run and evaluation; and diagnose common ways demonstrations fail to teach the intended behavior.

## 1. What SFT does

Supervised fine-tuning (SFT) continues training from a pretrained checkpoint on input/target demonstrations. For an input context `x` and target response tokens `y_1…y_T`, the standard autoregressive objective increases the likelihood of each target token conditioned on the context and earlier target tokens. Chat SFT is one application; the same mechanism can train structured extraction, tool-use traces or other serialized tasks when the examples represent the intended inference contract.

SFT teaches patterns represented in the demonstrations; it does not guarantee that every prompt is followed, that a claim is true, or that a tool is authorized. The model can imitate errors, overfit a narrow style, forget useful behavior or learn artifacts in the serialization. Data quality, objective, mixing, evaluation and operational controls remain part of the method.

Before training, specify:

- base checkpoint, tokenizer, chat template and model context limits;
- task contract, allowed inputs, expected output and error/refusal behavior;
- target roles/spans, EOS/turn-ending policy and loss mask;
- data provenance, licenses/permissions, privacy and retention policy;
- deduplication and leakage-resistant train/validation/test split;
- sampling/mixture policy, sequence length, packing and truncation;
- loss reduction, optimizer/schedule, batch in tokens/examples, precision and checkpointing;
- evaluation gates, rollback artifact, ownership and serving path.

## 2. Causal next-token likelihood

Let a serialized training example contain tokens `z_0,…,z_(L-1)`. A causal model at position `t-1` predicts target token `z_t` from the preceding context. Let `m_t` be 1 when target `z_t` contributes to loss and 0 otherwise, and let `w_t` be an optional nonnegative target weight. The per-token negative log likelihood is `ell_t = -log p_theta(z_t | z_<t)`.

The basic token-normalized objective for a batch is:

```text
FORMULA [SFT-01]: L_token = (sum_b sum_t m_(b,t) * w_(b,t) * ell_(b,t))
                              / (sum_b sum_t m_(b,t) * w_(b,t))
WHERE: b indexes examples; t indexes target tokens; m is a 0/1 loss mask;
       w is a nonnegative target weight; ell is NLL [nats or bits, as defined].
CONSTRAINT: denominator > 0; labels follow the trainer's causal shift;
            weights and mask are applied exactly once. If w=1 on valid targets,
            this is the mean NLL per contributing target token.
NUMERICAL EXAMPLE: losses [1,2,3] and masks [1,0,1] give
                   L_token=(1+3)/(1+1)=2 nats/target token.
INTERPRETATION: excluded prompt/pad positions remain context where permitted but
                are not direct supervised targets under this mask.
```

NLL averaged per token does not equal averaging per-example means when sequences have different target lengths. A sequence-average objective first computes each example's mean and then averages examples:

```text
FORMULA [SFT-02]: L_sequence = (1/B_valid) * sum_b [N_b > 0] *
                               (sum_t m_(b,t) * ell_(b,t) / N_b)
WHERE: B_valid is the count of examples with at least one target;
       N_b = sum_t m_(b,t); [N_b>0] is an indicator.
CONSTRAINT: every valid example receives equal outer weight, irrespective of
            its target-token count; define handling of zero-target examples.
NUMERICAL EXAMPLE: example A has losses [1,3] (mean 2); example B has loss [5]
                   (mean 5); sequence mean=(2+5)/2=3.5.
INTERPRETATION: short examples have more weight per target token than long ones.
```

The same two examples under token averaging give `(1+3+5)/3=3`, rather than 3.5. Neither reduction is universally correct. Token averaging weights each supervised token equally; sequence averaging weights each valid example equally. Some trainers sum loss per microbatch, normalize by local token counts, apply example weights, or divide by a fixed accumulation denominator. Distributed training can further change the effective weighting if ranks have different numbers of unmasked tokens. Determine and test the actual reduction before interpreting loss or comparing runs.

## 3. Inputs, targets and masks

A serialized chat sequence may include system/developer instructions, user messages, assistant responses, tool calls and tool results. All can be in the model input; not all should be targets. Under assistant-only SFT, prompt tokens condition the answer but are ignored as targets. Assistant response tokens are supervised. Whether to target tool calls, tool outputs, reasoning channels, refusal markers and end-of-turn tokens is an explicit task/data-policy decision, not a default inferred from message role.

Attention masks and loss masks differ:

- **Attention/position metadata:** establishes which sequence positions exist and may interact under the model's architecture.
- **Loss mask/labels:** determines which target positions contribute to the objective.
- **Causal mask:** prevents token positions from attending to future positions in standard causal decoding/training.

A training stack may shift labels inside the model or expect pre-shifted labels. Inspect the batch and loss implementation. Shifting twice or not at all creates off-by-one targets. If a pad ID equals an end marker, explicit lengths/masks—not token ID equality—must identify padding.

A tiny inspectable sequence is safer than trusting the high-level collator. For every token, verify input ID, message role, target label after shift, loss-mask value, attention behavior and end-marker meaning. Include the final assistant turn and any tool handoff. Verify that no prompt, padding, tool result or untrusted span is accidentally optimized as an assistant answer.

## 4. Demonstration design and data integrity

A demonstration is a labeled behavior specification. It needs a correct desired output, enough context, unambiguous constraints and provenance. Review:

- **Correctness:** domain expert review for claims, calculations, code or policy.
- **Coverage:** ordinary, edge, ambiguous, refusal, out-of-scope and recovery examples.
- **Consistency:** compatible tone, schema and policy across authors and time.
- **Representativeness:** task, language, demographic and input-format slices relevant to deployment.
- **Provenance and rights:** source, permitted use, user consent where required, PII/sensitive-data handling.
- **Duplicates and contamination:** exact and near-duplicate prompts/answers across splits; overlap with evaluation and benchmark sets.
- **Difficulty and artifacts:** boilerplate, answer-position shortcuts, template IDs, label leakage and repeated synthetic phrasing.

Split at the unit that protects independence. If many examples derive from one conversation, user, document, repository, policy version or time window, a random row split can leak near-identical content. Keep an untouched test set for final decisions. Validation data may guide checkpoints or hyperparameters and should not silently become the final test.

Track every transformation from raw authorized record through filtering, deduplication, serialization, tokenization, masking, packing and split assignment. Store counts and exclusion reasons at each stage. Reproducibility requires a data snapshot/hash, code/config, base model, tokenizer/template versions, random seeds and checkpoint provenance.

## 5. Worked target-mask and normalization example

Consider two assistant-only examples. After the trainer's causal shift, example A contributes three target losses `[1, 2, 1]`; example B contributes one target loss `[4]`. Their prompts and pad positions are present as context or batch padding but masked from loss.

- Token-average: `(1+2+1+4)/4 = 2.0` nats per target token.
- Per-example means: A=`4/3`; B=`4`; sequence-average=`(4/3+4)/2=8/3≈2.667` nats/example.
- Token weighting gives the three-token response A three times as many loss terms as B. Sequence weighting gives each example half of the outer weight.

This contrast matters when sequence length correlates with task, source, quality or subgroup. A change in packing, truncation or response length can alter the objective even when the visible example count does not change.

**Mask trace:** Suppose the rendered input is `[BOS, USER, U1, U2, ASSISTANT, A1, A2, TURN_END, PAD]`. Under assistant-only loss, mark the target positions corresponding to `A1`, `A2`, and optionally `TURN_END` as supervised (depending on the explicit policy); ignore prompt tokens and PAD. Because causal targets are shifted, map each target to the preceding logit position. The chosen template may use different markers; this trace is schematic and is not a tokenizer prescription.

**Independent checks:** four token losses sum to 8; divide by four for token mean 2.0. Sequence means sum to `4/3+4=16/3`, divide by two to `8/3`; its difference from token mean is `2/3`. Confirm the batch's actual target count after shift, not just the visually counted answer tokens. No training run has been performed.

## 6. Training-run design

A controlled SFT run should change one principal factor at a time. Record a baseline evaluation before training and compare checkpoints on the same held-out protocol. Keep a known-good base checkpoint and make the trained artifact's lineage unambiguous.

Typical run plan:

1. Validate training, validation and test split integrity; run leakage and rights checks.
2. Render/tokenize a small sample and inspect all fields, masks, shifts and truncation.
3. Run a finite-gradient smoke batch; assert intended target count and reduction.
4. Fix schedule, effective batch definition, optimizer, precision policy, seed policy and checkpoint cadence.
5. Track train/validation loss by target-token count and dataset slice; inspect gradient norms, learning rate and skipped updates.
6. Save checkpoints with configuration, tokenizer/template, data manifest, step and evaluation metadata.
7. Evaluate quality, guardrails and regressions at predeclared checkpoints; select using validation only.
8. Evaluate the chosen candidate once on the held-out test; preserve the test result for promotion decision.
9. Compare serving behavior, latency, memory, fallback and rollback under deployment-like prompts.

Low training loss proves fit to the sampled targets under the configured objective, not correctness, user benefit, broad generalization or safety. A model may simply memorize repeated examples or exploit artifacts.

## 7. Evaluation and regression controls

Define metrics by task and include a baseline. For structured outputs, measure schema validity and field-level correctness separately. For grounded answers, check support against source documents and distinguish abstention from unsupported claims. For dialogue behavior, use blinded human assessment with a written rubric and assess disagreement. For code or tool tasks, execute in a sandbox with safe constraints and evaluate both correctness and side effects.

Report:

- primary metric, unit of analysis, population, split, threshold and uncertainty;
- per-slice scores and worst-case/critical failure examples;
- refusal and policy-boundary behavior where relevant;
- general-capability regression checks beyond the target task;
- sequence-length, language, ambiguity and input-quality slices;
- training/serving template parity and artifact identity;
- evaluation cost and annotator/judge reliability;
- whether the test set influenced any prior decision.

Pair automated metrics with error analysis. Exact match may penalize semantically valid alternatives; judge models may be biased or inconsistent; average quality may hide a severe subgroup regression. Keep an auditable set of failed examples and map each proposed data change to the failure mode it is meant to correct.

## 8. Failure modes

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Training loss barely decreases | Wrong labels/shift, all targets masked, low learning rate, incompatible tokenizer/checkpoint | Inspect target counts, one-batch logits/labels, gradient norms and token IDs | Fix contract/config first; rerun tiny batch and verify loss changes on intended targets |
| Loss decreases but answers are malformed | Template mismatch, end-marker errors, truncation, metric blind spot | Inspect rendered/tokenized train and inference examples; validate raw decoded outputs | Align templates and target masks; evaluate exact served serialization |
| Model parrots prompt or user text | Prompt positions labeled; role boundaries corrupted | Audit shifted labels around role markers and compare loss contribution by token class | Correct mask/serialization and re-evaluate prompt leakage |
| Training score high, held-out score low | Leakage, duplicate rows, overfit, split mismatch | Group by source/entity/time; duplicate and contamination audit | Rebuild split at independence unit; retrain and preserve untouched test |
| Long answers dominate learning unexpectedly | Token averaging, loss weights or packing changed | Compare per-example target counts and effective loss contribution | Choose explicit token- or sequence-weight policy; recompute after collation |
| Short/long examples have distorted influence | Sequence mean versus token mean, truncation, rank-local normalization | Derive actual denominator across microbatches/ranks; bucket by length | Correct reduction or document intended weighting; test unequal-length batch |
| Validation improves, final test regresses | Repeated test peeking, distribution shift, small sample uncertainty | Review experiment history and test-set access; examine confidence intervals | Freeze a fresh independent test or gather valid new evaluation data |
| General behavior regresses | Narrow mixture, conflicting demonstrations, too many updates or high learning rate | Run baseline regression suite and slice behavior by domain/task | Rebalance/limit training or use a smaller intervention; require guardrails |
| Prompt injection or unsafe behavior grows | Untrusted text labeled as instruction, bad refusal examples, policy conflict | Trace data provenance/roles and run adversarial boundary probes | Repair dataset/policy and add external controls; do not rely solely on SFT |
| Effective training data differs from expected | Filtering, dedupe, packing or sampler bug | Reconcile row/token counts and sampled IDs with manifests | Fix pipeline and record exact post-transform counts before restart |

## 9. Practical decision: SFT or not?

Use SFT when the error is recurring, the desired behavior can be demonstrated, the training examples are authorized and representative, and held-out evaluation can test the intended change. Prefer a prompt, retrieval, validator or workflow fix when it directly closes the gap with lower complexity and adequate reliability. Preference optimization may be more suitable when the specification is inherently comparative and reliable ranking data is available; this method is covered separately.

A bounded acceptance plan states in advance:

- what failure SFT should change and what unrelated behavior must not regress;
- minimum held-out improvement and maximum guardrail regression;
- split and evaluation protocol, including uncertainty and reviewer rubric;
- equal-budget baseline and what cost categories count;
- deployment/rollback conditions and model/data owner;
- stop rule for label disagreement, leakage, unstable training or no material gain.

If the evidence is inconclusive, report it as inconclusive. Do not lower thresholds after seeing candidate results or relabel a failure as success because training loss improved.

## 10. Interview and self-check questions

### Q1. What probability does causal SFT maximize?
**Answer:** The model probability of each supervised next token conditioned on prior context and earlier target tokens.
**Reasoning:** The autoregressive likelihood factors into conditional token probabilities.
**Follow-up:** What does a loss mask do?
**Answer:** Selects which target-token terms contribute to the objective.

### Q2. In the worked example, what is token-average NLL?
**Answer:** 2.0 nats per target token.
**Reasoning:** Sum `[1,2,1,4]` to 8 and divide by four.
**Follow-up:** What is sequence-average NLL?
**Answer:** `8/3≈2.667` nats per example.

### Q3. Why do these reductions differ?
**Answer:** Token averaging gives each target token equal weight; sequence averaging gives each valid example equal outer weight.
**Reasoning:** Example A has three target tokens, B has one.
**Follow-up:** Which is correct universally?
**Answer:** Neither; choose and document the intended weighting.

### Q4. Do prompt tokens have to be excluded from model input if they are excluded from loss?
**Answer:** No; they can remain context while their target labels are ignored.
**Reasoning:** Attention context and target supervision are distinct.
**Follow-up:** Which masks answer those questions?
**Answer:** Attention/causal masks and loss masks, respectively.

### Q5. What is the danger of random row splitting conversations from one source?
**Answer:** Related/near-duplicate content can leak between train and evaluation.
**Reasoning:** Rows are not independent if they share source, user, document or time.
**Follow-up:** What should split unit reflect?
**Answer:** The deployment generalization claim and dependence structure.

### Q6. Why inspect labels after shifting?
**Answer:** The trainer may shift internally or expect pre-shifted labels; a mismatch targets the wrong token.
**Reasoning:** Causal logits predict the next token, not the token at the same input index under typical convention.
**Follow-up:** What can verify alignment?
**Answer:** A tiny known sequence with token IDs, labels, masks and logit positions inspected together.

### Q7. What can falling training loss establish?
**Answer:** The model fits sampled targets under that configured objective to some extent.
**Reasoning:** It does not test independent generalization or task quality.
**Follow-up:** What evidence is still needed?
**Answer:** Held-out evaluation, regression/guardrail tests and error analysis.

### Q8. What happens if all target positions are masked?
**Answer:** The loss denominator is zero or the implementation returns an invalid result; the batch must be rejected or handled explicitly.
**Reasoning:** A mean over zero valid targets is undefined.
**Follow-up:** What should the pipeline assert?
**Answer:** At least one valid target per contributing batch/example according to policy.

### Q9. Why can packing change the objective?
**Answer:** It changes boundaries, target counts, attention visibility and potentially per-example/token weighting.
**Reasoning:** Concatenated examples can accidentally condition on or predict across boundaries.
**Follow-up:** What must be tested?
**Answer:** Boundary masks, sequence resets/position semantics and actual loss denominators.

### Q10. When should SFT be stopped without promotion?
**Answer:** When the held-out change misses thresholds, harms guardrails, or the result is uninterpretable due to leakage/data defects.
**Reasoning:** Training completion is not product acceptance.
**Follow-up:** What alternative is valid?
**Answer:** Retain baseline and fix the diagnosed data/product/evaluation issue.

| Decision | Required check |
