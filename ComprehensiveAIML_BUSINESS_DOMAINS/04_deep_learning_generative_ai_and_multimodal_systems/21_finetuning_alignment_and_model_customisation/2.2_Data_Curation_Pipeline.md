## Learning outcomes

Learners can design a versioned curation pipeline from approved source through training-ready records; keep each transformation and exclusion auditable; select and evaluate parsing, filtering, deduplication and split policies; protect provenance and evaluation boundaries; and diagnose common data-quality failures without silently changing policy.

## 1. Curation is a sequence of governed transformations

Curation transforms source artifacts into data that can safely and meaningfully support a declared training objective. It is not a single cleaning command. Every stage has input assumptions, output schema, failure handling, counts, and versioned policy.

```text
source register and permission decision
             ↓
immutable acquisition snapshot and manifest
             ↓
parse / extract text and structure
             ↓
scope, quality, privacy and safety filters
             ↓
normalize and canonicalize for comparison
             ↓
deduplicate and resolve versions
             ↓
assign source/entity/time splits
             ↓
review samples and accept a frozen dataset
             ↓
hand off training-ready records with lineage
```

The ordering is not universal. For example, source-level access checks must precede processing, while some privacy checks are needed both before and after extraction. The pipeline contract should explain the order and why. Never make a transformation irreversible before preserving the approved raw snapshot and enough lineage to reproduce or remediate it.

The goal is not to maximize retained count. It is to produce an approved, fit-for-purpose, reproducible corpus whose known errors and exclusions are visible.

## 2. Define scope, schema, and acceptance gates

Before acquisition, define the training objective and the allowed data scope. Define required fields such as source ID, document ID, version, acquisition timestamp, language, source URI or controlled reference, permission status, content type, transform version, and any labels with their provenance. Use stable identifiers that do not expose personal or confidential values in logs.

An acceptance gate has:

- a named requirement and responsible owner;
- deterministic or documented decision logic;
- explicit pass, quarantine, reject, or review outcomes;
- a reason code and stage version;
- aggregate counts and a safely sampled audit trail;
- a policy for uncertain cases.

Use **quarantine** when evidence is insufficient and a human decision is required. Do not treat unknown license, parser output, language, or privacy status as an implicit pass. Record rejected data at the minimum level needed for counts and traceability without retaining prohibited content unnecessarily.

## 3. Acquisition and immutable manifests

Acquire only from approved source records. Save the source version or snapshot, acquisition date, retrieval method, and integrity hash. Verify archive contents and file types before extraction; impose safe limits on file size, nesting, decompression ratio, and parse time to reduce malformed or hostile input risk.

A manifest maps each source object to a stable document ID and records relevant rights, retention and transformation controls. Keep manifests separate from content where access restrictions differ. Avoid placing raw text, secrets, personal data, signed URLs, or unrestricted internal paths in broad-access logs.

A checksum detects byte changes but does not prove the source is authorized, complete, safe, or semantically unchanged. A mutable web page captured today and the same page captured next month should have separate snapshot records, even if some extracted text matches.

## 4. Parsing and extraction

Parsers convert source formats into a defined intermediate representation. Capture extraction errors, unsupported files, malformed records, encoding failures, table/heading structure loss, and empty or truncated content. A parser returning valid JSON does not prove the extracted text is faithful.

Parse quality should be checked by source type using manually inspected samples and automated invariants. Examples include page count, text length, expected metadata, table boundaries, code-block integrity, and character replacement frequency. Keep original offsets or references when downstream tools must return to the source.

Do not flatten all structure without considering task impact. Headings, table cells, code, speaker identity, timestamps, and document boundaries can carry meaning. Normalize only after preserving the source representation and a recoverable lineage map.

## 5. Filtering and transformation

Filtering may enforce scope, quality, privacy, safety, language, date, or task relevance. Each filter must be separately measurable. Combining many filters in one opaque rule makes false rejection difficult to diagnose.

For every rule, track:

- input population and denominator;
- accepted, rejected, and quarantined counts;
- exclusion reasons and rule version;
- sampled false-positive and false-negative review;
- impact by language, source, time, domain and other relevant slices;
- downstream quality and utility consequences.

Normalization may standardize Unicode, whitespace, markup, boilerplate, or metadata. Preserve both raw and normalized references when policy permits. Do not strip punctuation, code indentation, markup semantics, or non-Latin characters merely because they appear unusual. Transformation quality is task-specific.

Privacy filtering is not a blanket guarantee of anonymity. Exact-name and identifier detectors miss contextual clues and can incorrectly redact ordinary terms. Use the organization's approved privacy process, minimize access, and test residual risk on representative samples. Keep audit artifacts proportionate to sensitivity and retention constraints.

## 6. Deduplication policy

Deduplication reduces repeated exposure and can reduce benchmark leakage. It can also remove meaningful revisions, repeated legal language, intentionally repeated instructional patterns, or valid examples with shared boilerplate. Decide the unit and method in advance: exact bytes, normalized text, document, passage, near-duplicate cluster, or semantic similarity.

A defensible duplicate pipeline:

1. Define which overlaps are disallowed and for which objective.
2. Choose a candidate-generation method and similarity threshold appropriate to the source types.
3. Group candidates with stable cluster IDs and retain the original source IDs.
4. Review a stratified sample of accepted duplicate pairs, rejected pairs, and threshold-edge cases.
5. Define a deterministic representative policy (for example, authoritative/current version), not an arbitrary first-row choice.
6. Report removed records and token volume by source, version and reason.
7. Re-run evaluation contamination checks after material changes.

Exact hashing can find byte-identical files but misses formatting variants. Normalized exact hashes capture some variants but depend on normalization. Shingle or locality-sensitive methods retrieve candidates but can miss pairs or over-group boilerplate. Embedding similarity is not proof of duplication. A deduplication score should not be confused with verified duplicate labels.

Deduplication must preserve lineage from every removed record to its retained representative or cluster. If a source is later disallowed, traceability must support identifying the affected retained documents and derived artifacts.

## 7. Split design and leakage control

Split assignment should reflect the intended generalization question. Random document splits can be appropriate for independent exchangeable examples, but can leak when documents share source, person, organization, conversation, repository, case, event, or time series.

Choose the dependency unit before chunking. Assign all chunks from one parent document to the same split. Where the deployment goal concerns future content, use a time-based split and freeze the time cutoff. Where it concerns unseen users or entities, group by that identity under privacy safeguards. A mixed strategy can group by entity and then use a temporal boundary.

Keep tuning data separate from final test data. Control access to test examples and labels, and log any use in prompt examples, model-generated synthetic data, reviewer instructions, and iterative error analysis. A test set viewed repeatedly becomes part of the development feedback loop.

Split policies can cause distribution shifts or leave a very small slice. Report counts and relevant composition by split; do not imply representativeness based only on the split percentage.

## 8. Label and instruction quality

For supervised records, preserve the exact input, target, label source, instruction version, annotator/reviewer process and adjudication status. Labels should be task-specific and valid for the model behavior being trained. An answer can be factually correct but violate the desired format or policy; a preference label can reflect unclear instructions rather than a real preference.

Reviewers need a rubric, representative calibration examples, a way to mark ambiguity, and a defined adjudication path. Track inter-rater agreement only alongside the actual rubric and sampling procedure; a single agreement statistic does not establish label validity. Audit rare and high-impact categories, not just a random average sample.

For synthetic labels, retain generation model/version, prompt, sampling settings, filters, and human review status. Synthetic data can amplify teacher errors, stylistic artifacts, and source contamination. It is not independent evidence merely because it has a different file ID.

## 9. Reproducibility, lineage, and dataset release

A dataset release is defined by source snapshot identifiers, policy versions, parser and filter code/config versions, dedup policy, split manifest, tokenizer/format dependencies where applicable, and a content integrity reference. Pin environment and dependency versions that can alter extraction or normalization.

A reproducible release should answer:

- Which source records were eligible and why?
- Which rules transformed, excluded, quarantined or merged each record?
- Which exact split contains each retained parent record?
- Which code/config versions generated the release?
- How are sensitive data and restricted manifests protected?
- What is the procedure when a source is corrected, expires, or is withdrawn?
- Which training runs and model artifacts consumed this version?

A checksum of a whole dataset can verify an artifact but does not provide a usable lineage graph. Preserve row-level or object-level references under least-privilege controls. If authorized data removal cannot be mapped to training artifacts, record that as a governance limitation; do not claim automatic unlearning or complete erasure without evidence.

## 10. Worked pipeline-yield calculation

Illustrative pipeline input: 10,000 source documents. The parser successfully extracts 95%; 90% of parsed documents pass the declared scope/quality gate; a subsequent duplicate policy removes 10% of that eligible remainder. Assume every stage applies sequentially and each percentage uses the current-stage denominator.

```text
FORMULA [CURATE-01]: D_final = D_0 * r_parse * r_scope * (1-r_dup)
WHERE: D_0 = acquired documents [documents]; r_parse, r_scope = pass fractions [0..1];
       r_dup = duplicate-removal fraction applied to scope-pass records [0..1].
CONSTRAINT: all rates are illustrative; the sequence and denominator are explicitly specified.
NUMERICAL EXAMPLE: D_0=10,000; r_parse=0.95; r_scope=0.90; r_dup=0.10.
                   Parsed=9,500; scope-pass=8,550; final=8,550*0.90=7,695 documents.
INTERPRETATION: 7,695 is a yield estimate, not a quality score, rights determination, or measured pipeline result.
```

Independent check: 10,000 documents lose 500 parse failures; 9,500 remain. Ten percent of 9,500 is 950; after the scope gate, 8,550 remain. Ten percent of 8,550 is 855; `8,550-855=7,695`.

The sequential result is not equivalent to subtracting 5%, 10%, and 10% from the original count; the filters have different denominators. The quality gate should also report per-source rates. A single aggregate 90% pass rate can hide an accidental total exclusion of one language or source type.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Sudden large yield drop | Parser version change; new filter; source snapshot shift | Compare stage counts and reason codes by source and code version | Roll back or correct the identified stage; regenerate a versioned release |
| High retained count but poor text | Parser silently drops tables, headings or code | Manually inspect stratified output and structural invariants | Fix parser or preserve structure; rerun quality audit |
| Duplicates remain in training | Duplicate unit too narrow; normalization mismatch; split after chunking | Search exact and near-duplicate candidates across splits at parent level | Correct dedup/split order; re-evaluate contamination and affected runs |
| Excessive data removed | Threshold too aggressive; repeated templates; quality detector bias | Review false-positive samples by source and slice | Tune a bounded rule with measured tradeoff; preserve original snapshot |
| Sensitive content appears downstream | Source screening missing; extractor exposes metadata; redactor misses context | Trace sampled records from source through each transformation | Restrict access and follow incident process; block release until approved |
| Training and test overlap | Random split across dependent records; synthetic derivation leakage | Group by source/entity and inspect overlap lineage | Rebuild splits and evaluate on a clean test; document prior contamination |
| Cannot reproduce dataset | Mutable sources; unpinned transforms; missing split manifest | Re-run from source hashes and compare stage outputs | Pin dependencies and store manifests before training another release |
| Unapproved source persists in checkpoint lineage | Provenance lost during merges or shards | Trace source identifiers to dataset release and consuming runs | Contain affected artifacts and follow governance decisions; do not promise unlearning |

## 12. Interview and self-check questions

### Q1. Why is curation a pipeline rather than one cleaning step?
**Answer:** Different stages enforce different permissions, structure, quality, privacy and leakage requirements and need distinct denominators and audit evidence.
**Reasoning:** Opaque combined filters make failures hard to attribute.
**Follow-up:** What should each stage emit?
**Answer:** Versioned outputs, counts by reason, lineage, and sampled quality evidence.

### Q2. Why preserve source snapshots if normalized text is available?
**Answer:** Source snapshots support provenance, reproducibility, corrections and traceability through transformations.
**Reasoning:** Normalization can lose structure or change content.
**Follow-up:** Does a hash prove authorization?
**Answer:** No; it identifies bytes, not rights or safety.

### Q3. What makes a split leaky?
**Answer:** Dependent examples or evaluation content cross the boundary through shared source, entity, time, chunks, prompts or synthetic derivation.
**Reasoning:** The evaluation no longer tests the intended unseen unit.
**Follow-up:** What is the remedy for chunk leakage?
**Answer:** Assign parent documents before creating chunks.

### Q4. Why can near-deduplication reduce useful data?
**Answer:** It can merge meaningful revisions, repeated clauses, code variants or structurally similar but distinct examples.
**Reasoning:** Similarity is a candidate signal, not a task-independent truth label.
**Follow-up:** What validates a threshold?
**Answer:** Reviewed pairs and downstream quality/contamination analysis across representative sources.

### Q5. Why quarantine records with unknown provenance?
**Answer:** The pipeline cannot establish that use is permitted or that restrictions can be honored.
**Reasoning:** Absence of metadata is not evidence of permission.
**Follow-up:** What happens after resolution?
**Answer:** Apply the approved rule, record decision provenance, then include or reject deterministically.

### Q6. Compute the final yield after the example gates.
**Answer:** 7,695 documents.
**Reasoning:** `10,000*.95*.90*.90=7,695`.
**Follow-up:** Is 7,695 a quality score?
**Answer:** No; it is a count after illustrative pass fractions.

### Q7. How can a parser be wrong while producing valid text?
**Answer:** It can omit tables, reorder columns, merge headings, truncate pages or replace characters and still return a syntactically valid string.
**Reasoning:** Format validity is not semantic fidelity.
**Follow-up:** How do you detect it?
**Answer:** Stratified manual inspection plus source-specific structural invariants.

### Q8. What does a dataset release need for reproducibility?
**Answer:** Pinned source snapshots, transformation/config versions, split manifest, integrity references, and data lineage.
**Reasoning:** A mutable source and unpinned parser can change outputs.
**Follow-up:** Is one whole-dataset checksum enough?
**Answer:** No; it cannot identify affected records or explain transformations.

### Q9. Why inspect filter error by language or source?
**Answer:** Aggregate accuracy can hide systematic exclusion or retention errors in a subgroup.
**Reasoning:** Different content types trigger detectors differently.
**Follow-up:** What should follow a discovered bias?
**Answer:** Correct the rule, regenerate the release and recheck downstream effects.

### Q10. What is the difference between deletion from a data release and deletion from trained weights?
**Answer:** Removing a source record from a future release does not prove its influence has been removed from an already trained model.
**Reasoning:** Training artifacts require separate lineage and validated remediation.
**Follow-up:** What is a safe claim?
**Answer:** State exactly which dataset artifacts were updated and what model-level remediation, if any, was actually demonstrated.

## Quick reference card

| Pipeline control | Minimum practice |
|---|---|
| Source gate | Approve the specific source and purpose before training use; quarantine uncertainty. |
| Acquisition | Pin snapshot, identity, date, integrity hash and controlled provenance. |
| Parsing | Version parser; inspect representative outputs and source-specific structure. |
| Filtering | Separate rules and denominators; report exclusions, quarantine and slice effects. |
| Deduplication | Define unit, threshold, representative policy and audit false merges/misses. |
| Splitting | Group dependencies before chunking; protect test data from iterative tuning. |
| Lineage | Preserve source-to-transform-to-release-to-run relationships under least privilege. |
| Reproducibility | Pin source and transform versions; save a split manifest and release metadata. |
| Remediation | Trace affected data and artifacts; do not imply model unlearning without evidence. |
| Evidence | Yield math is illustrative; no live corpus or pipeline was measured. |
