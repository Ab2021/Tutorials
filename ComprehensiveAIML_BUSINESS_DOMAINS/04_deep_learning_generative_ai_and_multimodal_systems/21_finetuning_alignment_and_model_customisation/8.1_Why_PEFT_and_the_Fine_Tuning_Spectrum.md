## Learning outcomes

Given a task, base model, data and deployment constraints, learners can choose among prompting, retrieval, full fine-tuning and parameter-efficient fine-tuning (PEFT); estimate trainable adapter parameters and raw base-weight storage; distinguish trainable-parameter savings from total training/serving memory; select a strategy based on quality, cost, multi-tenant lifecycle and reversibility; and define evaluation and rollback gates.

## 1. Adaptation is a spectrum of interventions

Adapting a model need not mean changing every parameter. The choice spans system prompts and examples, retrieval/tools, output validators, adapters or other PEFT methods, and full-parameter fine-tuning. Some tasks need no weight change: current/private facts may call for retrieval; a hard schema can be validated deterministically; a behavior already present may need a clearer prompt. Training is more defensible when a repeatable pattern cannot be supplied reliably through context or external controls and valid training data exists.

**Full fine-tuning** updates all or most model parameters. It offers broad capacity for changing representations but requires optimizer state/gradient memory, compute, carefully curated data and a deployment artifact for each resulting model (unless weights are otherwise shared). It risks broad regression, forgetting, data leakage and high recovery cost.

**PEFT** updates a smaller set of parameters while freezing most of a base model. Common forms include low-rank updates (LoRA), quantized-base plus adapters (QLoRA-style), prompt/prefix tuning and other adapter/low-rank variants. Their details and compatibility vary. PEFT can reduce trainable-state memory and make task-specific artifacts smaller, but the frozen base still has to be stored, loaded and served; activation memory, optimizer state, sequence length and runtime overhead remain relevant.

A practical spectrum:

1. **Prompt/in-context examples:** no learned weight update; fast to revise, but limited context budget and prompt sensitivity.
2. **Retrieval/tool/control:** externalizes fresh facts or deterministic operations; requires access control, retrieval quality and runtime reliability.
3. **PEFT/adapters:** learns task-specific deltas; base compatibility and adapter lifecycle become hard constraints.
4. **Full fine-tuning:** broad parameter updates; largest trainable state and highest model-artifact/retraining burden, but may be needed for broad changes.

This order is a diagnostic guide, not a rigid maturity ladder or guarantee that cost always increases monotonically. A retrieval system may cost more operationally than a small adapter; serving many adapters can exceed one fine-tuned model's complexity.

## 2. Low-rank update parameter accounting

For a dense projection matrix `W` with shape `d_out × d_in`, a LoRA-style low-rank update can be written `DeltaW = B A`, where `A` has shape `r × d_in`, `B` has shape `d_out × r`, and rank `r` is usually much smaller than both dimensions. The number of trainable matrix parameters is `r*d_in + d_out*r = r(d_in+d_out)`. This counts the two adapter matrices only; biases, modules, embeddings, normalization, optimizer state and additional trainable parameters are excluded.

```text
FORMULA [PEFT-01]: N_adapter = r*(d_in+d_out)
                  N_dense = d_in*d_out
                  fraction = N_adapter/N_dense
WHERE: d_in, d_out are projection dimensions [parameters/axis]; r is positive
       integer rank; counts are trainable scalar parameters.
CONSTRAINT: assumes both low-rank matrices are trainable and the base matrix is
            frozen; excludes biases, embeddings, other adapted layers and all
            optimizer/gradient/activation memory.
NUMERICAL EXAMPLE: d_in=d_out=4096, r=16;
                   N_adapter=16*(4096+4096)=131,072;
                   N_dense=4096*4096=16,777,216;
                   fraction=131,072/16,777,216=0.0078125=0.78125%.
INTERPRETATION: this projection has about 128x fewer trainable adapter scalars
                than dense weights; it does not imply 128x lower total memory,
                faster training, or equivalent task quality.
```

If a scaling convention uses `alpha/r`, with `alpha=32` and `r=16`, the multiplier is `2`. This is a configuration factor, not a parameter count or universal LoRA formula; some implementations use different scaling variants. Confirm initialization, dropout, target modules and scaling semantics in the actual library.

## 3. Raw storage versus total memory

For an illustrative 4,096×4,096 matrix, there are 16,777,216 scalar weights. At 16 bits per weight, payload storage is `16,777,216*2=33,554,432 bytes=32 MiB` (binary MiB). At 4 bits per weight, idealized raw payload is `16,777,216*0.5=8,388,608 bytes=8 MiB`, excluding quantization scales/zeros, packing alignment, metadata and allocator overhead. The raw payload ratio is 4:1 under this idealized bit-width comparison.

Quantizing a base does not make all training memory four times smaller. A training run may still allocate adapter gradients and optimizer state, activations, temporary dequantization buffers, workspace, checkpoint staging and communication buffers. Quantization metadata and block granularity add storage; some operations dequantize on the fly or materialize wider values. Actual memory is a measured property of model, sequence length, batch, checkpointing, optimizer and kernel implementation.

Keep separate estimates:

- **Base payload:** packed weight bytes plus quantization metadata.
- **Trainable parameters:** adapter/selected parameters and their gradients.
- **Optimizer state:** often wider than adapter weights; optimizer-specific.
- **Activations:** depend strongly on batch, sequence, hidden dimensions and checkpointing.
- **Runtime temporaries:** dequantization, attention, workspace and allocator fragmentation.
- **Serving footprint:** base, active adapter(s), KV cache, workspace and batching policy.

A smaller adapter checkpoint can simplify distribution while base loading remains the dominant cold-start cost. Conversely, an adapter bank can multiply cache pressure and routing complexity. Profile both training and serving for the target workload.

## 4. Choosing method from the diagnosed gap

| Need/constraint | Candidate | Main checks |
|---|---|---|
| Known behavior is available with clear instructions | Prompt/example change | Robustness across paraphrases and context competition |
| Current/private facts or authoritative grounding | Retrieval/tools | Freshness, source quality, access control and citation accuracy |
| Deterministic schema or action safety | Validator/workflow control | False rejects, bypass paths and failure recovery |
| Narrow, repeatable behavior shift with modest training budget | PEFT/adapter | Held-out quality, base compatibility, lifecycle and serving overhead |
| Broad representation/domain update with extensive valid data | Full fine-tuning or continued training | Full cost, forgetting, regression, checkpoint lineage and recovery |
| Multiple related tasks/tenants with isolated task deltas | Adapter family or routing | Cross-tenant isolation, cache key/version pinning, contention and rollback |

First establish the baseline failure, data rights, quality target, worst-case risk, memory budget and serving model. Compare interventions against a simple baseline with the same evaluation set. Use full fine-tuning only when the broader update is needed and its added cost/regression risk is justified. Use PEFT only when the task delta is compatible with a fixed base and adapter serving is operationally sound.

## 5. Adapter lifecycle and compatibility

An adapter is not self-describing merely because its tensor shapes load. Record the exact base checkpoint hash/revision, architecture/config, tokenizer and vocabulary, template, target module names, rank/alpha/scaling, dropout, quantization recipe, training data manifest, code and optimizer configuration. Compatibility must be checked when loading or merging; matching a model name is not sufficient.

Lifecycle decisions:

- **Versioning:** immutable adapter IDs with base revision and data lineage.
- **Selection:** route only authorized task/tenant adapters; avoid trusting a user-supplied name.
- **Loading/cache:** key by base and adapter versions plus dtype/device; bound memory and eviction.
- **Concurrency:** define whether adapters can be swapped per request/batch; test races and session pinning.
- **Isolation:** prevent one tenant's adapter/data/output from influencing another request; test negative cases.
- **Rollback:** keep prior adapter and known-good base, configuration and routing rules.
- **Retirement:** remove artifact/cache entries and handle dependent workflows without silently changing model behavior.

Merging adapter weights into a dense base can reduce runtime composition overhead for one fixed model but creates a new artifact and may lose the ability to switch adapters. The merged artifact must be validated against the unmerged composition for the target dtype and kernel path. Weight merging between independently fine-tuned models has stricter compatibility requirements discussed in the dedicated module 8.5 topic; do not infer compatibility from equal tensor shapes alone.

## 6. Quality, regression and economic evaluation

An adaptation experiment should report task quality and general regressions alongside training/serving costs. Use the same prompts, task policy, retrieval, decoding and evaluation rubric for the baseline and candidate. Include task-specific held-out examples, out-of-domain prompts, refusal/safety boundaries, subgroup/language slices and error analysis. Track uncertainty and data provenance; a small test set is not a broad guarantee.

For cost, specify lifecycle horizon and include data collection/labeling, engineering, compute, checkpoint storage, deployment, adapter routing/cache, monitoring and rollback. Compare cost per successful task outcome or time-to-quality, not only trainable parameter count. Estimate peak device memory from actual tensor/state/activation configuration and validate by profiling; raw weight bytes are only one component.

If the adaptation is for several tenants or tasks, calculate both shared-base and adapter-specific operating costs. Measure cold-load latency, cache hit rate, active adapter working set, memory headroom and routing/failure rates. Consider whether the shared base is allowed to be reused across tenants under the data policy; adapter isolation does not automatically prove training-data isolation.

## 7. Failure modes and diagnosis

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Adapter trains but behavior barely changes | Wrong target modules, low rank/signal, frozen/trainable parameter bug, evaluation mismatch | Inspect trainable parameter names/gradients and before/after logits on a discriminating set | Correct configuration first; controlled rank/data sweep with held-out gate |
| Train quality rises, general quality falls | Narrow data, overfit, forgetting, excessive updates or label conflict | Regression suite by task/language/safety slice; compare checkpoints | Reduce scope/updates or rebalance; retain base rollback and require guardrail pass |
| “4-bit base” does not fit expected memory | Metadata, activations, optimizer, temp buffers, fragmentation or workspace | Measure per-component peak and allocated/reserved memory at target sequence/batch | Recompute complete memory budget; reduce identified component, not guessed bits/weight |
| Adapter fails on a similarly named base | Wrong checkpoint revision, target modules, vocabulary/config or quantization setup | Compare hashes/config/tokenizer and state-dict keys; run exact-load and output checks | Pin compatible base and rebuild/validate; do not ignore missing/unexpected key warnings |
| Merged output differs from adapter output | Merge scaling/dtype/order, quantization, rounding or unsupported module | Compare layer/output and task logits across representative shapes/dtypes | Use supported merge path or retain unmerged serving; validate the exact merged artifact |
| Adapter routing leaks task/tenant state | Cache key omits tenant/base/version, hot swap races, session not pinned | Cross-tenant negative tests, concurrent adapter-swap stress and trace IDs | Fix routing/isolation before use; invalidate unsafe cache entries and retest |
| Many adapters increase serving latency | Cold loads, cache churn, synchronization or dynamic batching fragmentation | Measure latency by cache state and adapter working set | Bound/partition adapter bank or prewarm approved hot set; compare full fine-tune alternative |
| Quantized adapter matches average but fails rare slice | Outlier sensitivity, quantization error or data coverage gap | Slice errors by activation/weight outliers and task subgroup; compare higher precision | Use targeted supported precision/quantization or narrow scope; rerun regression gates |
| Parameter-count savings presented as speedup | Trainable count confused with total operations, memory traffic or wall time | Profile step time, throughput, memory and time-to-quality | Report the measured metric and exact workload; remove inferred speedup claim |
| Training artifact cannot be reproduced | Missing base/data/template/config versions or sampler nondeterminism | Reconcile manifests, hashes, seeds, software versions and run metadata | Restore lineage; rerun only after snapshotting complete inputs |

## 8. Bounded method-selection exercise

**Scenario:** A team has one fixed policy-QA task, a read-only authoritative document store, a 24-GiB training-memory limit and a 16-GiB serving-memory budget. It observes occasional answers that ignore the required output schema and asks whether to fine-tune. No measurement or production result is provided.

Decision steps:

1. Reproduce the schema failure and separate model output from parser/UI errors.
2. Add a deterministic schema validator and test whether prompt/example changes meet the acceptance target.
3. Since facts must come from the document store, evaluate authorized retrieval separately; do not train stale policy facts into weights as a substitute for source access.
4. If a repeatable behavior gap remains, compare a LoRA adapter with full fine-tuning using the same licensed demonstrations and held-out policy/source split.
5. Estimate base, optimizer, gradients, activations, temporary buffers and serving cache—not just adapter parameters—then profile the real training/serving configuration.
6. Test schema validity, grounded correctness, refusal behavior, regression, cold-load and rollback; select only if thresholds and budgets pass.

This decision may favor a validator/retrieval combination without training; a PEFT candidate is conditional on measured residual failures. No approach is selected in advance because actual baseline and measured hardware/model results are absent.

## 9. Interview and self-check questions

### Q1. What is PEFT?
**Answer:** Updating a smaller selected parameter set while most base parameters remain frozen.
**Reasoning:** It reduces trainable state relative to full fine-tuning but not every workload cost.
**Follow-up:** Name one PEFT method.
**Answer:** LoRA, adapter tuning, prompt/prefix tuning or another validated variant.

### Q2. How many rank-16 LoRA parameters for a 4096×4096 projection?
**Answer:** `16*(4096+4096)=131,072`.
**Reasoning:** Two low-rank factors contain `r*d_in` and `d_out*r` parameters.
**Follow-up:** What fraction of the dense 16,777,216 parameters?
**Answer:** `0.78125%`.

### Q3. Does that mean total training memory is 0.78125% of full fine-tuning?
**Answer:** No.
**Reasoning:** Base weights, optimizer/gradient state, activations and temporaries remain.
**Follow-up:** How determine actual peak?
**Answer:** Profile the exact configuration and attribute memory components.

### Q4. What does alpha/r=2 mean for alpha 32 and rank 16?
**Answer:** A scaling multiplier of 2 under that convention.
**Reasoning:** `32/16=2`.
**Follow-up:** Is it universal?
**Answer:** No; implementations can use other scaling conventions.

### Q5. How much raw storage is a 4096×4096 matrix at 4 bits?
**Answer:** `8,388,608 bytes=8 MiB`, excluding metadata.
**Reasoning:** `16,777,216*0.5 bytes`.
**Follow-up:** Does this predict QLoRA peak memory?
**Answer:** No; activations, optimizer, metadata and temporary buffers remain.

### Q6. When is retrieval preferable to training?
**Answer:** When facts are current, private, authoritative or need source grounding.
**Reasoning:** A weight update does not supply freshness or access-controlled provenance.
**Follow-up:** What must retrieval enforce?
**Answer:** Correct document selection, authorization and reliable grounding.

### Q7. Why can two adapters be incompatible despite identical tensor shapes?
**Answer:** Base checkpoint, module mapping, tokenizer, config, scaling or quantization can differ.
**Reasoning:** Shape compatibility is necessary but not semantic identity.
**Follow-up:** What should be pinned?
**Answer:** Exact base revision/hash and adapter training/config provenance.

### Q8. What is a risk of merging adapters into a base?
**Answer:** It creates a new artifact and may remove runtime switchability or change numerical outputs.
**Reasoning:** Merge operation/dtype/order and serving path affect behavior.
**Follow-up:** What comparison is required?
**Answer:** Validate merged against unmerged outputs and task metrics on target configurations.

### Q9. What does adapter isolation not guarantee?
**Answer:** It does not by itself guarantee training-data isolation or safe routing/cache behavior.
**Reasoning:** Data provenance and runtime state are separate controls.
**Follow-up:** Name an operational test.
**Answer:** Cross-tenant negative tests and concurrent adapter-swap/session-pinning checks.

### Q10. What is a defensible method-selection basis?
**Answer:** Diagnosed gap, valid data, held-out quality, risks, lifecycle cost, hardware profile and rollback feasibility.
**Reasoning:** Parameter count alone is not user benefit or total cost.
**Follow-up:** What if a simple validator meets the target?
**Answer:** Avoid training unless another measured requirement justifies it.

## 10. Quick reference

| Decision | Evidence required |
|---|---|
| Prompt/retrieval/control or weight update? | Failure diagnosis, source/freshness requirements and simple baseline |
| Full FT or PEFT? | Needed capacity, data, total memory/compute, regression and lifecycle analysis |
| How big is the adapter? | Rank × adapted dimensions, with all excluded parameters stated |
| Is quantized base feasible? | Payload plus metadata, activations, optimizer, temporaries and measured peak |
| Can adapter ship safely? | Base compatibility, tenant routing, cache/concurrency, monitoring and rollback |
| Did the adaptation help? | Held-out task quality, safety/regression slices, uncertainty and cost per outcome |
