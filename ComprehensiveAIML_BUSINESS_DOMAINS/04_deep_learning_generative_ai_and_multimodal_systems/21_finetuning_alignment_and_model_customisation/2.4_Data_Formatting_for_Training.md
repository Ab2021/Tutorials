## Learning outcomes

Learners can convert approved conversation or task records into a model-specific serialized format; distinguish prompt tokens from target tokens; define label and attention masks; handle padding, truncation, packing and end markers without losing alignment; and test that training examples encode the intended task rather than formatting artifacts.

## 1. Formatting is part of the task definition

A training record is not just text. Formatting determines which roles and boundaries the model sees, which tokens are predicted, which positions can attend to one another, and how the loss is computed. A correct source example can become a wrong training target through an incorrect chat template, mask, truncation rule, or tool-result boundary.

The formatting pipeline typically transforms a structured example into:

- **input token IDs**: the serialized sequence presented to the model;
- **attention mask or position metadata**: which positions exist and can interact under the model's attention rules;
- **labels**: target token IDs or ignored positions;
- **loss weights**: optional per-token or per-example weights;
- **provenance**: source example, template version, tokenizer version, and transform configuration.

Keep source structure until the final serialization stage. Store raw role/content fields separately from rendered text so the same data can be reserialized when the template changes and so that template defects can be isolated from source defects.

## 2. Structured examples and chat templates

Represent a conversation as ordered messages with explicit roles and typed content. Common roles include system, developer, user, assistant, and tool, but a particular model may support a subset or use different syntax. Tool calls are assistant messages with structured recipient/arguments in some formats; tool output is a separate message. Do not flatten tool calls into plain prose if the model is expected to learn the control flow.

A chat template serializes structured messages into a token sequence with role markers, separators, optional channel metadata, and turn-ending markers. Template syntax is model-specific. An end-of-message, end-of-turn, and handoff-to-tool marker may be distinct. They are not interchangeable just because each appears at a message boundary.

The exact serialized result is part of the model interface. Version the template and tokenizer together. Test representative conversations by inspecting rendered text and token IDs, not by assuming a library's “chat format” matches a checkpoint.

### Template contract

For each template, document:

1. accepted message roles and content types;
2. role/order constraints and behavior on missing or duplicate messages;
3. exact boundary and end-of-turn markers;
4. tool-call and tool-result serialization;
5. escaping of untrusted text and literal marker spellings;
6. whether an open assistant prefix is allowed for inference;
7. target-label and loss-mask policy for each token class;
8. truncation and packing rules;
9. tokenizer and template version compatibility.

A rendered prompt that “looks right” is insufficient if token IDs or labels differ from the intended contract.

## 3. Inputs, targets, labels, and causal shift

In causal language modeling, logits at one sequence position are commonly trained to predict the next token. Frameworks differ on whether they shift labels inside the model/loss function or expect pre-shifted labels. Confirm the actual trainer contract before constructing labels; applying the shift twice or not at all causes off-by-one training.

For a serialized token sequence `x_0, x_1, …, x_(n-1)`, next-token training conventionally predicts `x_(t+1)` from positions through `x_t`. A label mask decides which target positions contribute to the objective. To exclude prompt tokens while learning the assistant answer, the mask must align with assistant target tokens after the implementation's shift convention.

Many implementations use an ignore sentinel (often a configured value such as `-100`) for target positions excluded from cross-entropy; the value is framework-specific. Padding can be masked with the attention mask, label ignore value, or both, depending on implementation. Attention and loss masks answer different questions: “may this position participate in attention?” versus “does this target position contribute loss?”

Do not infer mask semantics from field names. Inspect a batch after collation and verify the loss function's exact interpretation.

## 4. Prompt loss versus answer-only loss

A standard language-model objective may predict all non-padding tokens, including prompt tokens. Supervised fine-tuning often masks user/system prompt positions and applies loss to assistant targets only. Neither policy is universally correct; select according to the intended objective and preserve the decision in the dataset contract.

For assistant-only loss:

- include context tokens in model input so the answer is conditioned on them;
- ignore prompt target positions as specified by the trainer convention;
- include the intended assistant response and any required end marker;
- exclude padding and any untrusted/control spans that should not be targets;
- ensure tool-result text is not accidentally labeled as assistant output.

If user and assistant messages are concatenated, a missing role boundary can make the model learn to continue user text as though it were its own answer. Inspect the exact transition tokens and labels.

## 5. Worked label-mask example

Schematic token sequence:

```text
[SYSTEM: S1 S2] [USER: U1 U2 U3] [ASSISTANT: A1 A2] [TURN_END] [PAD]
```

Suppose the objective is assistant-only response loss and the template semantics make `A1`, `A2`, and `TURN_END` the assistant's target tokens. The system/user tokens remain in the input as context, but their target positions are ignored. The pad position is also ignored and excluded from attention as required by the model implementation.

```text
FORMULA [FORMAT-01]: N_loss = sum_i I(label_i is not ignored and position_i is a valid target)
                    loss_fraction = N_loss / N_valid_target_positions
WHERE: label_i = implementation-aligned next-token target; I = indicator; N_loss = contributing labels.
CONSTRAINT: labels are aligned to the trainer's shift convention; prompt, pad, and non-target roles are masked by explicit policy.
NUMERICAL EXAMPLE: serialized sequence has 2 system, 3 user, 2 assistant, 1 turn-end and 1 pad token.
                   Assistant-only policy yields 3 contributing targets: A1, A2, TURN_END.
                   The 5 prompt tokens and 1 pad token do not contribute; 3 of 8 non-pad target positions are loss-bearing.
INTERPRETATION: prompt context remains available to condition the answer, but is not itself supervised under this policy.
```

This is a schematic count. In a real next-token objective, the first token may be provided by a preceding boundary position, labels may be shifted internally, and target positions can be counted differently by the trainer. Validate with a tiny known sequence and inspect the actual logits/labels pairing. The answer marker or end marker may be included or excluded based on the intended training task.

## 6. End markers, incomplete turns, and tool calls

End markers signal different control transitions only if the model/template defines them that way. A user-message boundary, assistant-turn completion, and tool handoff may require distinct markers. Using the wrong end marker can teach the model to stop early, continue when it should stop, or fail to invoke a tool.

Training examples should reflect actual inference behavior. If the model is prompted with an open assistant prefix at inference, examples should use compatible boundaries. If tool use is in scope, include valid assistant tool-call structure, a corresponding tool result, and the assistant continuation where appropriate. Validate arguments and escape boundaries; do not treat untrusted tool output as trusted instructions by default.

For multi-turn training, decide whether all assistant turns are targets or only a final answer. Ensure target masks reflect that choice and prevent system/user/tool tokens from being accidentally optimized as assistant responses.

## 7. Padding, truncation, and batching

Padding makes examples in a batch share a length. The attention mask generally marks which positions correspond to real sequence content, but exact use varies by architecture and attention implementation. The loss mask must also prevent padding labels from contributing. If pad ID equals an end token ID, token ID equality alone cannot identify padding; use explicit sequence lengths/masks.

Truncation must preserve essential structure and label alignment. For long examples, define whether to truncate left/right, drop examples, retain answer spans, split into windows, or summarize upstream. Truncating away the user question while keeping the answer creates a misleading target; truncating away the answer marker can change stop behavior.

Test lengths at zero, one, max length minus one, max length, and max length plus one where valid. Confirm no token/label shift, no dropped final answer without a recorded reason, and no position that is simultaneously padding and loss-bearing.

## 8. Packing independent examples

Packing concatenates multiple examples into a fixed-length sequence to reduce padding. It is safe only when boundary and attention semantics preserve the intended independence. A separator token alone does not guarantee isolation: standard causal attention lets later examples attend to earlier tokens unless attention masks or position/segment policy prevent it.

Possible policies include:

- **Independent-example packing:** block cross-example attention and reset relevant positions as required.
- **Document-stream training:** concatenate text intentionally and permit cross-document context according to the objective.
- **Naive concatenation:** rely on end markers without attention isolation; valid only if that interaction is intended.

The choice affects context, loss, and data leakage. For supervised chat examples, accidental cross-example conditioning can expose one example to another and alter behavior. Record packing policy and test a batch whose examples contain unmistakable sentinel tokens; verify the second example cannot access the first where isolation is required.

## 9. Weights, selective targets, and denominators

Some objectives assign token or example weights. Weighted loss changes the effective contribution of records and can affect normalization. State whether the denominator is number of examples, number of non-ignored tokens, sum of token weights, or another quantity. Different denominator choices produce different gradient scales even with identical labels.

When examples are length-normalized, a short and long answer may contribute comparable total weight. When tokens are equally weighted, long answers contribute more. This is a modeling choice, not a formatting detail to leave to a library default.

For a batch with valid weighted targets, a generic weighted mean is `sum_i w_i * loss_i / sum_i w_i`. Some implementations instead divide by count of tokens or batch size. Verify the actual reduction. Log loss-bearing token counts and weights so run-to-run comparisons have a meaningful denominator.

## 10. Data-format validation

Before training at scale, inspect a small batch from raw structured record through final model input. For each example, display or safely decode:

- source roles/content and provenance reference;
- rendered template string and token IDs;
- attention/position metadata;
- labels after any shift convention;
- loss mask and weights;
- truncation and packing boundaries;
- decoded model targets and expected assistant/tool behavior.

Automated invariants should check role order, required end markers, non-empty target spans where expected, padding/label consistency, sequence length, allowed special tokens, and absence of prohibited fields. Golden examples should cover ordinary turns, multi-turn context, tool handoff, empty content, Unicode, long inputs, truncation, and malformed structures.

Test the collated batch, not only the pre-collation record. Collators may pad, shift, concatenate, mask, or reorder fields. A correct preprocessing row can become incorrect during batching.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Model copies the prompt or user voice | Prompt positions labeled; role markers missing; label shift wrong | Inspect token/label pairs and role boundaries on one batch | Correct template/mask and add a loss-mask regression example |
| Assistant answer is not learned | Answer tokens ignored; label offset wrong; truncation removes target | Count expected and actual target IDs after collation | Fix target alignment; verify loss on a tiny deterministic batch |
| Model stops too early or continues incorrectly | End marker semantics mixed or missing | Inspect end-of-turn/tool handoff tokens and generations | Use the checkpoint-compatible marker and test turn transitions |
| Loss changes with batch padding | Pad labels not ignored; reduction denominator includes pads | Compare same examples under different batch lengths | Correct attention/loss masks and denominator policy |
| Packed examples influence each other | Cross-example attention unmasked; position reset mismatch | Sentinel test with distinct preceding example content | Isolate examples or explicitly adopt stream semantics |
| Tool output is learned as assistant instruction | Tool role flattened or labeled as assistant | Inspect serialized roles and target masks | Preserve tool role and mask according to objective |
| Training/inference mismatch | Different template, tokenizer or open-prefix convention | Compare exact token IDs on shared conversation fixtures | Pin template/tokenizer and add parity tests |
| Long examples have degraded targets | Truncation cuts response or boundaries | Inspect near-limit examples and retained target positions | Set explicit truncation/window policy and audit impact |

## 12. Interview and self-check questions

### Q1. What does a chat template do?
**Answer:** Serializes structured messages and control transitions into a model-specific token sequence.
**Reasoning:** Roles, boundaries and end markers are part of the learned interface.
**Follow-up:** Is one template interchangeable with another?
**Answer:** No; verify checkpoint compatibility and exact token IDs.

### Q2. What is the difference between attention mask and loss mask?
**Answer:** Attention mask controls which positions participate in attention; loss mask controls which targets contribute to the training objective.
**Reasoning:** A prompt token can be visible context but not a supervised target.
**Follow-up:** Can padding affect both?
**Answer:** Yes, but exact implementation semantics must be verified for each mask.

### Q3. Why can prompt tokens remain in input while excluded from loss?
**Answer:** They condition the model's response, while the objective supervises only selected answer targets.
**Reasoning:** Context and target are distinct roles in supervised training.
**Follow-up:** Is assistant-only loss mandatory?
**Answer:** No; select and document the objective explicitly.

### Q4. Why inspect labels after collating?
**Answer:** The collator may pad, shift, pack, or mask records and can introduce alignment errors.
**Reasoning:** Pre-collation data does not prove the model receives correct targets.
**Follow-up:** What tiny test is useful?
**Answer:** A short known sequence with expected input IDs, labels, ignored positions and next-token pairing.

### Q5. Does an end-of-message marker always mean the assistant turn is done?
**Answer:** No; message end, turn end and tool handoff can have distinct semantics.
**Reasoning:** Model formats may encode different control transitions.
**Follow-up:** What if one marker is substituted for another?
**Answer:** The model may stop, continue, or call tools incorrectly.

### Q6. Why is a separator insufficient for independent packed examples?
**Answer:** Causal attention may still let the later example attend to earlier tokens.
**Reasoning:** Token boundaries and attention isolation are separate mechanisms.
**Follow-up:** How do you test isolation?
**Answer:** Use sentinel content and confirm later outputs cannot depend on earlier packed examples under the intended mask.

### Q7. What should be excluded from assistant-only loss?
**Answer:** Prompt, padding, and non-target role tokens according to the stated objective; tool outputs are not automatically assistant targets.
**Reasoning:** Labels must match the desired behavior and role semantics.
**Follow-up:** Should the final end marker be trained?
**Answer:** Decide based on model/template behavior and test the stopping transition.

### Q8. How can padding change loss if labels are correct for real tokens?
**Answer:** Padding may be included in the reduction denominator or accidentally receive a valid label.
**Reasoning:** Loss normalization changes gradient scale.
**Follow-up:** What should be logged?
**Answer:** Non-padding and loss-bearing token counts and the exact reduction denominator.

### Q9. What can truncation do to a supervised example?
**Answer:** Remove instructions, role boundaries, answer tokens or end markers and leave a misleading partial target.
**Reasoning:** The retained span determines model context and supervision.
**Follow-up:** What is a robust policy?
**Answer:** Explicit, tested handling at length boundaries with recorded drop/window decisions.

### Q10. Why version the template alongside tokenizer and checkpoint?
**Answer:** The template's markers and tokenization define the model-facing sequence contract.
**Reasoning:** A mismatch changes input IDs and control semantics.
**Follow-up:** What is minimum compatibility evidence?
**Answer:** Exact rendered strings/token IDs and label-mask tests on representative conversations.
