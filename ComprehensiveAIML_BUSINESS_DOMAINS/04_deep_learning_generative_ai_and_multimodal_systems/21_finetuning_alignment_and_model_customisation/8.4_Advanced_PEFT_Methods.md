## Learning outcomes

Given a base model, a behavior gap and deployment constraints, learners can distinguish bottleneck adapters, soft/prefix prompts, IA3-style activation scaling and LoRA-family variants; calculate adapter and prefix-state counts; choose an adaptation locus from the actual constraint; reason about multi-adapter routing and composition; and validate quality, isolation, runtime cost and rollback before deployment.

## 1. Advanced PEFT is a placement choice

PEFT methods differ primarily in **where** they introduce trainable degrees of freedom and **how** those degrees affect the frozen network:

- **Bottleneck adapters:** small trainable down-projection/nonlinearity/up-projection paths inserted into transformer blocks.
- **Soft prompt / prompt tuning:** learned embedding vectors prepended to an input; the base model weights remain frozen.
- **Prefix tuning:** learned virtual key/value (or transformed prefix) states supplied to attention layers; implementations differ in representation and projection.
- **IA3-style scaling:** learned multiplicative vectors applied to selected activations or attention/FFN components.
- **LoRA-family variants:** low-rank residual updates to selected linear projections; scaling, initialization, decomposition and target-module choices vary.

No method is universally “more parameter-efficient.” Parameter count is only one dimension. Compare behavior coverage, data, base compatibility, training memory, inference latency, adapter-bank operations, composition rules, monitoring and reversibility. A learned prefix can be small in checkpoint bytes while increasing every request's effective sequence length; a bottleneck adapter can be compact but add layerwise compute; a multiplicative vector can be tiny but have insufficient capacity for the task.

First diagnose whether weights should change at all. Retrieval is usually safer for current or access-controlled facts; deterministic validators are better for hard output constraints; prompts can solve behavior already present. PEFT is appropriate only after these simpler controls are tested against the same outcome and guardrail criteria.

## 2. Bottleneck adapters

For hidden width `d` and bottleneck width `h`, a simple adapter block can be written as a residual transformation:

```text
FORMULA [APEFT-01]: y = x + W_up * f(W_down * x)
                   N_adapter = d*h + h*d = 2*d*h
WHERE: x,y [d]; W_down [h,d]; W_up [d,h]; f is a chosen nonlinearity;
       N_adapter is scalar trainable matrix elements.
CONSTRAINT: one independent adapter, no biases, no layer norm, no parameter
            sharing; placement (attention, FFN or both) is specified separately.
NUMERICAL EXAMPLE: d=4096, h=64; N_adapter=2*4096*64=524,288 parameters.
INTERPRETATION: count applies per inserted adapter. It is not a total-model count,
                a memory profile or proof that an adapter can represent the task.
```

If adapters are inserted in both attention and FFN positions in 32 layers under the same dimensions, the illustrative count is `32*2*524,288=33,554,432` parameters. This can be larger than a narrowly targeted LoRA configuration even though each adapter has a small bottleneck. Count actual placements and shared modules; do not infer them from a framework preset name.

Adapter placement affects behavior and runtime. A serial residual adapter introduces layerwise operations; parallel variants and placement before/after normalization change the effective computation. Mixing an adapter implementation trained for one architecture or normalization convention into another is not safe merely because its dimensions match.

## 3. Soft prompts and prefix states

A soft prompt of `p` learned embedding vectors at hidden width `d` contains `p*d` trainable scalars. It occupies input-context positions and can compete with user/retrieved context within the model's maximum length. A prompt of 64 vectors at width 4096 has `64*4096=262,144` parameters, excluding any prompt encoder.

Prefix tuning commonly attaches learned key/value states per layer. For one simplified attention layout with `p` virtual positions, `H_kv` key/value heads, head dimension `d_h`, two K/V tensors and `b` bytes/scalar:

```text
FORMULA [APEFT-02]: M_prefix = L * 2 * p * H_kv * d_h * b
WHERE: L is adapted layer count; 2 accounts for keys and values; p is virtual
       prefix positions; H_kv is K/V head count; d_h is head dimension; b is
       bytes per stored scalar. M_prefix is payload bytes.
CONSTRAINT: counts directly stored per-layer K/V prefix states only; excludes
            prompt encoder, projection weights, padding, allocator overhead,
            ordinary request KV cache and implementation-specific sharing.
NUMERICAL EXAMPLE: L=32, p=16, H_kv=8, d_h=128, b=2;
                   M_prefix=32*2*16*8*128*2=2,097,152 bytes=2 MiB.
INTERPRETATION: this is static prefix payload for one active adapter under the
                assumed representation; it is not complete serving memory.
```

Prefix methods can alter attention cost and usable context. If virtual tokens are represented as regular input positions, the effective sequence length grows from `T` to `T+p`; quadratic attention-score element count changes from `T^2` to `(T+p)^2`. For `T=2048` and `p=16`, the ratio is `(2064/2048)^2≈1.0157`, about 1.57% more score elements in this simplified full-attention comparison. Kernel implementation, cached prefix handling and causal masking determine actual latency; measure rather than infer speed.

## 4. Multiplicative scaling and low-rank variants

IA3-style methods learn selected vectors that scale activations or attention quantities. For a single `d`-wide activation vector `x`, a learned scale `l` yields `x' = l ⊙ x`, with `d` scalar parameters for that location. This is extremely compact, but it can only rescale the chosen coordinates; it cannot independently introduce every kind of cross-coordinate transformation. Target choices—keys, values, FFN intermediates or other tensors—define capacity and behavior.

LoRA-family variants preserve the central low-rank idea but may change scaling, initialization or decomposition. For example, a magnitude-direction decomposition can separate a vector/matrix magnitude parameter from a directional low-rank update. The implementation's exact tensors and merge semantics control parameter count and numerical behavior. Do not substitute a generic `r(d_in+d_out)` formula when extra magnitude, bias, normalization or module-specific tensors are trainable.

A rank update, a bottleneck adapter and an activation scale are not interchangeable merely because each has fewer parameters than full fine-tuning. Compare their geometry and locus:

| Method | Trainable locus | Main capacity boundary | Serving consideration |
|---|---|---|---|
| LoRA-style | Selected weight projections | Low-rank update subspace and target set | Can be composed/merged only with compatible base and method semantics |
| Bottleneck adapter | Layer residual path | Bottleneck width and placement | Adds layerwise path; adapter selection must be pinned per request/session |
| Soft prompt | Input embeddings | Fixed learned context and available input budget | Consumes context positions; template/order must be stable |
| Prefix tuning | Attention K/V states or derived states | Prefix length/layer representation | Adds prefix cache/state and may alter attention/caching path |
| IA3-style | Selected activation coordinates | Diagonal/multiplicative reweighting at targets | Very small artifact, but target tensor semantics must match exactly |

## 5. Multi-adapter routing and composition

Serving multiple adapters turns PEFT into a state-management problem. A correct request must choose an authorized base+adapter pair, pin it for the request/session, use a cache key that includes every behavior-changing version, and return a traceable artifact identity. The adapter name supplied by a caller is not authorization.

Minimum routing key fields:

- base checkpoint revision/hash and architecture/config;
- adapter artifact ID/version, target modules, method configuration and dtype;
- tokenizer/template/system-prompt version where they affect behavior;
- tenant/authorization scope and policy version;
- device/runtime/kernel configuration when it changes compatibility;
- session or request binding so an in-flight generation cannot hot-swap adapters.

Composition is a separate decision. Adding two LoRA deltas to a compatible base may be mathematically defined at a shared targeted matrix, but it does not prove behavioral compatibility. Prefixes and soft prompts can compete for context positions and may be order-sensitive. Adapters can conflict through nonlinear layers. Test each permitted composition against a composed baseline and disallow arbitrary user-selected combinations by default.

For a cache with capacity `C` adapter payloads and a requested working set `W`, a miss is unavoidable if `W>C` under steady use without other assumptions. This is a capacity fact, not a latency prediction. Measure cache hit rate, load time, eviction, memory headroom, concurrency and cross-tenant isolation under the actual request mix.

## 6. Training and evaluation controls

For every advanced PEFT experiment, record base/model/tokenizer/template versions, target modules, trainable parameter names/counts, method configuration, optimizer/precision, data manifest, split unit, seeds, checkpoint identity and evaluation protocol. Inspect `requires_grad` or the framework's trainable list and reconcile it with the intended count.

Compare against an appropriate baseline—often prompt/retrieval controls, frozen base and existing LoRA/SFT candidate—on the same held-out prompts and decoding configuration. Report task quality, safety/refusal boundaries, grounding, schema validity, language/subgroup slices, sequence-length behavior, cold/warm serving latency, peak memory, active adapter count and rollback behavior. Training loss or tiny artifact size is not an acceptance metric.

Use a bounded rank/width/prefix-length sweep only if data and compute budgets support it. Keep completed optimizer updates and evaluation data comparable. Changing rank, alpha, target modules, learning rate and dataset at once prevents attribution. For prompt/prefix methods, keep user context budget and truncation policy fixed in comparison; a quality difference may otherwise be caused by altered input capacity.

## 7. Failure modes

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Tiny adapter has no task effect | Wrong targets, insufficient capacity, no gradients, baseline already saturates metric | Inspect trainable names/gradients and a discriminating held-out slice | Fix configuration before increasing rank/width; test one factor at a time |
| Prompt/prefix harms long-context quality | Virtual tokens consume budget, template order mismatch, truncation or attention-mask defect | Compare usable user tokens, mask/position IDs and matched-total-length evaluation | Reduce/relocate prefix or choose another method; preserve target context budget |
| Adapter count is lower than expected | Shared parameters, target discovery mismatch, frozen extras or typo in module selector | Enumerate names/shapes and reconcile formula to state dict | Correct explicit target list; record actual count rather than framework label |
| Adapter count is higher than expected | Both attention/FFN sites, biases, norms, prompt encoder or duplicate target matches | Audit optimizer parameter groups and unique storage IDs | Remove unintended trainables; avoid double-counting tied parameters |
| Runtime regresses with many adapters | Cache churn, cold loads, synchronization, composition or batching fragmentation | Measure warm/cold latency, cache hit rate, active set and routing trace | Bound active bank/prewarm approved set or serve fixed merged artifact after validation |
| Wrong adapter response leaks across requests | Cache key omission, authorization bug, session race, unsafe hot swap | Cross-tenant negative tests and concurrent request/session-pinning tests | Block rollout; correct isolation and invalidate cache before retesting |
| Composed adapters degrade behavior | Nonlinear task interference, incompatible targets/scales, prompt order conflict | Compare each component and permitted composition on held-out task/regression sets | Permit only validated compositions; default to one adapter or separate routes |
| Merged artifact differs from live adapter | Scaling, dtype/quantization, base revision or target mismatch | Layer/output comparison under target kernel/dtype and task tests | Use supported merge pipeline or retain live composition; version merged artifact separately |
| Quantized base shifts PEFT behavior | Reconstruction error, outliers, compute dtype or backend mismatch | Paired full/quantized-base runs with same adapter/data/evaluation | Diagnose layer/slice error; choose supported precision or narrow deployment |
| Model improves average but harms a critical slice | Data imbalance, capacity tradeoff, metric masking or routing population mismatch | Slice evaluation and inspect worst-case errors with domain owners | Do not promote; revise data/method/scope and retain rollback |

## 8. Bounded method-selection exercise

**Scenario:** A platform serves three authorized internal task families from one compatible base model. Each task needs a different response style and has a 32k-token user-context requirement. The workload has a 20-adapter potential working set but permits only eight resident adapter payloads per GPU. No measurement is available.

Decision process:

1. Test whether system prompts, retrieval and deterministic output validation satisfy the three behavior contracts without adaptation.
2. If adaptation remains necessary, compare targeted LoRA, a bottleneck adapter, and a prefix/soft-prompt candidate using identical licensed demonstrations, context budget and held-out task/safety tests.
3. Reject a prefix configuration that reduces the available 32k user-context budget unless the requirement and measured quality are revised explicitly.
4. Design the adapter cache with base+adapter+tenant+policy version in the key; since `W=20>C=8`, provision a load/eviction policy and measure its effect instead of assuming all adapters remain warm.
5. Run cross-tenant negative tests, session-pinning and adapter-swap races; do not use arbitrary composition unless it passes separate evaluation.
6. Select the smallest operationally safe method that meets per-task quality, context, cost and rollback gates. No method is selected by this draft because no baseline, workload trace or evaluation is measured.

## 9. Interview and self-check questions

### Q1. How many matrix parameters does one width-4096, bottleneck-64 adapter contain?
**Answer:** `2*4096*64=524,288` excluding biases and other trainables.
**Reasoning:** It has a down and up projection.
**Follow-up:** What is the count for two placements in each of 32 layers?
**Answer:** `32*2*524,288=33,554,432`.

### Q2. Why is a soft prompt not free at inference?
**Answer:** It consumes learned context positions and may increase attention work.
**Reasoning:** The model processes virtual context in addition to user tokens.
**Follow-up:** What must be held fixed when comparing it with LoRA?
**Answer:** Usable user-context budget, template/masks and evaluation prompts.

### Q3. What does the 2 MiB prefix example include?
**Answer:** Only assumed per-layer K/V prefix payload for one active adapter.
**Reasoning:** The formula excludes ordinary KV cache, base, activations and allocator overhead.
**Follow-up:** What must be measured?
**Answer:** Full serving memory and latency under target context/concurrency.

### Q4. Why are two adapters with matching shapes not automatically composable?
**Answer:** Their bases, target modules, scales, task interactions and runtime semantics may differ.
**Reasoning:** Shape does not establish behavioral or version compatibility.
**Follow-up:** What is the safe default?
**Answer:** Permit only explicitly validated compositions.

### Q5. What must an adapter cache key include beyond adapter name?
**Answer:** Base/version, adapter/version/configuration, authorization scope and behavior-changing runtime/template identity.
**Reasoning:** Omitting one can load incompatible or unauthorized behavior.
**Follow-up:** How test it?
**Answer:** Cross-tenant negative and concurrent request/session-pinning tests.

### Q6. If 20 adapters may be active but cache capacity is eight, can all remain resident?
**Answer:** No, not under a steady working set of 20 without additional capacity.
**Reasoning:** `W>C` forces misses/evictions.
**Follow-up:** What does that not tell you?
**Answer:** Actual hit rate or latency; those require workload measurement.

### Q7. When is IA3-style scaling attractive?
**Answer:** When a small, target-specific multiplicative adjustment is sufficient and evaluated.
**Reasoning:** It uses few parameters but has constrained expressiveness.
**Follow-up:** What must be pinned?
**Answer:** Exact target tensor semantics and base architecture.

### Q8. Why can a bottleneck adapter have more parameters than a LoRA configuration?
**Answer:** It may be placed at more locations and has two `d×h` paths per placement.
**Reasoning:** Compare actual target counts and shapes, not method labels.
**Follow-up:** Does more parameters mean better quality?
**Answer:** No; validate held-out behavior and regressions.

### Q9. Does a merged adapter remove the need for versioning?
**Answer:** No.
**Reasoning:** The merge creates a new base-derived artifact with its own compatibility and rollback record.
**Follow-up:** What comparison is required?
**Answer:** Merged-versus-live output/task validation on target dtype/kernel.

### Q10. What promotes an advanced PEFT candidate?
**Answer:** Held-out task gain within safety/context/cost/operational gates, with proven routing and rollback.
**Reasoning:** Artifact size or train loss alone is insufficient.
**Follow-up:** What if a validator meets the contract without PEFT?
**Answer:** Keep the simpler validated control.
