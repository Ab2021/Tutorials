## Learning outcomes

Given an observed model failure and a proposed deployment, learners can distinguish broad capability gaps from response-behavior gaps; explain what post-training can and cannot change; compare prompting, retrieval, supervised fine-tuning and preference optimization at the decision level; define a bounded evaluation before choosing a method; and stop when evidence does not justify additional training.

## 1. Pretraining and the deployment contract

Pretraining learns statistical structure from a large corpus, commonly through a token-prediction objective. This can yield broad language, coding, factual and reasoning capabilities, but the training objective does not by itself specify a product's complete interaction contract: which tasks to answer, which sources to trust, how to format outputs, when to ask a question, or when to refuse.

Post-training is a family of additional procedures applied after a pretrained checkpoint to shape behavior for selected tasks or preferences. It may include supervised fine-tuning (SFT), preference/reward modeling, reinforcement learning from human feedback (RLHF), direct preference optimization and related methods. These are not interchangeable algorithms, nor guarantees of safety or truth. Each changes a model using a particular data and objective signal and needs evaluation against the intended use.

A deployment contract should state:

- intended users, tasks and supported input/output modes;
- the behavior required for correct, incomplete, ambiguous and out-of-scope requests;
- which facts must be grounded in supplied or retrieved sources;
- output schema, tone, latency and refusal/escalation expectations;
- unacceptable behaviors and the harm severity of each;
- evaluation population, comparator, acceptance threshold and monitoring plan.

Without this contract, “better aligned” or “more helpful” is not operationally testable.

## 2. Capability versus behavior

A **capability gap** means the model lacks knowledge, skill, context or reliable computation for the task. Examples include not knowing a private policy, failing a domain calculation, or lacking needed information in its context. A **behavior gap** means the model can perform a task under some conditions but does not reliably follow the desired interaction pattern: it may ignore format instructions, over-answer, fail to ask a needed clarification, or not use a provided source.

This distinction is diagnostic, not absolute. A behavior that appears inconsistent may arise from insufficient capability, prompt ambiguity, missing context, decoding, data mismatch or evaluation noise. Post-training can make a behavior more likely, but it cannot create a reliable factual source that the model has never received. Retrieval or an application-side check may be the safer fix for freshness, access control or exact provenance.

A useful diagnostic sequence:

1. Reproduce the failure with the exact prompt, model version, decoding settings and context.
2. Check whether required information is present and authorized in the prompt or retrieval result.
3. Test a clearly stated instruction and a minimal example of the desired response.
4. Compare model performance on a held-out set with the same information and output requirement.
5. Identify whether the gap is missing information, missing capability, inconsistent behavior, integration error or a measurement defect.
6. Choose an intervention that directly addresses the diagnosed cause; avoid using training to compensate for a deterministic software defect.

## 3. Intervention ladder

| Intervention | Best fit | Primary limitation / risk |
|---|---|---|
| Prompt or system-instruction change | A behavior is already available but instructions, examples or task framing are insufficient | Context competition, prompt sensitivity and fragile generalization |
| Retrieval or tool use | Needed facts are external, private, current or must be cited | Retrieval quality, access control, latency, tool errors and source grounding |
| Output validation or workflow control | A hard schema, deterministic policy or approval boundary can be enforced externally | May reject valid outputs; cannot fix all semantic errors |
| Supervised fine-tuning | Repeated input-to-target demonstrations teach a stable task/style/format pattern | Labeling cost, narrow coverage, overfitting, data leakage and regressions |
| Preference or reward-based optimization | Multiple plausible outputs require ranking against a defined preference | Reward/label misspecification, optimization instability, reward hacking and evaluation gaming |
| More/better pretraining or domain adaptation | Broad knowledge/representation or domain language is missing at scale | High compute/data cost, uncertain causal effect, contamination and broader regressions |

This is a diagnostic ladder, not a mandatory progression and not a claim that each option is always cheaper than the next. Choose based on the defect, data rights, privacy, deployment constraints, evaluation and lifecycle cost. Often a controlled product change is simpler and more auditable than modifying model weights.

## 4. What post-training changes

Training changes parameters so the model's conditional output distribution changes for some inputs. It can increase the likelihood of demonstrated or preferred responses, improve a measured format-following behavior, or teach a task pattern. The effect is statistical: there is no per-prompt guarantee unless an external system enforces it.

Post-training can also reduce performance elsewhere. A narrow dataset can overrepresent a style or demographic, encode annotation mistakes, teach spurious correlations, or shift behavior on unrelated tasks. A preference signal can favor verbosity, confidence or superficial judge satisfaction rather than correctness. A decline may be hidden if evaluation contains only the training domain or lacks difficult negative cases.

Use a causal discipline: compare a candidate with a baseline that differs only in the intervention under study, keep evaluation data independent, and report uncertainty and subgroup behavior. If multiple changes occur together—new data, prompt, retrieval, decoding and fine-tuning—the measured difference cannot be attributed to training alone.

## 5. Define success before selecting a method

For a bounded task, define a primary metric and guardrails. Specify the unit of analysis (request, conversation, answer, token or user), eligible population, time window, comparator, annotation protocol, threshold and uncertainty. Examples include exact schema validity per request, grounded-answer accuracy on a held-out set, refusal correctness on a harm taxonomy, or human preference under blinded pairwise review. One metric cannot establish general helpfulness, truthfulness and safety simultaneously.

A simple decision accounting model can expose hidden costs:

```text
FORMULA [PT-01]: C_total = C_build + C_train + C_eval + C_serve + C_monitor
WHERE: C terms [currency over a stated lifecycle horizon]; build includes data/engineering;
       train includes compute; evaluate includes annotation and test execution;
       serve and monitor use the same horizon and deployment volume.
CONSTRAINT: compare interventions at equal task scope, horizon, quality threshold,
            currency basis and included cost boundaries; this is accounting, not a
            prediction of quality or savings.
NUMERICAL EXAMPLE: ILLUSTRATIVE normalized cost units over 12 months:
                   prompt/retrieval=8+0+2+10+3=23;
                   SFT=12+15+5+10+4=46.
INTERPRETATION: SFT's additional recurring or fixed cost is justified only if it
                closes a material measured behavior gap that the baseline leaves open.
```

The example gives a 23-unit difference under constructed assumptions; it does not estimate an actual vendor, training job or service. Quality, risk and feasibility remain separate decision axes. Lower cost is not a win if the intervention misses a required safety or accuracy threshold.

## 6. Worked decision: reliable structured answers

**Scenario:** An internal assistant must return a structured disposition from a supplied policy excerpt. Some outputs omit a required field even when the excerpt and schema are present. The organization considers SFT. No model or deployment has been tested; numbers below are ILLUSTRATIVE.

The baseline evaluation has 200 independent requests. Suppose 170 meet all required fields and semantic constraints: exact task success is `170/200=85%`. The proposed acceptance threshold is at least 95% on this evaluation and at least 90% on each predeclared policy category; a separate adversarial set checks unsupported claims and refusal boundaries. These are decision gates, not measured results.

Before training:

1. Validate that the prompt actually includes the schema and the relevant excerpt on every case.
2. Separate parser, serialization and display errors from model omissions.
3. Add deterministic schema validation and a bounded repair/retry only if its failure and safety behavior are defined; record the baseline with and without this product control.
4. Inspect failures for recurring learnable patterns versus absent policy facts or ambiguous rules.
5. If a prompt/example intervention meets thresholds, stop: SFT is not justified by this failure set.
6. If omissions persist despite clear context and appropriate controls, prepare licensed demonstrations with leakage checks, an independent held-out split and a training/deployment rollback plan.

After any SFT experiment, compare on the same frozen test protocol and add a broader regression suite. Report success rate with a confidence interval, subgroup/category results, invalid-format rate, unsupported-claim/refusal guardrails, inference latency, memory, training/data cost, and results across repeated seeds if stochastic variation matters. Promote only if predeclared gates pass and the intervention improves the actual product objective. One hundred percent on a small test set would still not prove universal compliance.

## 7. Data signal and alignment boundaries

Post-training data expresses what the model is asked to imitate or prefer. The data is therefore part of the specification. Review coverage, label definitions, annotator instructions, disagreement and appeal handling, provenance, privacy, representativeness, allowed use and contamination controls. Keep source prompts and desired outputs aligned to a known policy version. Examples with hidden assumptions teach unstable behavior.

Preference labels are judgments under a rubric and context, not objective ground truth. Human raters can disagree or miss domain errors; AI-generated preferences can reproduce model biases or self-reinforce stylistic artifacts. Reward optimization can exploit weaknesses in its reward signal. Use independent task evaluation and targeted challenge sets rather than using training reward as the sole quality metric.

Safety is a system property spanning data, model, tools, access control, user interface, escalation, monitoring and incident response. Fine-tuning can improve selected responses but cannot replace authorization enforcement, sandboxing, deterministic policy checks or human review for high-impact actions.

## 8. Failure modes and diagnosis

| Symptom | Competing explanations | Discriminating check | Bounded response |
|---|---|---|---|
| Training improves training examples only | Overfit, duplicates across splits, narrow task variation | Exact/near-duplicate audit; held-out source/time/domain evaluation | Repair split and expand valid coverage; rerun independent evaluation |
| Model sounds more confident but is not more correct | Preference rubric rewards style; factual evidence absent | Blinded correctness and calibration review with source-grounded labels | Revise rubric/data or add retrieval/verification; do not treat fluency as accuracy |
| SFT fixes format but worsens refusal behavior | Conflicting examples or objective tradeoff | Paired regression slices for allowed, disallowed and ambiguous prompts | Correct data policy and reevaluate both behaviors before promotion |
| Reward rises but user/task quality does not | Reward proxy mismatch, judge leakage or reward hacking | Compare reward to independent human/task outcomes; inspect failure samples | Stop reward-only tuning; fix objective or use direct task gates |
| No visible change after post-training | Wrong checkpoint/adapter, low signal, evaluation insensitive, serving mismatch | Trace loaded artifact/version; compare logits/behavior on discriminative cases | Fix artifact routing or redesign test; avoid scaling training blindly |
| Apparent gain vanishes in production | Prompt, retrieval, decoding, model version or traffic changed | Reconstruct exact request path and stratify by version/traffic | Restore controlled comparison; isolate the changed component |
| Model learns stale policy | Training examples conflict with current policy or retrieval | Versioned policy probes and source citation checks | Route current rules through retrieval/system controls; refresh or remove stale examples |
| Sensitive data leaks in outputs | Unauthorized training data, memorization, retrieval ACL defect | Provenance audit; access-control tests; privacy/security review | Contain exposure and remediate source or authorization path; do not rely on refusal examples alone |

## 9. Promotion gate and rollback

A candidate is not ready merely because training finished or its loss decreased. Require:

- artifact identity, data lineage, training configuration and reproducible evaluation record;
- task-specific held-out improvement meeting predeclared thresholds;
- no unacceptable regression in safety, privacy, subgroup or general-capability checks;
- serving compatibility, latency/resource limits, observability and safe fallback;
- explicit rollback trigger, owner and previous known-good artifact;
- staged rollout and monitoring that can attribute changes to the candidate version.

If results are mixed, narrow the supported task scope or retain the baseline. Do not average away a severe safety regression with gains on routine examples. If test leakage, policy ambiguity or invalid labels make the outcome uninterpretable, repair evaluation/data before promotion.

## 10. Interview and self-check questions

### Q1. Why can a capable pretrained model still fail a product task?
**Answer:** Its pretraining objective does not encode every product instruction, source, format or escalation rule.
**Reasoning:** Broad capability and reliable behavior under a specific contract are distinct.
**Follow-up:** Name a non-training intervention.
**Answer:** Retrieval, prompt changes, output validation or workflow control.

### Q2. When is a gap more likely a capability gap than a behavior gap?
**Answer:** Required information or task competence is absent even under clear instructions and adequate context.
**Reasoning:** Repeating or strengthening the instruction cannot supply missing evidence.
**Follow-up:** What can address missing current/private facts?
**Answer:** Authorized retrieval or a tool, with access and source validation.

### Q3. When can SFT be justified?
**Answer:** A repeated behavior pattern is learnable from valid demonstrations and simpler alternatives fail the predefined evaluation.
**Reasoning:** SFT changes the model's response distribution but has costs and regression risks.
**Follow-up:** What must remain independent?
**Answer:** Held-out evaluation data and promotion gates.

### Q4. Why can preference optimization produce a worse assistant despite a higher reward?
**Answer:** The reward may proxy style or judge preference rather than actual task correctness or safety.
**Reasoning:** Optimization follows the specified signal, including its defects.
**Follow-up:** What independent evidence is needed?
**Answer:** Task outcomes, blinded review, safety slices and regression checks.

### Q5. In the illustrative lifecycle calculation, which option has lower total cost?
**Answer:** Prompt/retrieval totals 23 units; SFT totals 46.
**Reasoning:** Sum the five stated cost categories for the same 12-month horizon.
**Follow-up:** Does that alone choose the intervention?
**Answer:** No; required quality, risk, feasibility and uncertainty are separate gates.

### Q6. Why are model weights not an authorization boundary?
**Answer:** Statistical behavior does not reliably enforce identity- and resource-specific access rules.
**Reasoning:** Authorization should be checked by deterministic application controls.
**Follow-up:** Can refusal tuning replace tool access checks?
**Answer:** No.

### Q7. Why does a random train/test split sometimes overstate generalization?
**Answer:** Near duplicates, shared sources or temporal leakage can place related examples on both sides.
**Reasoning:** Evaluation then tests memorized overlap, not the intended deployment shift.
**Follow-up:** What split might fit policy data?
**Answer:** Version-, source-, time- or entity-separated evaluation based on expected use.

### Q8. What is a valid response when prompt/retrieval meets the threshold?
**Answer:** Stop without fine-tuning.
**Reasoning:** The simplest validated intervention meets the stated need.
**Follow-up:** What should be monitored?
**Answer:** The same outcome and guardrail metrics under production traffic, with change detection.

### Q9. How should a candidate be handled if it improves average accuracy but fails one severe safety slice?
**Answer:** Do not promote under the original contract; investigate, narrow scope or repair the regression.
**Reasoning:** An average cannot erase a critical failure.
**Follow-up:** What if the slice was post hoc?
**Answer:** Treat it as a signal requiring predefined follow-up evaluation, not as a certified result.

### Q10. What must a promotion record contain?
**Answer:** Candidate identity, data/config lineage, held-out results, risk checks, serving plan, monitoring and rollback owner/trigger.
**Reasoning:** A result without provenance or recovery path is not an operational decision.
**Follow-up:** What invalidates comparison?
**Answer:** Uncontrolled changes in prompts, retrieval, decoding, model artifact or evaluation population.

## 11. Quick reference

| Diagnostic question | Action |
|---|---|
| Is information missing? | Supply authorized context or retrieval; do not expect parameter updates to provide freshness |
| Is behavior inconsistent despite adequate context? | Test prompt/workflow controls, then evaluate whether demonstrations can teach the pattern |
| Is fine-tuning warranted? | Compare against simpler baselines on a frozen, representative evaluation set |
| Is a metric meaningful? | Define unit, population, comparator, window, rubric, threshold and uncertainty |
| Is alignment sufficient for safety? | No; retain access controls, validation, escalation, monitoring and rollback |
| Is the candidate promotable? | Only after quality and guardrails pass with traceable artifacts and operational readiness |
