## Learning outcomes

Learners can classify candidate data sources by task and provenance; estimate usable token volume after explicit exclusions; distinguish data volume from data quality and legal permission; plan mixed-domain sampling; preserve a held-out test boundary; identify contamination and duplication risks; and decide whether more data is likely to address a measured model gap.

## 1. Why data scope precedes model scale

A training corpus defines the examples and distributions from which the training objective receives signal. Its size does not determine whether it is suitable. A million duplicated, stale, inaccessible, or mismatched examples may provide less useful information than a smaller, better-governed dataset. Conversely, a narrow high-quality set can still fail to cover rare cases or future use.

Before estimating token volume, specify the task, learner-visible inputs and outputs, target population, expected deployment distribution, accepted sources, and prohibited uses. A data source must be evaluated for permission and provenance before it is counted as available. “Found online,” “public,” “internal,” or “user-provided” is not itself a sufficient training-use determination.

Separate these questions:

1. **Can the organization access the data?** Technical reachability and credentials.
2. **May the organization use it for this purpose?** Contract, license, consent, policy and applicable review.
3. **Does it represent the target?** Population, time, language, domain, and exclusions.
4. **Can it be transformed safely?** Privacy, security, label integrity, retention and deletion traceability.
5. **Will it improve the target objective?** Held-out evidence, not corpus size alone.

This lesson does not provide legal advice. The responsible data owner and qualified reviewers determine permissions for the actual organization, source, jurisdiction, and use.

## 2. Source classes and their risks

| Source class | Potential value | Questions before inclusion |
|---|---|---|
| Licensed or curated text corpus | Broad language/domain coverage | What uses, redistribution, retention and derivative artifacts does the license permit? |
| Internal policy or product documents | Current organization-specific facts | Which versions are authoritative; may content train weights or should it be retrieved at runtime? |
| Human demonstrations | Explicit desired task outputs | Who authored them, under what instructions, with what rights, quality checks and population coverage? |
| User interactions or support logs | Real request distribution and edge cases | Consent, privacy, sensitive data, feedback selection, user expectations and retention constraints? |
| Synthetic model-generated data | Scalable structured examples | Teacher provenance, errors, diversity, filtering, circularity and whether synthetic examples match deployment? |
| Code repositories | Syntax, APIs and programming patterns | Repository license, secrets, dependencies, test data, version/time leakage and provenance? |
| Public benchmark or evaluation items | Comparability or task-specific measurement | Were they in training, tuning, prompt examples, or synthetic derivations? Can they remain held out? |

Source classes are not mutually exclusive. A single corpus may include multiple origins and restrictions. Preserve source-level provenance through merging so that a later correction, deletion, license update, or contamination finding can be traced to affected shards and checkpoints.

## 3. Provenance and governance record

A source register records the evidence needed to decide whether a corpus can enter a pipeline. At minimum, capture source identity, owner/contact, acquisition method and date, exact version or snapshot, permitted purpose, restrictions, sensitive-data review, transformation history, approved population, retention rule, and the reviewer who made the decision.

For derived artifacts, maintain traceability from a source record through downloaded objects, normalized text, deduplicated documents, chunks, tokenized shards, training runs, checkpoints, adapters, and evaluation sets. The chain should support both reproducibility and an authorized response to correction or removal requests.

A cryptographic hash can identify bytes but cannot establish ownership, permission, quality, or anonymity. A content address helps detect accidental changes; pair it with a human-readable provenance and governance manifest.

### Source inclusion gate

A source is included only when its use is approved for the specific purpose and its known restrictions can be carried through the intended pipeline. Unknown permission is not approval. If metadata is missing, quarantine the data while the source owner resolves the uncertainty; do not silently assign a broad default license.

Minimize data collection. Exclude sensitive fields not needed for the task. If text must be redacted, test whether the transformation preserves task utility and removes sensitive information to the required standard; simple substitution may leave identifying context. Hashing low-entropy identifiers is not reliable anonymization.

## 4. Scale metrics: documents, tokens, and useful exposure

“Corpus size” can mean source files, documents, bytes, examples, unique documents, tokens, training sequences, loss-bearing tokens, or optimizer updates. These units are not interchangeable.

For language-model training, token count depends on tokenizer and inclusion policy. A document with 1,000 words is not necessarily 1,000 tokens. Count with the intended tokenizer after normalization, filtering, deduplication and formatting. Record whether counts include special tokens, separators, padding, prompt tokens, masked targets, and repeated epochs.

Distinguish:

- **Raw bytes:** storage before parsing and filtering.
- **Raw documents:** source-level records before deduplication.
- **Eligible documents:** records authorized and within scope.
- **Unique/retained documents:** after declared deduplication and quality controls.
- **Token positions:** tokenized inputs including any padding/markers under a defined convention.
- **Loss-bearing tokens:** positions that contribute to the training objective.
- **Training exposure:** examples/tokens presented across epochs or replay, potentially including repeated tokens.
- **Unique information:** not directly measured by token count; duplicates, common boilerplate and low-quality text reduce novelty.

A statement such as “trained on 10 billion tokens” should specify tokenizer, counting convention, corpus snapshot, deduplication, epochs, and whether the value means unique retained tokens or total processed tokens.

## 5. Worked usable-volume estimate

Illustrative source plan: begin with 100,000 documents averaging 400 tokens/document after tokenization. Suppose 20% are excluded because a reviewed purpose restriction does not allow this training use, then 10% of the remaining set is removed by a specified deduplication procedure.

Derivation: multiply initial documents by the allowed fraction; then apply the second removal fraction to the remainder. Multiply retained documents by average tokens/document only if the average is measured over retained documents or explicitly assumed unchanged.

```text
FORMULA [DATA-01]: D_retained = D_0 * (1-r_rights) * (1-r_dedup)
                  N_tokens ≈ D_retained * t_avg
WHERE: D_0 = raw documents [documents]; r_rights, r_dedup = removal fractions [0..1];
       t_avg = mean token count of retained documents [tokens/document].
CONSTRAINT: sequential removal fractions apply to the current remainder; the 400-token mean is assumed stable after exclusion/deduplication.
NUMERICAL EXAMPLE: D_0=100,000; r_rights=0.20; r_dedup=0.10; t_avg=400.
                   D_retained=100,000*0.80*0.90=72,000 documents.
                   N_tokens≈72,000*400=28,800,000 tokens.
INTERPRETATION: the illustrative retained volume is 28.8 million tokens before split assignment, formatting losses, and target masking.
```

Independent check: after rights exclusions, 80,000 documents remain; ten percent of those is 8,000, leaving 72,000. `72,000*400=28,800,000` tokens.

If one incorrectly subtracts 20% and 10% from the original total additively, one obtains 70,000 documents. That is wrong for a sequential 10%-of-remainder removal. If the 400-token average was measured before filtering, the token total is only an estimate: excluded documents may be longer or shorter. Recompute actual token counts on the retained data.

Suppose 10% of retained documents are reserved for validation and 10% for test, with disjoint assignments and document-level grouping. Remaining training volume is `72,000*0.80=57,600` documents, or approximately `23,040,000` tokens at the same assumed mean. The splits should be assigned according to entity/time/source boundaries before splitting derived chunks, and a test set must not be used for tuning.

## 6. From retained tokens to packed sequences

At `L=2,048` tokens per full sequence, the retained corpus has `floor(28,800,000/2,048)=14,062` complete sequences with 1,024 tokens left over, if tokens can be concatenated freely with no boundary or isolation cost. After the illustrative split in section 5, the 23,040,000-token training portion gives `floor(23,040,000/2,048)=11,250` full sequences. These are idealized packing counts, not counts of valid independent training examples.

Real packing may insert document delimiters, preserve per-document boundaries, mask cross-document attention, drop short remainders, or pad sequences. Each choice changes useful token positions and context. A packed sequence can contain several documents, but the model must not accidentally attend across boundaries when the task requires isolation. Count loss-bearing tokens after formatting, not only raw tokenized text.

If each document is kept separate and padded to 2,048, padding overhead may be large. The actual cost depends on document length distribution. For example, 72,000 short documents can generate many padded positions even with a modest retained-token total. Report both non-padding and allocated sequence positions.

## 7. Domain mixtures and sampling

A training mixture assigns sampling probabilities to source groups. If source `i` has token fraction `q_i` in the available corpus and is sampled with probability `p_i`, then `p_i` controls exposure; it need not equal `q_i`. Oversampling can increase domain exposure but also repeat examples and shift the objective toward that source.

For `K` domains, probabilities satisfy `p_i ≥ 0` and `sum_i p_i = 1`. If an illustrative mixture allocates 70% of sampling to general text and 30% to domain text, then a processed budget of 10 million tokens yields 7 million and 3 million sampled token positions, respectively, before masking and repeated-example accounting. This does not imply the domain source contains three million unique tokens.

A token-weighted mixture and an example-weighted mixture can differ substantially when example lengths vary. State the sampling unit. If each document is sampled uniformly, long documents can contribute more tokens per draw; token-level sampling changes the effective probability of short and long documents.

Replay can preserve general capability during domain adaptation, but the right proportion is an empirical question. Too little replay may permit regressions; too much can dilute the target domain signal. Compare candidate ratios with held-out domain and general evaluations, and report data composition and compute budget.

## 8. Data quality, duplication, and contamination

Exact duplicates waste compute and can overweight repeated content. Near duplicates may arise from mirrors, revisions, quoted passages, template boilerplate, or syndicated content. Deduplication methods trade recall against false merges; removing near duplicates can also discard legitimate repeated legal clauses, code patterns, or versions that represent meaningful temporal change.

Contamination occurs when evaluation items or close variants enter training, tuning, prompt demonstrations, synthetic generation, or annotator reference material in a way that inflates evaluation. Public availability does not guarantee absence from a pretraining corpus. Keep evaluation provenance and access controls, search for overlap where technically feasible, and describe residual uncertainty.

Data quality dimensions include correctness, source authority, recency, completeness, domain relevance, linguistic diversity, label consistency, and safety. A source may be high quality for one task and unsuitable for another. Human review procedures need instructions, reviewer training, disagreement measurement, adjudication, and audit sampling.

Filtering rules must be versioned and evaluated for subgroup impact. A language detector can remove short, code-switched or low-resource language content incorrectly. Quality scores trained on one population can encode selection bias. Maintain a retained/excluded sample and inspect false positives/negatives.

## 9. Data value and marginal utility

The marginal value of another token depends on what the current corpus lacks. Additional copies of common examples may have low information value; verified rare cases can be useful but may be too sparse to estimate performance reliably. A data acquisition decision should compare the cost and risk of new data with alternative interventions such as retrieval, better labels, clearer instructions, or a smaller targeted evaluation.

Useful diagnostics include learning curves at fixed architecture and objective; performance by domain/language/time slice; deduplication sensitivity; data ablations; and quality-vs-cost curves. When training budgets differ, do not attribute gains solely to data quality if the candidate also receives more tokens or optimizer updates.

A data scaling experiment should preserve an untouched test set, use a fixed tokenizer and model recipe where possible, sample subsets reproducibly, and quantify uncertainty from seeds and examples. A curve fitted over a small range should not be extrapolated without new measurements. The total token count is a planning feature, not a proof of sufficient coverage.

## 10. Failure diagnostics

| Symptom | Competing causes | Discriminating check | Bounded response |
|---|---|---|---|
| Usable corpus volume far below raw count | Rights exclusions; parse failures; dedup removal; tokenizer length differences | Stage-by-stage counts by source and reason | Resolve data rights or acquisition gaps; do not relax review silently |
| Domain behavior fails despite large corpus | Mismatch in task, stale sources, low-quality labels, dilution by mixture | Evaluate slices and source-specific ablations | Target the identified gap; test retrieval or SFT as alternatives |
| Validation score implausibly high | Duplicate overlap, benchmark contamination, prompt leakage | Near-duplicate audit and sealed fresh evaluation | Withdraw claim and replace contaminated test evidence |
| General quality falls after domain update | Mixture imbalance, repeated domain data, optimization or tokenizer shift | Matched replay-ratio runs and general regression suite | Adjust mixture or stop candidate; preserve baseline checkpoint |
| Rare language disappears after filtering | Detector false positives, normalization damage, length cutoff | Compare retained/excluded language samples and counts | Correct rule and regenerate splits; re-review fairness and quality |
| Data deletion cannot be traced | Provenance lost during merge/shard/augmentation | Follow source IDs through transforms to run/checkpoint | Block affected reuse until governed remediation is defined |

A useful diagnostic reports raw, eligible, retained, unique, tokenized, split, and loss-bearing counts separately. If two counts do not reconcile, identify the transformation responsible rather than hiding the difference in one “clean tokens” metric.

## 11. Interview and self-check questions

### Q1. Why is “the data is public” not enough to train?
**Answer:** Accessibility does not establish permission for the intended training use, privacy suitability, provenance or restriction handling.
**Reasoning:** Evaluate the specific source, purpose and organizational policy with qualified review.
**Follow-up:** What if permission is unknown?
**Answer:** Quarantine it until resolved; do not assume approval.

### Q2. Compute retained documents after sequential removals of 20% and then 10% of the remainder from 100,000.
**Answer:** `100,000*0.8*0.9=72,000`.
**Reasoning:** The second fraction applies to the remainder.
**Follow-up:** Why is additive subtraction wrong?
**Answer:** It incorrectly applies both percentages to the original denominator.

### Q3. At 400 tokens/document, what is the estimated retained token count?
**Answer:** `72,000*400=28.8 million` tokens.
**Reasoning:** Assumes average length remains 400 after exclusions and deduplication.
**Follow-up:** How do you reduce uncertainty?
**Answer:** Tokenize and count the retained corpus directly using the intended tokenizer and inclusion policy.

### Q4. What is the difference between token positions and loss-bearing tokens?
**Answer:** Positions may include prompts, padding, delimiters or masked labels; loss-bearing tokens contribute to the objective.
**Reasoning:** Formatting and masks determine the denominator and gradient signal.
**Follow-up:** What should a run record?
**Answer:** Both counts and the exact mask/packing convention.

### Q5. Why assign parent documents to splits before chunking?
**Answer:** Derived chunks from the same source can otherwise appear in both training and test, leaking content.
**Reasoning:** The dependency unit is the source document, not the chunk.
**Follow-up:** What if users are the unit of generalization?
**Answer:** Group by user or other relevant entity, subject to privacy and evaluation design.

### Q6. What is a token-weighted mixture?
**Answer:** A sampling policy that controls expected exposure by token share rather than only the number of examples.
**Reasoning:** Documents vary in length, so equal example counts do not imply equal token exposure.
**Follow-up:** Why oversample a small domain?
**Answer:** To increase exposure, while recognizing that repetition may increase and general behavior may shift.

### Q7. Does deduplication always improve quality?
**Answer:** No. It can reduce overweighting and contamination but may incorrectly merge meaningful variants or remove useful repetition.
**Reasoning:** Evaluate precision/recall on representative duplicate labels and downstream outcomes.
**Follow-up:** What should be retained?
**Answer:** Audit samples, thresholds, source identifiers and transformation versions.

### Q8. How can a large corpus still have low marginal value?
**Answer:** It may contain redundant, stale, low-quality or task-mismatched content.
**Reasoning:** Raw volume is not a direct measure of useful information.
**Follow-up:** What evidence guides acquisition?
**Answer:** Learning curves, slice gaps, data ablations, quality review and cost/risk comparisons.

### Q9. Why distinguish a held-out validation set from a test set?
**Answer:** Validation guides iterative choices; the test estimates final performance after those choices are fixed.
**Reasoning:** Repeated test inspection can overfit decisions to test examples.
**Follow-up:** What if a test set is contaminated?
**Answer:** It no longer supports the intended estimate; govern a new evaluation set and document the limitation.

### Q10. What should be counted before declaring a token budget?
**Answer:** Tokenizer, corpus snapshot, unique/retained scope, epoch/replay count, packing, special tokens, padding and loss-mask convention.
**Reasoning:** “Tokens processed” can mean several different quantities.
**Follow-up:** Does a token count measure unique information?
**Answer:** No; it can count repeated or low-value content.

## 12. Quick reference card

| Decision element | Rule |
|---|---|
| Source permission | Confirm the specific source and purpose before inclusion; unknown is not approved. |
| Provenance | Keep immutable source versions and links through transforms, shards, runs and checkpoints. |
| Volume | Count with the actual tokenizer after approved filtering and deduplication. |
| Denominator | Distinguish documents, token positions, loss-bearing tokens, unique tokens and processed exposure. |
| Sequential removals | Apply each removal rate to its stated current denominator. |
| Splits | Group by source/entity/time dependency before chunking; protect final test from tuning. |
| Mixtures | State sampling unit and token exposure; assess replay and general regressions. |
| Deduplication | Audit false merges and missed duplicates; thresholds are task/source dependent. |
| Data value | More volume is not a guarantee; measure marginal utility against alternatives. |
| Evidence | This lesson's values are illustrative; no data source or run was inspected. |
