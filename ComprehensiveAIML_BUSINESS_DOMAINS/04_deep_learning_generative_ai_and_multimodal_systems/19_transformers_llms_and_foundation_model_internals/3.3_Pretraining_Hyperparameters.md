## Learning outcomes

Learners can define optimizer and schedule parameters with unambiguous units; distinguish microbatch from global batch and token exposure; reason about learning-rate warmup/decay, weight decay, gradient clipping and precision; plan controlled tuning under a fixed budget; and diagnose unstable or undertrained runs using logs and checkpoint comparisons.

## 1. Hyperparameters are a coupled training configuration

A hyperparameter is a training choice set outside the learned model weights, such as learning rate, optimizer coefficients, batch size, weight decay, gradient clipping threshold, schedule, warmup duration, sequence length, precision, or data mixture. Hyperparameters interact. A learning rate that is stable at one batch size, token distribution, optimizer, or architecture may not behave the same after another changes.

Treat the full configuration as a versioned contract. Record the model and tokenizer, data release and sampler, objective and masks, optimizer, schedule, batch/token counts, precision, parallelism, seed, software stack, hardware and checkpoint selection rule. An isolated value such as “learning rate 3e-4” is not reproducible without its units and context.

Separate **hyperparameters** from **observed state**. Learning rate and weight decay are settings; optimizer moments, gradient norms, consumed tokens, loss, throughput, and current schedule step are runtime state. Save enough state to resume consistently.

## 2. AdamW-style optimization

An adaptive optimizer maintains running estimates of gradients and squared gradients; a decoupled weight-decay term modifies parameters separately from the adaptive gradient update in AdamW-style methods. Exact update details depend on implementation choices such as epsilon placement, bias correction, fused kernels, parameter groups, and whether decay is applied to embeddings, normalization parameters, or biases.

Typical configuration fields include:

- peak learning rate and warmup/decay schedule;
- first and second moment coefficients (often denoted beta values);
- numerical stabilizer epsilon;
- decoupled weight decay and parameter exclusions;
- gradient clipping norm and clipping scope;
- optimizer-state precision and checkpointing policy.

These values are not universal. Transfer from a paper or model card requires matching parameterization, batch, objective, token budget, initialization, precision, and implementation as closely as practical. Inspect the actual library defaults; defaults can change by version.

## 3. Learning rate and schedule

The learning rate controls update scale. Large values can destabilize training; very small values can make progress slow or leave a fixed compute budget underused. Warmup gradually increases the learning rate at the start to reduce early instability in some setups. Decay lowers it later to refine weights and limit late-stage disruption. Neither warmup nor decay guarantees stability.

A schedule must declare its independent variable: optimizer steps, tokens processed, epochs, wall time, or another measure. A token-based schedule is robust to changed batch size only if token counting and update behavior are handled consistently. A step-based schedule can consume a different token budget when batch/sequence length changes.

Illustrative linear warmup from zero to peak rate `η_max` over `S_w` steps:

```text
η(s) = η_max * s / S_w                 for 0 <= s < S_w
```

A cosine decay from `η_max` to `η_min` over `S_d` steps after warmup can be written:

```text
η(s) = η_min + 0.5*(η_max-η_min)*(1 + cos(pi*u))
where u = clamp((s-S_w)/S_d, 0, 1)
```

The schedule's boundary convention matters: exact value at warmup end, decay start, final step and resumed step should be tested. Some schedules include a nonzero minimum; some use a different shape or token-based horizon.

## 4. Global batch, microbatch, and token budget

**Microbatch** is the examples or sequences processed in one forward/backward microstep on a device. **Gradient accumulation** collects multiple microstep gradients before an optimizer update. **Global batch** aggregates examples over data-parallel replicas and accumulation. The actual number of token positions and loss-bearing targets can differ because of sequence length, padding, masking, packing and uneven batches.

For fixed sequence length `L`, a simplified dense full-batch token-position count is:

```text
T_positions/update = microbatch_sequences * data_parallel_replicas
                     * accumulation_steps * L
```

This excludes padding differences or special losses unless defined otherwise. Use actual non-padding and loss-bearing counts for token accounting.

Illustrative example: 4 sequences/device, 8 data-parallel replicas, 4 accumulation steps, and 2,048 positions/sequence gives `4*8*4*2,048=262,144` token positions per optimizer update. If only 90% of positions carry loss, the expected loss-bearing count is approximately 235,930 positions (rounding to an integer); measure the actual mask count rather than relying on this average.

Gradient accumulation can approximate a larger batch under some conditions, but it does not necessarily reproduce it exactly. Dropout/randomness, batch-dependent operations, optimizer update timing, gradient reduction order, clipping, and loss normalization can differ. Confirm that gradients are normalized over the intended target count.

## 5. Weight decay, clipping, and initialization

Weight decay discourages some forms of parameter growth, but its effect depends on implementation and parameter groups. Decaying normalization parameters or biases may be undesirable in some model recipes; do not assume a universal exclusion list. Record exactly which parameters are decayed.

Gradient clipping caps a norm under a specified scope (per parameter, per device, or global). It can reduce the impact of extreme updates but can also hide a persistent instability by clipping every step. Log pre-clip norm, post-clip behavior and fraction of clipped steps. Frequent clipping should trigger diagnosis of learning rate, data, loss scale, optimizer, or numerical issues.

Initialization and model parameterization affect update scales and stability. A hyperparameter recipe tied to one architecture may not transfer to a changed normalization order, width, residual scaling, embedding initialization, or output head. Record any architecture-specific scaling rules.

## 6. Precision and numerical stability

Training may use reduced-precision weights/activations with higher-precision accumulation or optimizer state. Exact choices depend on hardware, kernels, model scale, and numerical tolerance. Loss scaling can help some low-precision gradient representations but can overflow or underflow if configured poorly.

Monitor non-finite loss/gradients, overflow/underflow counters, gradient norms, parameter norms, optimizer state, and skipped updates. A run with silent skipped updates may consume tokens without making the expected optimization progress. Compare a small reference calculation or higher-precision baseline when investigating numerical anomalies.

Do not conflate a stable loss curve with numerical correctness: incorrect masks or label shifts can produce finite but invalid training. Validate both numerical behavior and data/objective invariants.

## 7. Controlled tuning plan

Hyperparameter tuning should answer a bounded question and preserve an evaluation boundary. A practical sequence:

1. Fix the data release, tokenizer, model definition, objective and evaluation protocol.
2. Validate a tiny batch and loss/gradient path before any sweep.
3. Define resource budget and candidate parameter ranges using prior evidence and feasibility.
4. Change a small set of parameters at a time; record interactions where a factorial or structured design is justified.
5. Use comparable token budgets and checkpoint-selection rules for candidates.
6. Track loss and stability at matched token/update points, plus task-relevant held-out metrics.
7. Stop unsafe or clearly infeasible runs under predefined criteria; record failures.
8. Repeat promising settings where seed variance matters.
9. Select using validation criteria, then evaluate once on protected test data.
10. Re-run the selected configuration with production data/system assumptions before claiming operational feasibility.

A sweep that spends different compute per candidate can confound quality with training budget. Early stopping can be useful, but compare at matched progress and account for learning-curve shape.

## 8. Checkpoints, resume, and schedule state

A checkpoint for faithful resume may need model weights, optimizer state, scheduler state, gradient scaler state, random-number-generator states, data sampler/shuffle position, consumed-token counters, and distributed state. Saving model weights alone supports inference but not necessarily exact continuation.

A resumed run must not accidentally restart warmup, repeat data unexpectedly, skip tokens, or change learning rate because the scheduler step was not restored. Compare a continuous run against an interrupted/resumed control on a small deterministic setup where possible. At scale, record divergence boundaries and resume semantics.

Checkpoint selection should follow a predefined validation and safety process. The final step is not automatically the best checkpoint; choosing the best validation checkpoint consumes validation information and should be included in the evaluation protocol.

## 9. Worked schedule example

Constructed configuration: 20,000 optimizer updates, linear warmup over 400 updates, peak learning rate `3e-4`, cosine decay to 10% of peak over the remaining 19,600 updates.

At update `s=200`, linear warmup gives `3e-4*(200/400)=1.5e-4`. At update 400, the schedule reaches `3e-4`. At the decay midpoint (update `400+9,800=10,200`), cosine factor is `(1+cos(pi*0.5))/2=0.5`; the learning rate is midpoint between peak and minimum: `(3e-4+3e-5)/2=1.65e-4`. At the final decay endpoint, rate is `3e-5` under this formula.

These values illustrate arithmetic only. The schedule is not a default for a real model. Warmup fraction, peak rate, decay shape, token horizon, and minimum rate require a validated recipe or controlled experiment.

## 10. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Loss spikes at start | Learning rate too high; warmup reset; malformed batch; precision overflow | Inspect step/token schedule, batch IDs/labels and gradient/overflow logs | Fix identified issue; restart from valid checkpoint under recorded policy |
| Training progresses very slowly | Learning rate too low; schedule decays too early; underutilized system; too few targets | Plot loss against updates and tokens; profile throughput and mask counts | Correct budget/schedule or system bottleneck with controlled change |
| Gradient norm spikes/clips every step | Data anomalies; unstable rate; loss normalization; bad precision | Inspect pre-clip norms, batch examples and clipping scope | Diagnose source before raising clipping threshold or masking symptoms |
| Resume diverges | Optimizer/scheduler/RNG/sampler state missing; duplicate/skip data | Compare step, tokens, LR, sampler IDs and optimizer state across resume | Restore full state or explicitly treat as a new run and document it |
| Candidate comparison favors larger batch | Different token budget, update count or loss denominator | Compare matched processed/loss-bearing tokens and compute | Re-run under matched budget; report tradeoff instead of single score |
| Non-finite values appear sporadically | Precision overflow; bad data; unstable optimizer state | Correlate batch/source, scale events, optimizer tensors and norms | Quarantine malformed input or adjust numeric recipe only with evidence |
| LR appears correct but outcomes vary | Scheduler unit mismatch; different effective batch or data order | Log LR against step and tokens, batch and sampler state | Pin schedule semantics and random/data state |

## 11. Interview and self-check questions

### Q1. Why is a learning rate not meaningful by itself?
**Answer:** Its behavior depends on optimizer, architecture, batch/token count, data, schedule, precision and implementation.
**Reasoning:** These jointly determine update magnitude and stability.
**Follow-up:** What should a run record?
**Answer:** The full config, versions, consumed tokens, schedule state, and relevant runtime observations.

### Q2. Compute tokens/update for 4 sequences/device, 8 replicas, 4 accumulation steps, length 2,048.
**Answer:** 262,144 token positions per update.
**Reasoning:** `4*8*4*2,048=262,144`.
**Follow-up:** Are all positions loss-bearing?
**Answer:** Not necessarily; padding and masks reduce the actual target count.

### Q3. What does gradient accumulation change?
**Answer:** It aggregates gradients across microsteps before an optimizer update, changing effective batch/update frequency under a declared convention.
**Reasoning:** It can approximate a larger batch, but randomness, normalization, clipping and update timing can differ.
**Follow-up:** What count should be matched?
**Answer:** Both token positions and actual loss-bearing targets, plus update and compute budgets as relevant.

### Q4. What is warmup for?
**Answer:** It gradually increases learning rate early in some recipes to reduce instability.
**Reasoning:** The initial model/optimizer state may be sensitive to full-rate updates.
**Follow-up:** Does warmup guarantee stability?
**Answer:** No; data, architecture, precision and other settings still matter.

### Q5. What can frequent gradient clipping indicate?
**Answer:** Persistent large gradients or a configuration/data/numerical problem.
**Reasoning:** Clipping caps updates but does not explain their cause.
**Follow-up:** What should be logged?
**Answer:** Pre-clip norms, clipping scope, fraction clipped, loss and affected batches.

### Q6. Why distinguish step-based from token-based decay?
**Answer:** Changing batch or sequence length changes tokens per update, so the same step horizon may represent a different data exposure.
**Reasoning:** Schedule progress depends on its unit.
**Follow-up:** How make it reproducible?
**Answer:** State the unit and log both steps and consumed tokens.

### Q7. Why save sampler and optimizer state for resume?
**Answer:** To avoid changing data order, optimizer moments, schedule or consumed-token state.
**Reasoning:** Model weights alone do not reconstruct the training trajectory.
**Follow-up:** Is exact reproducibility always guaranteed?
**Answer:** No; distributed kernels and nondeterminism may prevent bitwise identity; document the guarantee actually tested.

### Q8. Under the example schedule, what is the learning rate at update 200?
**Answer:** `1.5e-4`.
**Reasoning:** Halfway through linear warmup to `3e-4`.
**Follow-up:** What is the final rate?
**Answer:** `3e-5`, 10% of peak.

### Q9. Why compare runs at matched tokens and not only updates?
**Answer:** Different batch/sequence settings can process different data per update.
**Reasoning:** Equal step count does not imply equal training exposure.
**Follow-up:** What else can differ?
**Answer:** Compute, throughput, optimizer updates, mask count and data repetition.

### Q10. What makes a hyperparameter sweep controlled?
**Answer:** Fixed data/objective/model/evaluation where possible, declared resource budget, bounded candidate changes, matched progress and recorded failures.
**Reasoning:** Otherwise differences are confounded.
**Follow-up:** How select a final run?
**Answer:** Use predefined validation criteria and a protected final test, then verify operational feasibility.

## 12. Quick reference card

| Area | Record or verify |
|---|---|
| Optimizer | Implementation/version, coefficients, epsilon, parameter groups and decay exclusions. |
| Learning rate | Peak/min, schedule shape, warmup, unit (steps/tokens), endpoints and resume behavior. |
| Batch | Microbatch, replicas, accumulation, sequence length, padding and loss-bearing targets/update. |
| Stability | Loss, gradient norms, clipping fraction, non-finite/overflow and skipped updates. |
| Precision | Weights/activations/optimizer state, accumulation, scaler and numerical checks. |
| Data | Release, sampler state, consumed unique/processed tokens and replay. |
| Checkpoint | Model, optimizer, scheduler, scaler, RNG, sampler and distributed state as needed. |
| Tuning | Controlled comparisons, matched budget, validation protocol and failure records. |
| Evidence | Schedule arithmetic is illustrative; no training run performed. |
