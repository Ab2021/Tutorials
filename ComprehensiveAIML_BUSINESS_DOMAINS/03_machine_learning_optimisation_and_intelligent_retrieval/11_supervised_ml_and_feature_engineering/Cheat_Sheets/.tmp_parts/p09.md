
## 9. Complexity & Cost Analysis

### 9.1 Training cost of each family

The cost model below counts the dominant operation per family and converts at an assumed throughput. Throughput is ILLUSTRATIVE; the ratios between families are what transfer.

```text
COST MODEL (training)                                    LTB-40
   ridge closed form:      O(n d^2 + d^3)       one pass to form X'X, one solve
   lasso (coordinate desc):O(n d * passes)      typically 20-100 passes
   single CART tree:       O(d n log n)         sorting per node level
   histogram boosting:     O(M L d n)           bin scan per level, all rows
   exact-sort boosting:    O(M d n log(n/2^L))  sort per node level
   forest:                 O(B L d_sub n)       subsampled columns per split

   n = rows, d = features, M = boosting rounds, L = depth,
   B = forest trees, d_sub = columns per split

NUMERICAL EXAMPLE (ILLUSTRATIVE, n = 200,000, d = 60, M = 300, L = 6)
   histogram boosting: 300 * 6 * 60 * 200,000 = 21,600,000,000 operations
     at 2e9 simple operations per second on one core -> 10.8 s
     on 8 cores -> 1.35 s
   exact-sort boosting, per tree, summing over levels:
     level 0: 60 * 200,000 * log2(200,000)      = 60*200,000*17.61 = 2.11e8
     level 5: 60 * 200,000 * log2(200,000/32)   = 60*200,000*12.61 = 1.51e8
     summed over six levels                          = 1.088e9 per tree
     over 300 trees                                  = 3.264e11
     at 1e8 comparisons per second (sorting is not a simple op) -> 3,264 s
   ratio exact-sort / histogram at these settings = 3.264e11/2.16e10 = 15.1
```

The 15× factor is why histogram binning is the default in modern implementations. It is not a small optimisation; it is the difference between a ten-second fit and an hour-long one, and it changes what can be explored in a working day.

### 9.2 Memory

| Artefact | Size at `n = 200,000`, `d = 60` | Formula | Note |
|---|---|---|---|
| Feature matrix, binned uint8 | 12.0 MB | `n d` | One byte per cell |
| Feature matrix, float32 | 48.0 MB | `4 n d` | Needed for the linear family |
| Feature matrix, float64 | 96.0 MB | `8 n d` | Rarely necessary |
| Gradients and hessians | 1.6 MB | `2 × 4 n` | Two float32 vectors |
| Histogram accumulators | 0.2 MB | `2 × d × bins × 8` | `2×60×255×8`; per node, reused |
| Trained model, 300 trees depth 6 | 206 KB | `M 2^L × 11` | Eleven bytes per node |

Three observations. The model is small — a 300-tree model is a few hundred kilobytes, not a few hundred megabytes — so serving memory is never the constraint for tabular boosting. The *training* memory is dominated by the feature matrix, and binning it to one byte per cell is an 8× saving over float64. The gradient vectors are trivial, which is why row subsampling is cheap in memory and expensive only in the number of rounds needed.

For contrast, a 200-tree forest of depth 12 needs `200 × 4095` nodes, which at eleven bytes each is 9.0 MB — forty times the boosted model, because each forest tree is fully grown while each boosted tree is shallow.

### 9.3 Serving cost

```text
COST MODEL (serving)                                     LTB-41
   per-row cost = M * L node visits * cost per visit
   at 5 ns per visit (pointer chase, one comparison, cache miss likely)

   M = 300, L = 6 -> 1,800 visits -> 9.0 microseconds per row
     single-threaded throughput = 1e6/9.0 = 111,111 rows per second

   latency budget -> maximum ensemble size, depth 6:
     1 ms  -> 200 visits   -> 33 trees
     10 ms -> 2,000 visits -> 333 trees
     50 ms -> 10,000 visits -> 1,666 trees
```

The first row of that budget table is the one that ends arguments. A 1-millisecond budget admits roughly 33 depth-6 trees, which is far below the 300 to 1,000 that a tuning exercise will happily select. Either the budget is a real constraint and the ensemble must be truncated, or the budget must be renegotiated — but the model configuration cannot simply be chosen as if the budget did not exist. Truncation itself is defensible: the first 33 trees carry most of the movement (§6.7), so a truncated model is usually a slightly worse model rather than a broken one.

### 9.4 Retraining economics

A model that takes 40 minutes to fit can be retrained nightly inside a batch window; a model that takes six hours cannot. The comparison below is ILLUSTRATIVE arithmetic on the §9.1 figures.

| Family | Fit time at the §9.1 size | Nightly retrain feasible | Annual fits | Notes |
|---|---|---|---|---|
| Ridge | Under a second | Yes, hourly | 8,760 | Cost is the pipeline, not the fit |
| Single tree | Under a second | Yes, hourly | 8,760 | Unstable, so frequent refits do not help |
| Histogram boosting, 300 rounds | 10.8 s single-core | Yes, per shift | 3,650 | Fits inside any batch window |
| Exact-sort boosting, 300 rounds | 3,264 s single-core | Marginal | 365 | The fit itself becomes the schedule |
| Forest, 200 trees depth 12 | About 2 s of scan work, but a 9 MB model | Yes | 3,650 | Serving memory grows with retrains if versions accumulate |

The last column is the operational trap: a nightly retrain that keeps every version for rollback accumulates model artefacts. At 206 KB per boosted model, a year of nightly retrains is about 75 MB, which is nothing; at 9 MB per forest it is 3.3 GB, which is a conversation with the platform team.

### 9.5 Where the cost actually goes

The operation count above is not the whole story, and a practitioner who optimises against it alone will optimise the wrong thing.

- **Data movement dominates at scale.** Reading 200,000 rows × 60 columns from storage and joining them point-in-time usually costs more wall-clock time than the fit. A histogram fit that takes 10 s inside a pipeline that takes 40 minutes has optimised 0.4% of the runtime.
- **Hyperparameter search multiplies everything.** A 40-point grid at 10 s per fit is 400 s; a 200-point Bayesian search is 2,000 s. Search cost, not single-fit cost, is what makes experimentation slow.
- **Feature recomputation is often the largest term.** If each candidate configuration requires recomputing the feature matrix because the transformations live in a script rather than a materialised table, the fit is free by comparison.
- **Serving cost scales with request volume, not model count.** At 1,000 requests per second, 9 microseconds per row is 0.9% of one core; at 100,000 requests per second it is 90% of one core, which is when the ensemble size becomes a capacity decision rather than a modelling one.
