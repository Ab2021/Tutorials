
## 8. Failure Modes & Edge Cases

### 8.1 Failure index

Each entry states a symptom, the competing causes that produce that symptom, the check that discriminates between them, and the correction. The competing causes matter more than the symptom: "validation loss is bad" has at least five distinct mechanisms behind it and only one of them is fixed by tuning.

| ID | Failure | Symptom | Primary competing causes |
|---|---|---|---|
| FM-01 | Scale-dependent penalty | Ridge and lasso disagree wildly on the same data | Unscaled features; correlated group; a single outlier row |
| FM-02 | Cardinality-driven importance | An ID-like column tops gain importance | High cardinality; genuine signal; a leakage path |
| FM-03 | Unbounded leaf chase | Probabilities saturate at 0 and 1 | `lambda` at zero; `min_child_weight` too low; shrinkage at 1 with too many rounds |
| FM-04 | Gamma starves the model | Loss never drops below the intercept-only value | `gamma` above the achievable gain; depth 0; a single uninformative feature |
| FM-05 | Extrapolation flatline | Predictions constant outside the training range | Family limit; missing linear term; clipping upstream |
| FM-06 | Early stopping on the reported split | Reported metric better than deployment | Stopping set equals the evaluated set; no third split |
| FM-07 | Monotone constraint misapplied | Constrained model fits worse and hides it | Constraint sign reversed; constraint on a proxy feature; true non-monotonicity |
| FM-08 | Bin collapse | A feature contributes nothing though it has signal | Ties heavier than the bin budget; degenerate quantile edges |
| FM-09 | Importance sign flip across retrains | Two features trade places in the ranking | Correlated pair; split-count importance; small sample |
| FM-10 | Linear leaf on thin data | Spectacular training fit, terrible holdout | Fewer than ten rows per coefficient; no ridge on the leaf fit |

### 8.2 The triage order

When a tree-ensemble result is suspect, run checks in this order, because each one invalidates the ones after it.

1. **Is the split sound?** If rows from the same entity appear on both sides, nothing downstream is interpretable. Check entity overlap counts, not just dates.
2. **Is the stopping set disjoint from the evaluation set?** Early stopping makes the "held-out" score an optimistic estimate unless a third split exists.
3. **Did any split actually happen?** Print the tree count and the leaf count. A model with `gamma` too high silently produces one leaf per tree.
4. **Are the leaf sizes sane?** Print the distribution of `H` per leaf. Leaves with `H < 0.5` are shouting.
5. **Are the features on comparable scales?** Only relevant for the linear and linear-leaf cases, but fatal there.
6. **Is the reported metric the operating-point metric?** A ranking metric can improve while the queue at the deployed threshold gets worse.
7. **Only now, tune.**

### 8.3 Dossier FM-01 — the penalty that punished the wrong feature

**Symptom.** A ridge fit and a lasso fit on the same 40 features produced coefficient sets with no overlap in the top five, and the ridge model's validation AUC was 0.63 while lasso reached 0.71. Both were run through the same pipeline.

**Competing causes.** (a) The features were never standardised, so the penalty on a feature measured in thousands was negligible while the penalty on a ratio measured in `[0,1]` was enormous. (b) The features arrived in a correlated group and lasso selected one arbitrarily while ridge spread the weight. (c) A single outlier row distorted the OLS solution that both penalties shrink toward.

**Discriminating check.** Print each feature's standard deviation and the product `lambda * sd(x_j)`, which is the penalty expressed in the units of `y`. If that product spans more than an order of magnitude across features, the fit is not regularised — it is selectively punished. For (b), refit ridge and check whether the correlated pair's coefficients keep the same sign; lasso cannot answer that question because it removes one.

**Correction.** Standardise inside the fit, persist the scaling parameters with the model, and never re-derive them at scoring time from the serving batch. Then re-run the comparison.

**Prevention.** Make standardisation a property of the estimator pipeline, not a preprocessing script. A pipeline that cannot be serialised with its scaler will drift.

### 8.4 Dossier FM-03 — three rows decided the score

**Symptom.** A boosted model's validation log-loss rose after the team "improved" it by allowing deeper trees, and the probability histogram became bimodal at 0.02 and 0.97.

**Competing causes.** (a) `lambda` was left at the library's permissive default while depth increased, so each thin leaf received an undamped weight. (b) `min_child_weight` was unset, permitting leaves whose total `H` was below 0.5. (c) The shrinkage was 1.0 with 200 rounds, so there was no limit on total movement.

**Discriminating check.** Compute `H` per leaf and plot the histogram. With `H_j = sum p(1-p)` and `p` near 0.5, a leaf of three rows has `H` around 0.75; a leaf of one row around 0.25. In the failing model the median leaf `H` was 0.31, meaning half the leaves were effectively single rows. That single fact separates (b) from (a): if thin leaves dominate, `min_child_weight` is the primary cause regardless of `lambda`.

**Correction.** Set `min_child_weight` so that each leaf holds at least 20 effective rows (`H >= 5` at mid-range probabilities), then re-examine `lambda`.

**Prevention.** Log the leaf-size distribution as a training artefact next to the loss curve. A config that improves validation loss while halving median leaf size is a warning, not a win.

### 8.5 Dossier FM-05 — the flatline nobody tested

**Symptom.** A demand model scored well on backtests and then predicted an identical value for every store in a new region where volumes were 2.4 times higher than the training maximum.

**Competing causes.** (a) The tree cannot extrapolate, so every new-region row falls into the highest-volume leaf and receives that leaf's constant. (b) A winsorisation step upstream clipped the volume feature at the training maximum, so even a linear model would have seen a constant. (c) The new region genuinely has a different relationship and no model would transfer.

**Discriminating check.** Feed the model a synthetic row with the volume feature at 3× its training maximum and inspect the output. If the prediction equals the top leaf's constant to full precision, cause (a) is confirmed. Then check the raw feature distribution reaching the model: if it is already clipped, the failure is upstream and (b) is the cause. Distinguish (c) by checking whether any feature other than volume differs systematically in the new region.

**Correction.** Either add a linear term for the volume feature outside the ensemble (a residual linear model on top of the trees), or replace the volume feature's constant leaves with linear leaves so that each leaf carries a slope.

**Prevention.** Record the training min/max of every feature and compare with the serving distribution weekly. A feature exceeding 1.5× its training maximum is an extrapolation event and should raise a flag before it reaches a decision.

### 8.6 Edge case: the perfectly separable training set

When a feature separates the classes completely, unregularised logistic regression drives coefficients toward infinity and, in a finite-precision implementation, either diverges or stops at an arbitrary large value. Boosted trees with `lambda = 0` behave the same way over enough rounds. The symptom is a coefficient or leaf value whose magnitude grows with every iteration while the training loss decreases toward zero.

The check is to look at the coefficient or leaf-value trajectory, not the loss. If the magnitude grows monotonically while the loss curve flattens, you are in the separable regime. The fix is a positive penalty, which has a unique finite solution.

### 8.7 Edge case: `min_child_weight` measured on the wrong quantity

Some implementations treat the minimum-child criterion as a row count, others as a sum of `H`. On a balanced, mid-probability dataset the two are proportional (factor 0.25) and the distinction is invisible. On a heavily imbalanced dataset with base rate 0.02, `H` per row near the prior is `0.02 × 0.98 = 0.0196`, so a threshold of "5" means 255 rows if interpreted as `H` and 5 rows if interpreted as a count. Porting a configuration between libraries without checking which definition applies is a common and silent cause of overfitting.

### 8.8 Edge case: monotone constraint on a proxy

A monotone constraint says "the output must not decrease in this feature". If the feature is a proxy for something else, the constraint can be true of the proxy and false of the construct you care about. The failure is silent: the model still trains, the constraint still holds, and the output is still wrong in the region where the proxy and the construct diverge. The discriminating check is to plot the fitted function against the construct (not the proxy) on held-out rows; a monotone-in-proxy curve that is non-monotone in the construct means the constraint was applied to the wrong variable.

### 8.9 Edge case: `gamma` interacting with subsampling

With row subsampling, each tree sees a different subset, so the achievable gain varies per round. A `gamma` tuned on the full-data distribution will admit or refuse splits inconsistently across rounds, and the effective number of trees becomes random. The symptom is a training run whose tree count changes materially between seeds with the same configuration. The check is to run three seeds and compare admitted-tree counts; a spread wider than about 10% means `gamma` is sitting near the noise floor and should be lowered or the subsampling fraction raised.
