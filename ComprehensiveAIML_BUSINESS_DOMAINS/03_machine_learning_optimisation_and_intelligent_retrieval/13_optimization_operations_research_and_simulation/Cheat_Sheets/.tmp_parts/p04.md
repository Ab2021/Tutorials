## 4. Core Formulas with Full Derivation

The topic is diagnostic rather than constructive, so each block below is a **mechanism/invariant block**: preconditions → state transition → invariant and justification → worked trace → failure boundary. The four blocks correspond to the four layers of §2.

### 4.1 Base case: the monotonicity battery

**Preconditions.** Two runs of the same solver, `R1` and `R2`, on two instances that differ by exactly one declared modification. Both runs terminated with a proven bound, and both are maximisation problems unless stated otherwise. The modification is one of: relax integrality, add a constraint, raise a price coefficient, tighten a tolerance.

**State transition.** The instance changes; the feasible set changes; the reported optimum changes. What is asserted is the *direction* of the change, not its magnitude.

**Invariant and justification.** Four directions hold unconditionally, and each follows from set inclusion rather than from any property of the algorithm:

```text
D1  relax integrality:      F_LP superset of F_IP   =>  z_LP >= z_IP
D2  add a constraint:       F_new subset of F_old   =>  z_new <= z_old
D3  raise a price c_j:      same F, larger c        =>  z_new >= z_old
D4  tighten a tolerance t:  F(t') subset of F(t) for t' < t  =>  z_new <= z_old
```

`D1` holds because integrality is a restriction: every integer-feasible point is LP-feasible, so the LP's maximum over the larger set cannot be smaller. `D2` holds because an optimum over a subset cannot exceed an optimum over the superset. `D3` holds because the objective is evaluated at the same points with a weakly larger coefficient. `D4` holds because a smaller tolerance excludes points the looser one admitted. None of these depends on convexity, on the solver, or on run-to-run determinism — which is exactly why a violation is informative.

**Worked trace.** The LP `max 8x + 5y` subject to `6x + 4y <= 9`, `x, y >= 0`:

```text
LP optimum      x = 9/6 = 1.5, y = 0     ->  z_LP = 8 * 1.5 = 12
integer points  (0,0)=0  (1,0)=8  (0,1)=5  (0,2)=10   (1,1) infeasible: 6+4=10 > 9
so integer optimum (0,2) -> z_IP = 10
D1 check        z_LP = 12 >= z_IP = 10            holds
integrality gap (12 - 10)/10 = 0.20 = 20%          relative to the integer optimum
relative to LP  (12 - 10)/12 = 0.1667 = 16.67%     the other denominator, sometimes quoted
```

Now violate `D2` deliberately: add the constraint `y >= 1`. Feasible integer points with `y >= 1` are `(0,1) = 5` and `(0,2) = 10`, so the integer optimum stays `10`. The constraint was redundant for the integer problem but not for the LP: the LP optimum becomes `x = 5/6 = 0.8333`, `y = 1`, value `8*0.8333 + 5 = 11.667`. Both dropped, neither rose. The interesting case is when a reported optimum *rises* after a constraint is added: that is not a property of mathematics, it is evidence that the two runs solved different models — a cached build, a stale `M`, an input file from a different snapshot.

**Failure boundary.** The battery is only as strong as the claim that "only one thing changed". Two boundaries:

- If the modification simultaneously changes the feasible set and the objective (as adding a penalty row to the objective does), the directions conflict and the check is vacuous. Split the modification into two runs.
- `D3` fails to hold for *minimisation* unless the sign is flipped, and it fails for an objective coefficient that is bounded above by the constraint set. State the objective sense on every assertion; a battery that assumes maximisation and is applied to a cost model reports false failures and destroys trust in the check.

**Validity condition.** The battery licenses the sentence "at least one input differs between these two runs". It does not license "the second model is correct", and it does not detect an error present in both runs. A defect shared by both builds satisfies all four directions, which is why the battery must be paired with an external oracle — brute-force enumeration at small `n`, or a physically checkable replay.

### 4.2 General case: separating power and the economics of triage

**Preconditions.** A symptom `S` and two or more candidate causes `C_1 ... C_k` that can each produce `S`. A probe `P` is available whose outcome is binary. The prior probability of cause `i` is `p_i`, and the probe's behaviour is described by its true-positive rate `a_i = P(P = + | C_i)` and false-positive rate `b = P(P = + | not C_i)`.

**State transition.** Before the probe, the belief is the prior `p`. After a positive outcome, the belief is the posterior; after a negative outcome, the complement. The state is the posterior, and the transition is Bayes' rule:

```text
P(C_i | +) = p_i * a_i / ( p_i * a_i + (1 - p_i) * b )
P(C_i | -) = p_i * (1 - a_i) / ( p_i * (1 - a_i) + (1 - p_i) * (1 - b) )
```

**Invariant and justification.** A probe is *useful* only if it moves the posterior enough to change the next action. The quantity that decides this is the likelihood ratio `a_i / b` for a positive result: the probe separates `C_i` from the field by that factor. A probe with `a_i = b` has likelihood ratio `1` and is worthless no matter how authoritative it sounds. The justification is direct from the formula: if `a_i = b`, numerator and denominator share the factor `b`, and the posterior equals the prior.

**Worked trace.** Two causes of "plan is feasible but the workshop says it is overbooked": endpoint convention (`C_1`, prior `0.5`) and a stale buffer (`C_2`, prior `0.3`), remainder other (`0.2`). The probe is "find one pair with `f_A == s_B` and check whether the plan places both on the same resource". For `C_1` this probe fires with `a_1 = 1.0`; for `C_2` it fires with `a_2 = 0.2`, because a stale buffer can also produce a touching pair; for the remainder take `a = 0.1`.

```text
positive outcome:
  numerator C1    = 0.5 * 1.0 = 0.500
  numerator C2    = 0.3 * 0.2 = 0.060
  numerator other = 0.2 * 0.1 = 0.020
  total           = 0.580
  P(C1|+) = 0.500 / 0.580 = 0.862
  P(C2|+) = 0.060 / 0.580 = 0.103
  P(other|+) = 0.020 / 0.580 = 0.034
```

One probe costing about thirty seconds of inspection moves the leading hypothesis from `50%` to `86%`. That is the entire argument for ordering probes by cost and by likelihood ratio rather than by how interesting the hypothesis is.

**Failure boundary.** Bayes' rule is only valid if the probe's error rates are the ones you assumed, and the common failure is to *overstate* `a_i`. A probe that "checks the endpoint convention" but reads the timestamps from the same transformed table the solver read cannot discriminate at all: both hypotheses predict a positive result, `a_1 = a_2 = 1`, likelihood ratio `1`, posterior equals prior. This is the mechanism behind the most frustrating kind of debugging session — every check passes and the belief never moves, because every check was run downstream of the transformation under suspicion.

**Validity condition.** The posterior is a belief about the *cause of the symptom*, not about the correctness of the model. An `86%` posterior on an endpoint convention says where to look first; it does not say that fixing the convention will make the plan correct. The arithmetic above is ILLUSTRATIVE: the priors and error rates are constructed, not measured, and a different prior ordering changes which probe is cheapest in expectation.

### 4.3 Variants: gap, bound, and the range of a shadow price

**Preconditions.** A solver report containing an incumbent `z_inc`, a bound `z_bnd`, and a gap `gamma`. The report is for a maximisation.

**State transition.** The gap converts a bound into a usable interval, and the interval is what gets quoted.

```text
gamma = (z_bnd - z_inc) / |z_bnd|        definition used by most solvers
z_inc = z_bnd * (1 - gamma)              implied lower bound, exact under the definition
```

**Invariant and justification.** `z_inc <= z* <= z_bnd`, where `z*` is the true optimum, and the invariant survives any amount of solver internal behaviour because it is a statement about two *proofs*: the incumbent is proven feasible (a certificate exists in the form of an assignment satisfying every row), and the bound is proven valid (a dual solution or a node frontier). The gap is the width of the remaining uncertainty, expressed relatively.

**Worked trace, three gaps on the same instance.**

```text
gamma = 0.120,  z_bnd = 1000  ->  z_inc >= 1000 * 0.880 = 880     uncertainty band 120
gamma = 0.050,  z_bnd = 1000  ->  z_inc >= 1000 * 0.950 = 950     uncertainty band 50
gamma = 0.010,  z_bnd = 1000  ->  z_inc >= 1000 * 0.990 = 990     uncertainty band 10
```

Three statements with the same solver, the same model, and radically different evidential value. "We solved it" is true in all three. "The plan captures at least `99%` of attainable value" is true only in the third. Going from `12%` to `5%` buys `70` units of guaranteed value; going from `5%` to `1%` buys `40`. The marginal value of solver time is decreasing in exactly this arithmetic, which is the quantitative reason a `5%` gap is often the right stopping point and a `0.01%` gap is usually a vanity metric.

**Variant: the shadow price has a range.** A dual value is a *local* rate, valid only while the basis that produced it stays optimal. On `max 5x + 4y` subject to `2x + y <= 10 + b`, `x + 2y <= 8`:

```text
b      LP optimum    marginal value of b
0      28.00          -
1      30.00          +2
2      32.00          +2
3      34.00          +2
4      36.00          +2
5      38.00          +2
6      40.00          +2   (x = 8, y = 0; first row binding at equality)
7      40.00           0   (second row binds alone; b is slack capacity)
12     40.00           0
```

Dense-grid evaluation confirms each row to three decimals (the grid step of `0.0005` explains intermediate values like `29.999` and `31.9995`). The shadow price on `b` is `2` on `[0, 6]` and `0` above it. Extrapolating the local rate to `b = 12` gives `28 + 2*12 = 52`, an overstatement of `(52 - 40)/40 = 30%`. The failure is not arithmetic; it is applying a derivative outside the interval where it is the derivative.

**Failure boundary.** That interval was obtained by re-solving, which is the only honest way to get it; a solver's reported sensitivity range is valid for the *reported basis* and becomes invalid the moment a degenerate pivot changes it. Degeneracy is the boundary case: when the optimum sits at an intersection of three or more rows, the shadow price is not unique, and two solvers can legitimately report `2` and `0` for the same row. The correct response is to report a range and a chosen convention, not to average them.

**Validity condition.** These formulas assume a maximisation with `z_bnd > 0` and a bound that is genuinely valid. Under a minimisation the gap definition becomes `(z_inc - z_bnd)/|z_bnd|` and the sign of every "at least" flips; a report quoted across objective senses without this flip is off by the whole gap, not by a rounding error.

### 4.4 Limits and counterexamples

**Counterexample 1 — the bound is valid and useless.** Suppose a relaxation returns `z_LP = 10,000` on an instance whose integer optimum is `1,000`. All four directions hold, the gap is `90%`, and the bound prunes nothing: every node has an LP bound above the incumbent, so branch-and-bound degenerates to enumeration. A valid bound is not a *tight* bound, and the difference decides whether the method is affordable. The discriminating observation is node count per unit of gap closed, not the gap itself.

**Counterexample 2 — the tolerance makes an infeasible plan feasible.** A flow-conservation row `sum_out - sum_in = 0` evaluated on `0.1`, `0.2`, `0.3` coefficients yields a residual of `5.55e-17`, correctly accepted at a tolerance of `1e-6`. Scale the same network to units of thousands and the residual scales with the coefficients: a tolerance of `1e-7` applied to a model expressed in thousands is effectively `1e-4` in original units, so a genuine leak of `1e-5` passes as conservation. The invariant "residual below tolerance" is scale-dependent and therefore not an invariant at all until it is normalised — divide by a conserved scale, for example the total supply.

**Counterexample 3 — replication cannot fix a biased estimator.** A simulation whose warm-up is discarded at `2` hours when the transient lasts `4` will return a mean that is too low on every replication. Replicating `1,000` times produces a confidence interval of essentially zero width around the biased value. With a true mean of `21.4` and a warm-up-truncated mean of `19.7`, the bias is `(21.4 - 19.7)/21.4 = 7.9%`, and no number of replications moves it. This is the most damaging confusion in the catalogue, because the analyst's instinct — "add replications" — is exactly wrong: it increases the precision of a wrong number and thereby increases confidence in it.

**Counterexample 4 — the invariant that holds only for identical resources.** Minimum resource count equals peak simultaneous depth, a theorem about interval graphs. Add eligibility — a job runnable on only two of three bays — and the equality fails: the graph is no longer interval, chordality is lost, and the chromatic number can exceed the clique number. A scheduler that sizes the roster by peak depth and then applies eligibility will be short by however many jobs hit the restricted bays at once. The discriminating check is a small instance where a restricted job overlaps two eligible-bay jobs.

**Validity condition for the whole section.** Every invariant here is stated for a *declared* model class: maximisation, fixed instance, known feasibility relation, identical resources where stated. The catalogue's purpose is to make those declarations visible, because the failure mode that survives review is always the one where the declaration was implicit.
