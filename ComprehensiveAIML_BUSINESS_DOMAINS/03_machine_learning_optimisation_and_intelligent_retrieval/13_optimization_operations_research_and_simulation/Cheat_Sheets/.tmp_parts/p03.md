## 3. Foundational Definitions

The catalogue uses eight fields per issue. Their meaning is fixed here so that the entries in §8 and §11 can be terse without being ambiguous.

| Field | What it must contain | What it must not be |
|---|---|---|
| `ISSUE-ID` | a stable identifier `CI-nnn`, never reused after retirement | a number that changes when the sheet is reordered |
| `category` | one of the four defect classes defined below | a free-text tag such as "modelling bug" |
| `symptom` | an observation available in output, a log, or a replay — a value, a flag, an inequality that fails | "the answer looks wrong" |
| `competing causes` | at least two mechanisms that produce that *same* observation | a single cause, which is a guess rather than a diagnosis |
| `discriminating check` | a probe whose outcomes differ between the competing causes, ideally cheap and non-destructive | "investigate further" |
| `correction` | the change to make, stated at the level of the artefact (contract, data, model, code) | "fix the bug" |
| `prevention` | an assertion, test, or review gate that would have caught it before release | "be more careful" |
| `verification` | how you confirm the correction worked and the symptom is gone *and* nothing else moved | "re-run" |

**The four categories.** They partition defects by *where the error entered*, which determines who fixes it and how expensive the fix is.

`VIOLATED_ASSUMPTION` — the mathematics is correct and the model is faithfully solved, but a premise the method requires is false for this instance. Earliest-finish greedy on unequal values, an `M/M/1` formula on arrivals that are not Poisson, an LP bound treated as attainable when the solution is fractional. The distinguishing feature is that the solver's report is *true*: it says "optimal" and the answer is optimal *for the model it was given*. Nobody lied; a hypothesis failed.

`NUMERICAL_EDGE` — the formulation is right and the instance satisfies its assumptions, but a floating-point tolerance, a scaling choice, or a rounding convention changes the answer. Residuals just under a feasibility tolerance, `M` values that exceed the arithmetic range of the constraints they control, coefficients whose ratio spans nine orders of magnitude, `0.1 + 0.2 - 0.3 = 5.55e-17` making a conservation check fail on an exact identity. These are the cheapest to fix and the hardest to find, because the arithmetic is right everywhere except at the boundary.

`SCALE_FAILURE` — the method is correct and the arithmetic is exact, but the problem's size or the run's length puts it outside the region where the method is affordable or where the estimate is unbiased. State-space explosion in a multi-machine dynamic program, a time-indexed formulation with `345,600` binaries when the interval model needs `720`, a simulation whose conclusion rests on one run of a process that has not reached steady state.

`CONCEPT_CONFUSION` — two things that resemble each other are used interchangeably. Count objective versus value objective; earliest-due-date versus earliest-finish; hard constraint versus penalty; average load versus peak load; correlation between two series versus common random numbers used to *create* correlation; expected value versus minimax. The tell is that the wrong choice is *defensible in words* and produces a plausible number, which is why this class survives review longer than any other.

**Terms used in the entries.**

*Instance* — one concrete input: the coefficient matrix, right-hand side, objective vector, and any side data such as eligibility. Two runs on different instances are not comparable even when they use the same code.

*Incumbent* — the best feasible solution found so far. *Bound* — a proven limit on how good any feasible solution can be. *Gap* — the relative distance between them, conventionally `(upper - lower)/|upper|` for a maximisation, so a solver reporting a `12%` gap on an upper bound of `1,000` has a lower bound of `880`. The gap is a statement about *proof*, not about *quality*: a `0%` gap proves optimality within tolerance and says nothing about whether the model was right.

*Relaxation* — a problem whose feasible set contains the original's. The LP relaxation of a MIP drops integrality. A relaxation's optimum is an optimistic bound; it is attainable only if the relaxation happens to have an integral optimum.

*Integrality gap* — the relative loss from forcing integrality: `(z_LP - z_IP)/z_IP` for a maximisation. On the two-variable example `max 8x + 5y` subject to `6x + 4y <= 9`, `x, y >= 0` integer, the LP optimum is `x = 1.5`, `y = 0`, value `12`, while the integer optimum is `y = 2`, value `10`, so the integrality gap is `(12 - 10)/10 = 20%`. The gap is a property of the *formulation*, not of the solver: a tighter formulation of the same integer problem can have a smaller gap and solve in a fraction of the nodes.

*Soft constraint* — a rule expressed as a penalty in the objective, therefore violable if the penalty is smaller than the value gained. *Hard constraint* — a rule expressed as a row, therefore never violated in a feasible answer. The distinction is not stylistic: a policy written as a soft constraint of weight `5` per unit will be broken whenever an alternative earns more than `5`, and the resulting plan is "optimal" and non-compliant.

*Event time versus processing time* — event time is when the thing happened (a job finished at 14:03). Processing time is when the system learned it (the record was written at 14:09). A plan built from a snapshot is correct with respect to processing time and wrong with respect to event time; every late-arrival defect in this catalogue lives in that gap.

*Warm-up (transient)* — the initial period of a simulation during which the state distribution depends on the starting condition rather than on the system. *Steady state* — the regime where the distribution no longer depends on the start. Discarding warm-up is not optional when the performance measure is a level; it is optional only when the measure is a difference between two policies that share the same start.

*Replication* — an independent run with a different random-number stream. Replications estimate variability; a longer single run estimates a path. Confusing them is the most common statistical error in this unit, because a long run produces a very small standard error around a quantity that is not the one you meant to estimate.

*Common random numbers (CRN)* — using the same stream for two configurations so that their difference has lower variance than under independence. With per-configuration standard deviation `1.0` and correlation `0.8`, the standard deviation of the difference falls from `sqrt(2) = 1.414` to `sqrt(2 - 2*0.8) = 0.632`, so the variance falls by a factor of `5` and the replication count needed for a given half-width falls by the same factor. CRN is a variance-reduction technique, not a fairness argument.

*Little's law* — `L = lambda * W`, with `L` the mean number in system, `lambda` the mean arrival rate, and `W` the mean time in system. It holds for any stable system under weak conditions, which makes it the best cheap audit available: `L = 12` and `W = 21 min = 0.35 h` implies `lambda = 34.286` per hour, and if the arrival log says `21` per hour, one of the three numbers is measuring a different population.
