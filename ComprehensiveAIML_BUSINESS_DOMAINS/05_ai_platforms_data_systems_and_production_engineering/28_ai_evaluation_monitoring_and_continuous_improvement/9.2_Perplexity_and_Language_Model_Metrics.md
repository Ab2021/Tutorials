# 9.2 — Perplexity and Language Model Metrics

>
> **Boundary:** Perplexity is an exponentiated likelihood quantity for a declared tokenization, mask and corpus. It is not a direct score for instruction following, truthfulness, safety, tool use, user value or free-form generated quality. For objective instrumentation, see [9.1 — Training Metrics and Loss Analysis](9.1_Training_Metrics_and_Loss_Analysis.md).

## Learning outcomes

Learners can calculate perplexity from held-out token negative log-likelihood; state the tokenization/context/mask contract required for comparisons; distinguish corpus likelihood from task evaluation; construct a paired prompt comparison with an explicit tie convention; estimate a paired mean difference under stated assumptions; and prevent a language-model metric from becoming an unsupported release claim.

## 1. Perplexity is a transformed held-out loss

For eligible held-out tokens, mean negative log-likelihood (NLL) is measured in nats/token when natural logs are used. Perplexity (PPL) is its exponential:

```text
FORMULA [PPL-01]: mean_NLL = - (1/N) * sum(t=1..N) log p_theta(y_t | c_t)
                  PPL = exp(mean_NLL)
WHERE: N is the count of eligible scored target tokens; y_t is target token t;
       c_t is its allowed context; p_theta is the model probability; exp uses
       the same natural-log convention as NLL.
CONSTRAINT: N>0; tokenizer/vocabulary, target shift, mask, context policy,
            corpus version and scoring implementation are fixed and recorded.
NUMERICAL EXAMPLE: N=1,000 and summed NLL=1,500 nats gives mean_NLL=1.5 and
                   PPL=exp(1.5)=4.4816890703.
INTERPRETATION: under this precise corpus/tokenization/protocol, the model has
                inverse geometric-mean probability 4.4817. It is not a count
                of literal candidate words or an instruction-quality score.
```

The common informal phrase “effective branching factor” is only an intuition. A subword vocabulary, variable token boundaries, causal context and masked positions mean PPL cannot be read as “the model chooses among exactly 4.48 words.” Preserve NLL and `N`; PPL discards additive convenience and exaggerates numerical differences by exponentiation.

If a system reports bits-per-token instead, use base-2 logarithms or convert `bits_per_token = mean_NLL / ln(2)`. Do not compare a value in bits/token to one in nats/token without conversion. Neither unit is automatically comparable across tokenizers.

## 2. Comparison contract

A valid PPL comparison requires more than identical model family names. Pin and report:

- exact held-out manifest, data version, split-dependency rule and decontamination policy;
- tokenizer/vocabulary/special tokens, rendering template and Unicode normalization;
- target shift, excluded/masked positions and whether EOS/prompt tokens count;
- maximum context length, stride/window policy, document-boundary reset behavior and truncation;
- model checkpoint/revision, precision/runtime and scoring implementation;
- aggregation unit: total tokens, document, sequence, domain or prompt;
- corpus/domain/language slices and their token counts.

Changing any of these can change the event being scored. A tokenizer that encodes a string in fewer or different tokens changes the denominator and conditional probabilities. A longer permitted context can lower NLL without indicating that the model learned better standalone predictions. A test set containing training duplicates can deliver impressively low PPL with no valid generalization claim.

For context-limited models, score documents in a documented sliding-window protocol. Score only positions whose left context is available under the selected policy; do not score a token multiple times unless the estimator explicitly defines that weighting. Resetting at document boundaries versus carrying preceding text changes the conditional problem. There is no neutral default.

## 3. Aggregate first, then transform

Overall corpus PPL must be computed from aggregate token NLL, not by averaging document PPL values:

```text
FORMULA [PPL-02]: PPL_corpus = exp( sum_i NLL_sum_i / sum_i N_i )
WHERE: NLL_sum_i is total eligible-token NLL in unit i and N_i is that unit's
       eligible-token count; each unit uses the same scoring protocol.
CONSTRAINT: all N_i are nonnegative and total N_i>0; units are not first
            equally weighted unless that is the explicitly intended statistic.
NUMERICAL EXAMPLE: document A has N=1, NLL_sum=1; document B has N=9,
                   NLL_sum=9. Then corpus PPL=exp((1+9)/(1+9))=exp(1)=2.71828.
INTERPRETATION: mean document PPL, (exp(1)+exp(1))/2, matches here only because
                both document token losses happen to match; it is not general.
```

Counterexample: document A has one token at NLL `0`; document B has nine tokens each at NLL `2`. Corpus PPL is `exp(18/10)=6.04965`, whereas the unweighted mean of document PPLs is `(exp(0)+exp(2))/2=4.19453`. Report the selected aggregation and per-slice token counts. Use a sequence-weighted statistic only when the decision question is explicitly about a typical sequence rather than a randomly drawn eligible token.

A PPL difference is often easier to analyze in mean NLL: `Delta_NLL = NLL_candidate - NLL_baseline`. Negative values favor the candidate under the common lower-is-better convention. For the same tokenization/protocol, PPL ratio is `exp(Delta_NLL)`. A ratio below one favors the candidate, but does not quantify user impact.

## 4. Likelihood versus generated-task quality

Likelihood scoring uses reference continuations. Generated evaluation asks the model to produce outputs under a decoding policy and scores task-specific properties. They may disagree:

| Question | Suitable primary evidence | Why perplexity alone fails |
|---|---|---|
| Next-token fit to a stable corpus | Held-out NLL/PPL with declared protocol | It is exactly the likelihood objective, not task success |
| Structured extraction | Schema validity, exact/field match, abstention/error analysis | Many plausible tokens can still form an invalid structure |
| Factual QA | Grounded answer accuracy, citation/support audit, abstention behavior | High likelihood can reproduce unsupported but common text |
| Safety/refusal | Adversarial policy suite and human/validated rubric review | A safe response can have lower reference likelihood |
| Code/tool use | Sandboxed execution and task success | Surface-token likelihood does not execute code or tools |
| Creative or open-ended quality | Calibrated human or validated pairwise judging with slices | Reference continuations are not a unique correct output |

Use PPL as one diagnostic among task, safety, operational and calibration metrics. It can catch data/label/tokenization regressions early, but a lower PPL cannot justify replacement when the deployment contract differs from generic corpus prediction.

## 5. Pairwise prompt comparisons

When two candidates are judged on the **same prompts**, preserve pairing. For each prompt, declare whether candidate C wins, baseline B wins, or the comparison ties/is invalid. The treatment of ties must be declared before reporting a rate.

For 200 independent eligible paired prompts with 120 candidate wins, 60 losses and 20 ties:

```text
FORMULA [PAIR-01]: resolved_win_rate = W / (W+L) = 120/180 = 0.6666666667
                  half_tie_score = (W + 0.5*T) / (W+L+T) = 130/200 = 0.65
                  net_win_rate = (W-L) / (W+L+T) = 60/200 = 0.30
WHERE: W, L and T are candidate wins, losses and declared ties/invalid outcomes.
CONSTRAINT: every prompt has one recorded outcome; eligibility, rater/judge
            blinding, order randomization and tie/invalid policy are fixed.
INTERPRETATION: 66.7% is among resolved comparisons; 65% gives ties half credit;
                net win is +30 points over losses on all 200 prompts.
```

These three values answer different questions. Do not report `120/200=60%` as a “win rate” while silently discarding the outcome semantics. Invalid comparisons should normally be a separate category with causes; treating them as ties can hide evaluator failure or unreachable tasks.

Prompt-level outcomes can be clustered by user, document, conversation, domain or template. The effective independence unit may be a cluster rather than a prompt. When prompts share context, a prompt-level confidence interval can be falsely narrow. Define the sampling unit and use a cluster-aware method, resampling or a design that matches the deployment claim.

## 6. Paired uncertainty and decision gates

For a numeric prompt-level metric difference `d_i = score_C,i - score_B,i` on `n` independent units, the sample mean and its standard error are:

```text
FORMULA [PAIR-02]: d_bar = (1/n) * sum_i d_i
                   SE(d_bar) = s_d / sqrt(n)
WHERE: s_d is the sample standard deviation of paired differences; n is the
       number of independent, eligible pairs.
CONSTRAINT: pairs use identical prompts/conditions; sampling unit and dependence
            structure support the uncertainty method; missing pairs are reported.
```

Pairing removes prompt difficulty shared by both candidates and is usually more informative than comparing unrelated aggregates. It does not fix biased prompts, contaminated answers, judge bias, decoding nondeterminism, multiple metric fishing or dependence between examples.

A release gate needs more than “candidate average is higher.” Predeclare primary task metric, critical safety/error rates, non-inferiority margins for mandatory capabilities, required slices, uncertainty rule, valid-comparison coverage, operational constraints and escalation owner. A candidate with a favorable pooled win rate but unacceptable loss on a critical domain fails promotion.

## 7. Failure modes

| Symptom | Candidate causes | Discriminating check | Safe response |
|---|---|---|---|
| PPL improves after tokenizer change | Changed units/denominator, not necessarily better model | Score both under one tokenizer/protocol if valid; report non-comparability otherwise | Do not rank cross-tokenizer PPL directly |
| Very low held-out PPL | Duplicate/leaked data, trivial target, overly short/easy context or masking bug | Dedup/provenance audit; decoded target/mask; time/dependency split | Quarantine result until split/objective are validated |
| PPL differs across runs unexpectedly | Context window, EOS/reset, precision, template, target shift or data version changed | Compare scoring manifest and token/NLL counts | Recompute under one frozen harness |
| Candidate has lower PPL but worse task outcomes | Corpus likelihood is misaligned with task contract | Task/safety results on same checkpoint/version | Keep task gate primary; investigate objective/data mismatch |
| Win rate changes with candidate order | Position bias or non-blind evaluator | Randomized order and blinded re-annotation | Correct protocol before claiming preference |
| Many ties/invalids | Rubric cannot discriminate, prompts ambiguous, system failed or evaluator unstable | Tie reasons, judge traces/rater agreement and prompt audit | Report separately; improve rubric/prompt/evaluator |
| Narrow confidence interval feels implausible | Repeated/clustered prompts treated as independent | Cluster inventory and resampling at dependency unit | Recompute uncertainty at declared unit |
| Benchmark improves but deployment regresses | Benchmark/task population mismatch, contamination or changed prompt policy | Slice/population contract and deployment shadow/controlled evaluation | Block promotion; use representative evaluation |
| PPL calculation overflows/underflows | Exponentiating aggregate loss late or numerical implementation defect | Compute mean NLL in stable dtype; inspect N and finite values | Store NLL and exponentiate only for presentation |

## 8. Bounded checkpoint decision

**Scenario:** Candidate C is trained from a compatible baseline. On a frozen test manifest it reduces mean NLL from `1.50` to `1.45` under identical tokenizer/mask/context policy. Pairwise blinded review on 200 independent prompts produces 120 wins, 60 losses and 20 ties for C. A critical safety slice has only four prompts and one candidate failure; no predefined margin or human-rater calibration exists.

**Problem:** Aggregate likelihood and paired preference are favorable, but the safety evidence and review protocol are insufficient for promotion.

**Decision:** Keep C unpromoted. Record `Delta_NLL=-.05` and the declared pairwise conventions, then enlarge/review the critical safety slice, calibrate/validate the judge against blinded humans, verify prompt independence and predeclare a safety non-inferiority/maximum-failure gate. Re-run the frozen harness without changing tokenizer, prompts or decoding policy.

**Check:** Promotion requires the expanded safety gate, task slices, evaluator validity, lineage and operational checks. No numerical PPL or win-rate threshold is invented here.

## 9. Interview and self-check questions

### Q1. What is PPL when 1,000 scored tokens sum to 1,500 nats of NLL?
**Answer:** `exp(1.5)=4.4816890703`.
**Reasoning:** Mean NLL is `1500/1000=1.5` nats/token.
**Follow-up:** Is that a literal number of next words?
**Answer:** No; it is an exponentiated token-level likelihood quantity.

### Q2. Why retain mean NLL and token count as well as PPL?
**Answer:** NLL aggregates additively with token counts; PPL does not.
**Reasoning:** Corpus PPL is the exponential of aggregate mean NLL.
**Follow-up:** Can document PPL values simply be averaged?
**Answer:** Not for token-weighted corpus PPL.

### Q3. Can PPL compare two different tokenizers directly?
**Answer:** Generally no.
**Reasoning:** They partition text differently and change the scored events.
**Follow-up:** What must be pinned?
**Answer:** Tokenizer, target/mask, corpus, context policy and scoring harness.

### Q4. What is the resolved win rate for 120 wins, 60 losses and 20 ties?
**Answer:** `120/(120+60)=66.67%`.
**Reasoning:** Ties are excluded by this declared convention.
**Follow-up:** What is the half-tie score?
**Answer:** `(120+.5*20)/200=65%`.

### Q5. Does a lower PPL prove better instruction following?
**Answer:** No.
**Reasoning:** Likelihood on a reference corpus is not task/behavior evaluation.
**Follow-up:** What evaluates structured extraction?
**Answer:** Task-specific validity and field/exact-match measures with error analysis.

### Q6. Why use paired prompts to compare candidates?
**Answer:** Both see the same prompt difficulty and content.
**Reasoning:** The paired difference removes shared prompt variation.
**Follow-up:** What dependence still matters?
**Answer:** Shared users, documents, conversations or templates can require cluster-aware uncertainty.

### Q7. What must happen to invalid comparisons?
**Answer:** Record them separately with reasons under a predeclared policy.
**Reasoning:** Calling them ties can hide failures.
**Follow-up:** Why randomize order?
**Answer:** To reduce candidate-position bias.

### Q8. What can produce suspiciously low PPL?
**Answer:** Leakage, duplicates, trivial/masked targets, or an easier changed protocol.
**Reasoning:** The score follows the scoring population, not intent.
**Follow-up:** First check?
**Answer:** Provenance/dedup plus decoded token/mask examples.

### Q9. When does a paired standard error formula apply?
**Answer:** When the declared units are appropriately independent or dependence is handled.
**Reasoning:** `s_d/sqrt(n)` assumes the relevant sampling structure.
**Follow-up:** What if prompts cluster by customer?
**Answer:** Use customer as a cluster/analysis unit or an appropriate clustered method.

### Q10. What promotes a candidate with favorable PPL and win rate?
**Answer:** Passing predeclared task, critical-safety, validity, operational and lineage gates.
**Reasoning:** Aggregate metrics alone cannot establish release readiness.
**Follow-up:** What if the safety slice is tiny?
**Answer:** Collect enough valid evidence before promotion.

## 10. Quick reference

| Question | Required evidence |
|---|---|
| What does PPL mean? | NLL, eligible token count, tokenizer, mask and context/scoring protocol |
| Are PPLs comparable? | Matching tokenization, corpus, target policy, context and aggregation |
| Is corpus PPL correct? | Aggregate NLL numerator and token denominator before exponentiation |
| Did C beat B? | Same paired prompts, blinding/order control, tie policy and coverage |
| Is uncertainty valid? | Declared independent/cluster unit and method matching dependence |
| Can C be promoted? | Task/safety slices, uncertainty, evaluator validity, operations and lineage |
