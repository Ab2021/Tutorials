## Learning outcomes

Learners can define an eligible training-token denominator; compute masked token negative log-likelihood; distinguish token-, sequence- and batch-weighted reductions; inspect loss, gradient, learning-rate, throughput and data-health traces; diagnose common curve patterns without overclaiming causes; and set a checkpoint/promotion gate that requires held-out behavior in addition to training metrics.

## 1. A loss curve is an instrument reading

Training loss is a scalar summary of how the configured objective scores the examples and mask presented to the optimizer. It is not a universal measure of factuality, helpfulness, safety, task success, retrieval quality, calibration or serving performance. A lower number can be caused by easier examples, shorter sequences, changed tokenization, leakage, label-mask defects, altered reduction, changed mixture, or genuine generalization.

A useful run record makes the number interpretable. At minimum log:

- immutable model, tokenizer, template, dataset-manifest and code/config identifiers;
- global step, completed optimizer updates, tokens/examples seen, accumulation factor and distributed world size;
- objective name, label masking, reduction, ignored-index count and denominator definition;
- train loss plus held-out loss computed with a frozen matching protocol;
- learning rate, gradient norm/clipping indicator, parameter/update norm and nonfinite count;
- examples/tokens per second, data-loader wait, hardware/memory errors and checkpoint ID;
- mixture source/slice proportions, sequence length, packing/truncation statistics and duplicate/leakage controls.

Plot all metrics against **completed optimizer updates** and against **eligible target tokens** when possible. A wall-clock axis is necessary for operations but confounds throughput and outage changes with optimization progress. A “step” may mean microbatch, optimizer update or logging event; name which one.

## 2. Masked token negative log-likelihood

For a causal language model, target token `y_t` and predicted probability `p_theta(y_t | context_t)`, token negative log-likelihood is `-log p_theta(y_t | context_t)`. With an eligibility mask `m_t` of zero or one:

```text
FORMULA [LOSS-01]: L_token = - sum_t m_t * log p_theta(y_t | context_t)
                            / sum_t m_t
WHERE: m_t=1 only for target positions included in the objective; the denominator
       is the count of eligible target tokens; log is natural log.
CONSTRAINT: sum_t m_t > 0; target IDs, shifts and mask alignment are correct;
            all terms use the same tokenization/template and objective.
NUMERICAL EXAMPLE: eligible target probabilities [0.8, 0.5, 0.25] give
  L_token=-(ln .8 + ln .5 + ln .25)/3=0.7675283643 nats/token.
INTERPRETATION: this is the mean loss on three selected tokens only. It says
                nothing directly about unmasked prompt tokens or task success.
```

The mask must match the intended supervision. In a chat SFT example, user/system template tokens are often excluded while assistant response tokens are included; implementation conventions vary. An off-by-one shift can yield a plausible decreasing curve while training the wrong prediction target. Inspect one decoded, token-ID-level example with positions, labels, masks and shifted logits before long runs.

If all labels in a batch are ignored, the mean is undefined. Do not turn this into a zero loss silently; count and alert on empty-target batches. Their presence can indicate formatting, truncation, packing or data-loader defects.

## 3. Reductions change what a reported mean means

There are several valid aggregations, but they answer different questions:

| Aggregation | Formula / unit | Use | Hazard |
|---|---|---|---|
| Token-weighted | Total eligible-token NLL / total eligible tokens | Overall objective contribution | Long responses receive more weight |
| Sequence-weighted | Mean of per-sequence token means | Typical sequence behavior | Short sequences receive equal sequence weight |
| Batch mean of means | Mean logged loss values across batches | Fast dashboard signal if batches are comparable | Varying valid-token counts bias the result |
| Slice token-weighted | Token-weighted loss within declared slice | Detect mixture/domain behavior | Small slices have high uncertainty |

Example: sequence A has one eligible token with loss `1.0`; sequence B has nine eligible tokens each with loss `0.1`. Token-weighted loss is `(1+9*.1)/10=.19`, while sequence-weighted loss is `(1+.1)/2=.55`. Neither is “wrong.” They answer different questions. Store numerator and denominator as well as the displayed ratio so a dashboard can re-aggregate correctly.

Loss values across tokenizers, vocabularies, templates, target masks, reductions, dataset versions or objective definitions are not directly comparable. A standardization project should first normalize the logging contract, not rank runs by incomparable scalars.

## 4. Reading loss and optimization traces

Use the following patterns as hypotheses, not diagnoses:

| Observed pattern | Candidate explanations | First evidence to inspect | Do not conclude |
|---|---|---|---|
| Train and held-out loss fall then plateau | Capacity/optimization limit, noise floor, curriculum boundary, LR schedule | Fixed held-out protocol, LR, mixture, token count and slice losses | That more training cannot help |
| Train loss falls; held-out loss rises | Overfitting, contamination mismatch, distribution shift, evaluation bug | Data lineage/dedup, held-out preprocessing, slices and repeated checkpoint eval | That the model is generally worse without task evidence |
| Both losses jump at a step | LR/data/config/checkpoint/resume change, corrupted shard, logging bug | Run-event timeline, batch examples, gradient/overflow counters | That the optimizer alone caused it |
| Loss becomes NaN/Inf | Nonfinite inputs/logits, overflow, invalid labels, division by zero, kernel/hardware error | First nonfinite tensor, batch IDs, precision/scaler, denominator and environment logs | That lower LR is the complete fix |
| Loss oscillates widely | Small denominator, high LR, mixture/length variability, distributed aggregation error | Numerator/denominator, batch composition, LR, gradient/update norms | That variance proves instability |
| Smoothly low loss from start | Leakage, duplicated examples, trivial formatting, resume from wrong state, over-masking | Dataset overlap, decoded labels/masks, checkpoint provenance | That training succeeded |
| Throughput falls with stable loss | Data-loader, checkpointing, allocator, network or sequence-length shift | Queue/wait time, tokens/sec, lengths, I/O and hardware telemetry | That model quality changed |

Use synchronized events: data-version change, source mix change, tokenizer/template change, precision policy, gradient checkpointing, batch size, accumulation, optimizer, LR schedule, checkpoint resume and distributed topology. Without this timeline, post-hoc curve stories are weak evidence.

## 5. Gradient, update and precision signals

A gradient norm is a scale-sensitive diagnostic. It depends on parameterization, loss reduction, precision, batch composition, world size and clipping convention. Log the norm definition and whether it is measured before or after unscaling/clipping. A clipped norm alone may hide how often and how severely clipping occurred; log the unclipped value and clip fraction where feasible.

For learning rate, record the value actually applied to each parameter group, not only the nominal scheduler configuration. For Adam-like optimizers, monitor update-to-parameter ratio by named group when it is stable enough to interpret; a single global ratio can mask a dead target module or an unexpectedly trainable head.

Mixed-precision diagnostics require specific evidence: compute dtype, parameter/master dtype, loss-scale behavior, overflow/skipped-update count, nonfinite activation/gradient location, kernel/version and batch identity. FP16/BF16 labels alone do not explain a failure. Reducing loss scale or learning rate can contain an overflow, but must be followed by a root-cause check and held-out regression comparison.

## 6. Data and objective observability

Every training step should be traceable to a data manifest and aggregation of non-sensitive statistics. Useful controls include source/split counts, document/example IDs or privacy-safe hashes, duplicate rate, token-length quantiles, truncation rate, fraction of empty targets, assistant-token fraction, label vocabulary/range checks, language/domain proportions, license/policy status and time/version boundaries.

Sample decoded records at intake and after collation. For each sampled record show redacted source identity, rendered template, token count, input IDs around boundaries, labels, mask, target-token count and whether packing crosses an example boundary. This catches malformed role delimiters, unescaped special tokens, targets outside the loss mask, labels copied from prompts, accidental EOS stripping and truncation that removes every answer token.

A perfect input pipeline cannot establish data suitability. Hold out data by the deployment-relevant dependency unit—document family, user, organization, time, template, source or task—not merely random row. Record why that unit bounds leakage for the intended claim.

## 7. Checkpoint selection and promotion

Choose checkpoints using a frozen, declared protocol. A minimally defensible checkpoint table contains train/held-out token loss with numerators/denominators, task metrics, safety/critical-failure counts, length and domain slices, decoding/runtime version, cost/latency where relevant, and confidence/uncertainty approach. Repeatedly selecting on one tiny holdout contaminates it; reserve an untouched final set or use a governed evaluation rotation.

Training loss can support a **stop, inspect or compare** decision:

- **Stop and contain:** nonfinite values, integrity violation, missing lineage, empty-target burst, invalid label IDs or critical safety regression.
- **Inspect:** unexpected curve change, denominator/throughput shift, gradient anomaly or slice divergence.
- **Compare:** candidate checkpoints with the same frozen evaluation manifest and decoding policy.
- **Promote:** only after task and guardrail gates pass; never from train loss alone.

A checkpoint named “best loss” must include the metric definition, split, denominator, selection time and code/data/config IDs. The filename is not provenance.

## 8. Bounded diagnostic exercise

**Scenario:** A 10k-update SFT run reports a train-loss fall from 1.9 to 1.1. At update 6,200 held-out loss drops from 1.35 to 1.10 while the fraction of eligible assistant target tokens falls from 0.62 to 0.08 after a template deployment. Task evaluation is not yet run.

**Problem:** The drop could be better prediction, an easier target subset or a mask/template defect.

**Decision:** Freeze promotion. Compare pre/post rendered examples, token IDs, shifted labels, masks, eligible-token numerator/denominator, truncation and empty-target rate. Recompute held-out loss under the pre-change template and a fixed evaluation manifest. Segment by source/template version. Verify the training run event timeline and checkpoint state.

**Check:** If the template removed targets or changed the supervised positions, do not compare losses across the boundary and correct/restart from a known-good point. If the supervision contract is unchanged, run task and guardrail evaluation before selecting a checkpoint. No quality conclusion follows from the numbers supplied.

## 9. Interview and self-check questions

### Q1. What denominator belongs in masked token NLL?
**Answer:** The count of eligible target tokens, `sum m_t`.
**Reasoning:** Ignored prompt/padding positions do not contribute to the objective.
**Follow-up:** What if it is zero?
**Answer:** Treat the mean as undefined; count and investigate the batch.

### Q2. Calculate the average NLL for probabilities `.8`, `.5`, `.25`.
**Answer:** `0.7675283643` nats/token.
**Reasoning:** It is `-(ln .8 + ln .5 + ln .25)/3`.
**Follow-up:** Does that prove response quality?
**Answer:** No; it is an objective score under a specified tokenization/mask.

### Q3. Why can average batch loss be misleading?
**Answer:** Batch valid-token counts can differ.
**Reasoning:** An unweighted mean of batch means weights batches, not tokens.
**Follow-up:** What must be logged?
**Answer:** Numerator and eligible-token denominator.

### Q4. A held-out loss drop coincides with assistant-token fraction falling. What is the first action?
**Answer:** Audit template, labels, masks and denominators before interpreting the loss.
**Reasoning:** The objective population may have changed.
**Follow-up:** Should the run be promoted?
**Answer:** No; freeze selection pending a comparable evaluation.

### Q5. Does a falling training curve establish generalization?
**Answer:** No.
**Reasoning:** It only reports fit to the configured training objective/data.
**Follow-up:** What additional evidence is needed?
**Answer:** Frozen held-out task and guardrail evaluation with valid splits.

### Q6. What can cause a NaN loss besides an excessive learning rate?
**Answer:** Invalid data/labels, zero denominator, nonfinite activations, precision overflow, kernel or hardware faults.
**Reasoning:** NaN is a symptom, not a root cause.
**Follow-up:** What is the first evidence?
**Answer:** The first nonfinite tensor/batch plus precision and event logs.

### Q7. Why use completed optimizer updates on the plot axis?
**Answer:** Microbatches and accumulation can make “step” ambiguous.
**Reasoning:** Updates represent the optimizer's progress unit.
**Follow-up:** What other axis helps compare data exposure?
**Answer:** Eligible target tokens seen.

### Q8. Can two loss values from different tokenizers be ranked directly?
**Answer:** Generally no.
**Reasoning:** Tokenization changes the event and denominator.
**Follow-up:** What must match for a controlled comparison?
**Answer:** Tokenizer, template, labels, mask, reduction, dataset and evaluation protocol.

### Q9. Why log gradient clipping frequency?
**Answer:** A post-clip norm alone hides how often gradients were constrained.
**Reasoning:** Frequency/severity can indicate an optimization or data event.
**Follow-up:** Does clipping frequency prove a bug?
**Answer:** No; inspect it with schedule, precision, data and held-out metrics.

### Q10. What is a valid promotion criterion?
**Answer:** Predeclared task and guardrail gates on a valid frozen evaluation, plus operational and lineage checks.
**Reasoning:** Train loss is insufficient.
**Follow-up:** What if task evaluation is unavailable?
**Answer:** Do not make a task-quality promotion claim; collect required evidence.

## 10. Quick reference

| Question | Required evidence |
|---|---|
| What does this loss mean? | Objective, tokenizer/template, mask, numerator and denominator |
| Are runs comparable? | Same data/split/version, objective/reduction, tokenization and protocol |
| Did optimization fail? | First failure event, batch ID, nonfinite/precision/gradient/runtime traces |
| Did data change? | Manifest, source mix, lengths, masks, truncation and decoded samples |
| Which checkpoint is best? | Frozen held-out task/guardrail metrics, slices, uncertainty and lineage |
| Can this be promoted? | Acceptance gates and rollback; not train loss alone |
