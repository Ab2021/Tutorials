# 9.6 — Infrastructure Benchmarking and Profiling

> **Course location:** Module 28. This lesson maps to `finetuning_course/Module_09_Evaluation_Debugging/9.6_Infrastructure_Benchmarking_and_Profiling.md` in [`Train/Templates/directory.txt`](../../../Templates/directory.txt). The source body was unavailable; this is a new mapped draft.
>
> **Boundary:** A benchmark measures a declared system under a declared workload. It does not transfer to another model, driver, kernel, batch policy, context distribution or offered load without evidence.

## Learning outcomes

Learners can define TTFT, inter-token latency, end-to-end latency, throughput and capacity; construct a reproducible load profile; separate warm/cold and prefill/decode behavior; use traces to localize bottlenecks; and reject benchmark claims with mismatched workload or survivor-biased samples.

## 1. Metric contract

| Metric | Definition | Required boundary |
|---|---|---|
| TTFT | Request admission to first output token | Queue, tokenization, routing and prefill inclusion stated |
| Inter-token latency | Time between successive emitted tokens | Streaming flush/buffering policy stated |
| End-to-end latency | Declared start to declared completion | Input/output/tool/queue boundaries stated |
| Throughput | Completed output tokens or requests per elapsed time | Accepted versus offered load and token counts stated |
| Goodput | Work satisfying quality/validity/SLO contract per time | Failure/retry/invalid policy stated |
| Peak memory | Maximum declared allocator/device metric over interval | Allocation metric, model, batch/context/concurrency stated |

For `O` emitted tokens over `T` seconds, `throughput=O/T`. If 12,000 output tokens complete in 60 seconds, measured throughput is 200 tokens/s. This does not imply each request saw 200 tokens/s; queueing and batch sharing matter. Report p50/p95/p99 latency with sample count and the full offered/accepted/completed/error funnel.

## 2. Workload is the experiment

A representative harness records request arrivals, input/output length distributions, context reuse, priority/tenant classes, tool/retrieval behavior, decoding settings, concurrency, cancellation, warmup/cold-load state and admission/queue policy. Fixed tiny prompts can be a useful kernel microbenchmark but cannot establish a production SLO.

Separate prefill from decode. Longer input increases prefill and cache pressure; longer output exposes decode scheduling. Continuous batching can improve aggregate throughput while increasing a lightly loaded request's latency. Do not report a single “latency” value without a workload position and percentile.

## 3. Profiling method

1. Pin model/tokenizer/runtime/driver/kernel/hardware/configuration and capture immutable IDs.
2. Establish a correctness baseline: output validity/distribution requirements, no unexpected errors, and target quality guardrails.
3. Warm the intended code path; measure warm and cold behavior separately.
4. Collect low-overhead request metrics first, then targeted traces/profiles on a bounded sample. Profilers perturb timing.
5. Correlate queue time, CPU tokenization, device kernels, memory allocation, network/tool I/O and scheduler events by request/batch IDs.
6. Form one bottleneck hypothesis, change one factor, rerun identical workload and compare confidence/variance—not a favorable single trace.

A GPU utilization percentage is not a root cause. It may reflect useful kernels, synchronization, memory stalls, queue starvation or an inappropriate sampling interval. Trace gaps and queue state distinguish these possibilities.

## 4. Failure modes

| Symptom | Evidence | Safe response |
|---|---|---|
| High p99, good average | Per-request queue/prefill/decode distribution and tenant/length slices | Inspect tail path; avoid average-only SLO claims |
| Throughput gain, quality regression | Matched task/validity results plus decoding/runtime diff | Reject optimization until quality gate passes |
| Benchmark faster than production | Compare arrivals, lengths, cold state, retries and external calls | Rebuild representative workload or limit claim |
| GPU idle | Queue depth, CPU/I/O, scheduler and trace gaps | Localize before changing kernels/batch size |
| OOM only at load | Concurrent contexts, cache lifecycle and allocator peak trace | Size/admit against peak and cancellation behavior |
| Profiling changes result | Profile-on/off matched run | Use sampling/trace windows and report perturbation |
| p99 is unstable | Sample count, duration, outliers and workload changes | Extend matched observation; do not cherry-pick window |

## 5. Bounded capacity decision

A service must meet a 2-second p95 TTFT under an explicitly declared arrival rate and length mix. A benchmark on one warm request shows 300 ms TTFT and 200 tokens/s, but has no queueing, concurrency, cold-load or long-context data. **Decision:** no capacity claim. Run the workload harness at staged offered load, retain accepted/rejected/errors, plot p50/p95/p99 TTFT and inter-token latency by length/tenant slice, record peak memory and validate output quality. Admit traffic only below the measured safe envelope with headroom and rollback.

## 6. Interview checks

1. **What does 12,000 tokens in 60 seconds measure?** 200 aggregate output tokens/s for that interval.
2. **Why separate TTFT and ITL?** Prefill/queue and decode have different bottlenecks.
3. **Does utilization prove saturation?** No; inspect queue and traces.
4. **Why retain rejected requests?** Offered/accepted distinction defines capacity and survivorship bias.
5. **Why run quality checks after an optimization?** Faster invalid or regressed output is not goodput.
6. **What supports an SLO claim?** Representative workload, percentiles, error funnel, configuration lineage and sufficient duration.

## 7. Quick reference

| Claim | Required evidence |
|---|---|
| Faster | Matched workload/configuration, distribution and quality gate |
| More capacity | Offered/accepted/completed funnel, tail latency and peak memory |
| Bottleneck localized | Correlated request/batch traces, not utilization alone |
| Ready to deploy | SLO headroom, failure behavior, monitoring and rollback |
