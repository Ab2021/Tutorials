# 10.3 — Speculative Decoding

> **Course location:** Module 25. This lesson maps to `finetuning_course/Module_10_Inference_Deployment/10.3_Speculative_Decoding.md` in [`Train/Templates/directory.txt`](../../../Templates/directory.txt). The source body was unavailable; this is a new mapped draft.
>
> **Boundary:** Draft-token acceptance fraction is an observation, not a speedup guarantee. Correctness depends on the exact target/draft acceptance algorithm and sampling configuration.

## Learning outcomes

Learners can distinguish target and draft roles, calculate observed acceptance fraction, state the target-distribution correctness requirement, identify workload-dependent speedup limits, and validate speculative decoding before rollout.

## 1. Mechanism

A draft model proposes several future tokens. The target model evaluates the proposed prefix and accepts a prefix according to a specified algorithm; after rejection, it supplies or samples the next token under that algorithm. The objective is fewer sequential target-model decode iterations, not replacing the target model with the draft model.

Exact output-distribution preservation is algorithm- and configuration-specific. Greedy decoding, stochastic sampling, logits processors, tool/stop-token handling, penalties, temperature/top-p, RNG and numerical kernels can change behavior. Do not describe a speculative implementation as “equivalent” without a target-distribution or fixed-seed validation appropriate to its declared mode.

## 2. Acceptance arithmetic

For `D` drafted tokens and `A` accepted drafted tokens:

```text
FORMULA [SPEC-01]: observed_acceptance = A / D
WHERE: A is accepted proposal tokens and D is proposed tokens under one declared
       workload, target/draft pair, acceptance algorithm and decoding policy.
CONSTRAINT: D>0; rejected/replacement tokens, target calls, timing and request
            lengths are reported separately.
NUMERICAL EXAMPLE: D=10 and A=7 gives observed_acceptance=.7=70%.
INTERPRETATION: 70% describes this sample only. It does not equal 70% speedup.
```

Speed depends on target verification cost, draft cost, proposal length, acceptance distribution, batching, context length, kernel efficiency, queueing and request cancellation. A strong draft can still regress short requests if coordination overhead dominates. A weak draft can add work while accepting little.

## 3. Validation protocol

- Pin target and draft revisions, tokenizer, prompt/template, decoding settings, acceptance implementation, RNG/seed policy and hardware/runtime.
- Establish output correctness/equivalence tests for the declared decoding mode, including EOS, stop sequences, tool/schema constraints and edge contexts.
- Measure baseline and speculative TTFT, ITL, end-to-end latency, throughput, acceptance histogram, target/draft compute, error rate and quality metrics on matched workload slices.
- Inspect low-acceptance slices by language/domain/length/tool mode rather than reporting pooled rate only.
- Gate rollout with target-quality/safety, SLO, fallback and rollback requirements.

## 4. Failure modes

| Symptom | Check | Response |
|---|---|---|
| Acceptance high but latency unchanged | Draft/verification/queue timing breakdown | Profile matched path; adjust/disable policy for that workload |
| Output differs unexpectedly | Target/draft config, RNG, filters, stop handling and algorithm trace | Block rollout; fix equivalence contract |
| Short prompts regress | Per-length overhead and TTFT slices | Route only workloads with measured benefit |
| Long contexts OOM | Combined cache/workspace under proposal batch | Apply admission and capacity gates |
| Acceptance collapses after target update | Versioned acceptance histogram and quality slices | Revalidate draft pair; do not reuse prior benchmark |

## 5. Bounded decision

With 7 of 10 accepted proposals, report 70% observed acceptance only. **Decision:** run target-only and speculative paths on the same context/output-length/load mix. Promote only if output contract, quality/safety slices, tail latency and peak memory pass; otherwise retain standard decoding or restrict by validated route.

## 6. Interview checks

1. **What does 7/10 prove?** A 70% sample acceptance rate, not expected speedup.
2. **Why retain the target?** It verifies proposals and defines target behavior under the algorithm.
3. **What can break equivalence?** Sampling, filters, EOS/tool handling, RNG and implementation details.
4. **Why slice acceptance?** A pooled mean can hide critical workload regressions.
5. **What is fallback?** Target-only decoding with pinned compatible configuration.

## 7. Quick reference

| Claim | Required evidence |
|---|---|
| Correct | Declared algorithm/mode and target-equivalence tests |
| Faster | Matched end-to-end percentile data by workload slice |
| Safe | Quality/safety/schema gates and fallback |
| Deployable | Versioned target/draft pair, monitoring and rollback |
