# 10.1 — Inference Optimization: KV Cache and Batching

> **Course location:** Module 25. This lesson maps to `finetuning_course/Module_10_Inference_Deployment/10.1_Inference_Optimization_KV_Cache_and_Batching.md` in [`Train/Templates/directory.txt`](../../../Templates/directory.txt). The source body was unavailable; this is a new mapped draft.
>
> **Boundary:** Cache arithmetic is payload sizing under stated architecture assumptions. It excludes model weights, activations/workspace, allocator fragmentation, metadata, replicas and other processes; it is not a capacity measurement.

## Learning outcomes

Learners can calculate KV-cache payload, distinguish prefill/decode, explain continuous batching and admission control, define TTFT/ITL tradeoffs, and validate a scheduling policy under a declared workload and quality contract.

## 1. KV cache model

Autoregressive decoding retains attention keys and values for prior tokens. With `L` layers, `T` cached tokens, `H_kv` KV heads, head width `d_h`, `b` bytes/value and batch `B`:

```text
FORMULA [KV-01]: M_KV = 2 * L * T * H_kv * d_h * b * B bytes
WHERE: 2 accounts for keys and values. H_kv is KV-head count, not necessarily
       query-head count under grouped-query attention.
CONSTRAINT: all sequences use T cached tokens; representation is dense and no
            paging/compression/sharing/allocator overhead is counted.
NUMERICAL EXAMPLE: L=32, T=4096, H_kv=8, d_h=128, b=2, B=4:
 M_KV=2*32*4096*8*128*2*4=2,147,483,648 bytes = 2 GiB.
```

This count scales linearly with active tokens and batch. It changes with KV-head topology, precision and cache policy; never substitute query heads for KV heads without checking the architecture.

## 2. Prefill, decode and batching

**Prefill** processes the input context and populates KV state. **Decode** emits one or a small number of next tokens per active sequence, repeatedly reading growing cache. They have different work shape and often different bottlenecks. A short prompt/long generation workload does not represent a long prompt/short answer workload.

Static batching waits for a batch boundary. Continuous batching admits/finishes requests dynamically and can improve utilization, but requires fair scheduling, bounded queueing, cancellation cleanup and per-request accounting. Chunked prefill can protect decode latency by limiting how much prompt work enters a scheduling cycle. These are policies to measure, not universal improvements.

## 3. Admission and isolation

Admit against explicit budgets for KV tokens, sequence slots, context/generation limits, queue age, device headroom, tenant/priority policy and cancellation. A request accepted before reserving its cache budget can create an avoidable OOM or tail-latency incident. Evicting or compressing state must preserve the model/runtime's documented semantics; silently truncating history changes behavior.

Cache keys and request state must be scoped to model/tokenizer/template/adapter/tenant authorization when prefixes or adapters affect generation. Cross-tenant reuse is not an optimization absent explicit authorization and equivalence.

## 4. Failure modes

| Symptom | Check | Response |
|---|---|---|
| OOM only at concurrency | Active-token/sequence accounting versus KV payload and peak allocator trace | Tighten admission or increase provisioned headroom; test cancellation cleanup |
| Good throughput, bad TTFT | Queue time and prefill/decode share by length/priority | Bound queue/prefill chunks; evaluate SLO tradeoff |
| Long request starves short requests | Per-request queue age and scheduler decisions | Add declared fairness/priority policy; test adversarial mix |
| Cache reuse changes outputs | Key/version/position/prefix and tenant scope trace | Disable unsafe reuse; correct key and run equivalence tests |
| Memory estimate misses reality | Weights/workspace/metadata/fragmentation omitted | Measure target runtime peak; keep payload as lower-bound component |

## 5. Bounded SLO exercise

A service has the illustrative 2 GiB cache payload above before overhead. **Decision:** do not configure a GPU with exactly 2 GiB free. Inventory model/workspace/allocator headroom and measure peak under the target context/arrival mix. Set token/slot admission so accepted work fits measured headroom; then compare static, continuous and chunked-prefill policies using p50/p95/p99 TTFT, ITL, errors, cancellation and output-quality checks.

## 6. Interview checks

1. **Why is GQA relevant?** KV cache scales with KV heads, not query heads.
2. **What is 2 GiB here?** Raw cache payload under declared assumptions, not complete device memory.
3. **Why split TTFT and ITL?** Prefill/queue and decode have different tradeoffs.
4. **Does continuous batching guarantee lower latency?** No; it changes utilization and scheduling tradeoffs.
5. **What promotes a policy?** Measured SLO/quality/isolation gates under the actual workload.
