## Learning outcomes

Learners can classify major training memory components; estimate parameter, gradient and optimizer-state storage with explicit dtype assumptions; distinguish allocated, reserved and peak memory; identify activation, temporary and communication buffers outside a simple state estimate; and build a measured memory budget before selecting a device or optimization.

## 1. Memory is more than model weights

A training process may hold several memory categories at once:

1. **Parameters/weights:** model tensors used in forward and backward passes.
2. **Gradients:** derivative tensors accumulated for updates.
3. **Optimizer state:** moments, master weights, step counters, or other update state.
4. **Activations:** intermediate values retained for backward computation.
5. **Temporary workspaces:** kernels, attention, matrix multiplication, fused operators, and casts.
6. **Communication buffers:** collective, staging, send/receive, and gradient buckets.
7. **Input/batch tensors:** token IDs, masks, labels, embeddings, and preprocessing outputs resident on device.
8. **Runtime and allocator overhead:** CUDA context, library allocations, caching allocator reserve, fragmentation, and graph capture.

A parameter-only estimate is a lower bound on total training memory under most ordinary setups, not a fit test. Peak memory depends on allocation overlap and schedule, so summing every theoretical tensor may overestimate or underestimate actual peak depending on lifetimes and reuse.

## 2. Define byte and parameter conventions

Let `P` be the number of parameters, and let each state component use a specified number of bytes per parameter. A first-order persistent-state estimate is:

```text
M_state = P * (b_weight + b_gradient + b_optimizer + b_master + ...)
```

This formula assumes each listed tensor has one element per parameter and stays resident simultaneously. Real optimizers may keep multiple moments, use different precision for gradients or states, shard state across devices, or omit some tensors. Some parameters can be frozen, excluded from decay, or stored in a different format.

Use byte units explicitly:

- `1 GB = 10^9 bytes` (decimal);
- `1 GiB = 2^30 bytes` (binary).

GPU product documentation often reports capacity in bytes or GiB-like units; do not compare decimal estimates to a binary capacity without conversion. Keep headroom for inputs, activations, workspace, runtime, and peak variance.

## 3. Worked persistent-state estimate

Illustrative assumptions: `P=1,000,000,000` trainable parameters; weights use 2 bytes/parameter; gradients use 2 bytes/parameter; optimizer keeps two 4-byte moments per parameter. No master copy is included.

```text
FORMULA [MEM-01]: M_state = P * (b_w + b_g + n_m*b_m)
WHERE: P = trainable parameter count; b_w, b_g = bytes/parameter for weights and gradients;
       n_m = moment tensors/parameter; b_m = bytes/moment element.
CONSTRAINT: excludes master weights, activations, temporaries, buffers, runtime and allocator overhead; all listed tensors assumed resident.
NUMERICAL EXAMPLE: P=1e9; b_w=2; b_g=2; n_m=2; b_m=4.
                   M_state=1e9*(2+2+2*4)=12e9 bytes = 12 GB ≈ 11.18 GiB.
INTERPRETATION: this is only the modeled persistent state; it is not the total training footprint or evidence the job fits a 12-GB device.
```

Independent check by component: weights 2 GB; gradients 2 GB; first moment 4 GB; second moment 4 GB; total 12 GB decimal. At 1,000,000,000 parameters, an optional 4-byte master copy adds 4 GB, giving 16 GB before other allocations. Actual optimizer state depends on implementation and parameter groups.

## 4. Parameters, gradients, and optimizer states

A model's total parameter count is not necessarily the trainable count. Freezing a base model can eliminate or reduce gradient and optimizer state for those weights, while still requiring the frozen weights in memory for forward/backward through later trainable layers. Adapter tuning adds adapter parameters and states but still loads the base weights unless the system offloads or quantizes them.

Mixed precision does not imply one universal state layout. A common conceptual configuration can store low-precision forward weights, low-precision gradients, and higher-precision optimizer moments; another may keep master weights, shard optimizer state, use 8-bit states, or accumulate gradients in a wider type. Verify the actual framework and optimizer implementation.

Memory estimates should distinguish:

- all model parameters versus trainable parameters;
- weight dtype versus gradient accumulation dtype;
- optimizer tensors and their precision;
- replicated versus sharded state;
- persistent tensors versus temporary copies during casts or updates.

Changing the optimizer changes persistent memory. Reducing optimizer state may lower memory but can alter optimization behavior or add dequantization/metadata overhead; measure both memory and quality/stability.

## 5. Activations and sequence/batch effects

Activations are intermediate results from forward computation retained for backward. Their memory depends on batch size, sequence length, hidden widths, layer count, attention implementation, dtype, checkpointing, and which tensors are saved or recomputed.

For a tensor of shape `[B,T,d]` with `b` bytes per element, storage is `B*T*d*b` bytes. This is only one tensor; a transformer block may retain multiple tensors per layer. Increasing batch or sequence length often increases activation memory approximately linearly for many tensors. Attention intermediates can add sequence-length-dependent costs; the exact amount depends on whether the implementation materializes attention scores/probabilities or uses a memory-efficient kernel.

Do not use a single “activation bytes per parameter” factor without validating the architecture, sequence length and implementation. Measure peak memory across the target workload and sequence distribution.

## 6. Temporary workspaces and communication buffers

Kernels may allocate temporary workspaces for matrix multiplication, attention, optimizer updates, activation transforms, or fused operations. Distributed training libraries may maintain gradient buckets or collective buffers. Temporary allocations can overlap with activations and optimizer updates, creating a peak higher than the sum of steady-state categories.

Kernel selection and workspace sizes may change with shape, precision, library version and hardware. A profile at short sequence length does not establish memory at maximum sequence length. Include startup, graph capture, evaluation, checkpoint save and optimizer-step peaks if they occur in production.

## 7. Allocated, reserved, and peak memory

Framework memory reports can distinguish live/allocated tensors from memory reserved by a caching allocator. Reserved memory may be reusable by the framework but unavailable to unrelated processes. Device-level “used” memory can also include contexts, other processes and allocations outside the framework allocator.

Track at least:

- current and peak allocated/live framework memory;
- current and peak reserved memory;
- device-wide used and free memory;
- allocation failures and fragmentation indicators;
- process, rank, step and workload shape associated with the peak.

A job can fail despite a low steady-state snapshot if a transient allocation spikes during an optimizer step or checkpoint. Conversely, high reserved memory does not always equal active tensors. Diagnose with a synchronized memory timeline and allocator snapshots rather than assuming one counter tells the whole story.

## 8. Training versus inference memory

Inference often needs weights, input/temporary tensors, and a key/value cache for autoregressive generation. Training additionally needs gradients, optimizer state, and activations or recomputation support. A model that fits for inference may not fit for full-parameter training.

A parameter-efficient method can reduce trainable gradients and optimizer state, but it does not automatically remove base-weight memory or activation memory. Longer context can dominate activation and attention memory even when adapter parameter count is small.

State whether a budget is for training, inference, checkpoint loading, or peak end-to-end operation. Do not apply inference memory rules to full training without a component-level accounting.

## 9. Build a memory budget

A useful budget separates:

| Category | Estimate source | Measurement needed |
|---|---|---|
| Weights | Parameter count × dtype bytes, adjusted for sharding/quantization | Loaded checkpoint residency by rank |
| Gradients | Trainable parameter count × accumulation dtype | Peak after backward and during reduction |
| Optimizer state | Optimizer tensor inventory × dtype | Peak at optimizer step and after update |
| Activations | Shapes/lifetimes/checkpoint policy | Peak over batch/sequence/workload sweep |
| Temporary workspaces | Kernel/library behavior | Timeline under exact shapes/precision |
| Communication | Bucket sizes and parallel strategy | Peak buffers and collectives under load |
| Input/labels | Batch/sequence/mask shapes | Peak collation and device transfer |
| Runtime/allocator | Framework, CUDA, process and cache overhead | Device-level versus framework counters |
| Headroom | Operational safety margin | Concurrent workloads and worst-case sequence |

Record assumptions and uncertainties, then validate with a representative smoke run. Include worst-case sequence lengths and the largest planned batch. Leave capacity for checkpointing or evaluation peaks if they share the device.

## 10. OOM diagnosis

When an out-of-memory error occurs, capture the failure stage, allocation size, tensor shapes, sequence length, batch/accumulation, precision, optimizer step, device free memory, allocated/reserved counters, and concurrent process state. The cause may be an expected workload peak, an unexpected shape, fragmentation, a leak, a different kernel workspace, or another process.

A controlled reduction in microbatch is a useful diagnosis, but it also changes effective batch unless accumulation or another mechanism compensates. Changing precision, optimizer, checkpointing, sequence length, or model freezing changes the experiment and can affect quality or numerical behavior. State the tradeoff and validate the relevant behavior after the change.

Useful troubleshooting order:

1. Reproduce with the same code/config and capture exact failing step/shape.
2. Compare actual tensor/model dimensions and parameter count to budget assumptions.
3. Separate live allocated memory from allocator reserve and device-wide use.
4. Identify whether failure occurs in forward, backward, optimizer, communication, evaluation or checkpoint.
5. Profile activation/workspace lifetimes and competing processes.
6. Apply a bounded change to the measured cause and rerun the exact path.

Do not label every OOM “activation memory” or free cache as the universal solution. If the live working set exceeds capacity, cache clearing alone cannot make the workload fit.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| OOM before first forward pass | Weights/checkpoint plus runtime exceed capacity; duplicated model load | Measure load peak and per-rank resident tensors | Reduce/partition actual state or use a compatible representation; remeasure |
| OOM during backward | Activations, gradients, attention intermediates or workspace | Capture step timeline by shape and layer | Reduce measured activation/workspace driver with controlled tradeoff |
| OOM at optimizer step | Moments, master weights, update temporaries or gradient buckets | Compare pre/post-step memory and optimizer inventory | Correct state estimate, shard/offload or select optimizer with stability tests |
| Framework allocated low but device full | Other process, context, external allocation or driver use | Compare framework counters with device-level process accounting | Resolve ownership/concurrency or external allocator; do not blame model estimate alone |
| High reserved but no active tensor growth | Caching allocator reserve or fragmentation | Inspect allocator snapshot and allocated/reserved difference | Use framework-appropriate allocator diagnosis; avoid destructive cache-clearing folklore |
| Fits at short sequences, fails at long | Activations/attention/workspace scale with sequence length | Sweep lengths and capture peak curve | Budget for maximum supported workload or define explicit limits |
| Adapter tuning barely reduces footprint | Frozen base weights and activations still resident | Split trainable state from total model/activation memory | Choose method based on dominant component; do not infer from adapter parameter count |
| OOM disappears after reducing microbatch, quality changes | Effective batch/update semantics changed | Recalculate global sequences/tokens/update and compare gradients | Restore intended effective batch or explicitly validate new training regime |

## 12. Interview and self-check questions

### Q1. What does the 12-GB estimate include?
**Answer:** For the stated example, 2-byte weights, 2-byte gradients, and two 4-byte optimizer moments for one billion parameters.
**Reasoning:** `1e9*(2+2+8)=12e9` bytes.
**Follow-up:** Is this enough for training on a 12-GB card?
**Answer:** No; it excludes activations, temporaries, runtime, communication and allocator overhead.

### Q2. How many GiB is 12 decimal GB?
**Answer:** About 11.18 GiB.
**Reasoning:** `12e9/2^30≈11.18`.
**Follow-up:** Why specify units?
**Answer:** Hardware capacity and estimates can use different decimal/binary conventions.

### Q3. Does freezing the base model remove its weight memory?
**Answer:** Not usually; frozen weights still need to be loaded for forward computation.
**Reasoning:** Freezing removes parameter updates but not necessarily inference/forward residency.
**Follow-up:** Which states may decrease?
**Answer:** Gradients and optimizer state for frozen parameters, subject to implementation.

### Q4. Why can an inference-fit model fail during training?
**Answer:** Training adds gradients, optimizer state, activations, workspaces and communication buffers.
**Reasoning:** Inference and training have different live-state requirements.
**Follow-up:** Does parameter-efficient tuning guarantee fit?
**Answer:** No; base weights and activations can still dominate.

### Q5. What is the difference between allocated and reserved memory?
**Answer:** Allocated usually reflects live framework tensors; reserved includes memory held by a caching allocator for reuse.
**Reasoning:** Reserved can exceed live allocation.
**Follow-up:** Can device-wide usage exceed both?
**Answer:** Yes; contexts and other processes or non-framework allocations may consume memory.

### Q6. Why can sequence length change peak memory?
**Answer:** It increases activation sizes and may expand attention intermediates/workspaces.
**Reasoning:** Tensor shapes and lifetimes depend on `T`.
**Follow-up:** How should it be tested?
**Answer:** Sweep representative and maximum sequence lengths with the exact kernel/precision path.

### Q7. What is the memory effect of Adam-style moments?
**Answer:** Each moment adds state memory proportional to parameter count and its dtype.
**Reasoning:** The example includes two 4-byte moments, adding 8 bytes per parameter.
**Follow-up:** Do all optimizers use this exact layout?
**Answer:** No; inspect the implementation and state precision.

### Q8. Why does a lower microbatch change more than memory?
**Answer:** It may change effective batch, optimizer update frequency, gradient noise and schedule progress.
**Reasoning:** Accumulation and global reduction determine update semantics.
**Follow-up:** What must be recalculated?
**Answer:** Sequences/tokens per update, loss-bearing count and learning-rate schedule unit.

### Q9. Why is clearing allocator cache not a universal OOM fix?
**Answer:** It cannot eliminate a live working set larger than device capacity.
**Reasoning:** Cache reserve and active tensor memory are distinct.
**Follow-up:** What evidence is useful?
**Answer:** Allocated/reserved/device counters and a synchronized memory timeline at failure.

### Q10. What should a training memory report include?
**Answer:** State dtypes/counts, activations, workspaces, buffers, runtime/allocator, measured peaks, workload shape and headroom.
**Reasoning:** A single parameter-only value omits major components.
**Follow-up:** What is minimum validation?
**Answer:** Run the exact target path at representative and worst-case shapes and observe peak memory.
