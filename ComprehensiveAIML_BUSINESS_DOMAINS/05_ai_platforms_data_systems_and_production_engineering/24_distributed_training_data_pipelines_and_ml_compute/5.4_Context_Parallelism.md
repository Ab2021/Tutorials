## Learning outcomes

Learners can explain sequence/context sharding across ranks; distinguish context parallelism from tensor and data parallelism; reason about causal-attention access to remote key/value states; estimate per-rank sequence ownership; identify communication and memory tradeoffs; and validate causal masks, position continuity, loss counting and distributed outputs.

## 1. What context parallelism partitions

Context parallelism (CP) partitions sequence positions across a group of devices. Each rank owns a subset of tokens for the same logical examples. This can reduce per-rank storage of sequence-dependent activations and attention work for long contexts, while requiring communication so each query can use the key/value context defined by the model's attention pattern.

Unlike data parallelism, CP ranks do not necessarily process independent examples. Unlike tensor parallelism, which partitions hidden/weight dimensions within layers, CP partitions the sequence/context axis. A training configuration can combine CP with TP and DP; each rank's membership and effective batch depend on group construction.

Partitioning token positions does not change the logical sequence. Global position IDs, causal ordering, attention masks and loss targets must be preserved across rank boundaries.

## 2. Sequence ownership and shapes

Let sequence length be `T` and context-parallel degree `p_c`. Under equal contiguous partitioning, each rank owns `T/p_c` positions if `T` is divisible by `p_c`. For batch `B`, hidden width `d`, and element size `b` bytes, one local hidden-state tensor has approximate storage:

```text
M_local_hidden ≈ B * (T/p_c) * d * b
```

This is a per-tensor estimate, not total activation memory. Multiple layers/tensors, temporary communication buffers, padding, checkpointing and attention algorithm affect the footprint.

Illustrative example: `B=2`, `T=8,192`, `p_c=4` gives 2,048 sequence positions per rank. For `d=1,024` and 2-byte values, one local hidden tensor is `2*2,048*1,024*2=8,388,608` bytes, or 8 MiB (8.39 MB decimal), excluding all other tensors.

If `T` is not divisible by `p_c`, the implementation may pad, unevenly partition or reject the configuration. Padding affects attention and loss masks; never count padded positions as real targets unless the objective explicitly says otherwise.

## 3. Attention requires global context semantics

For standard causal self-attention, a query at position `i` may attend to valid key positions up to `i` (subject to additional masks). If query positions are split across ranks, the owner rank needs key/value information for the allowed context, potentially including positions owned by other ranks.

Implementations may circulate KV blocks in a ring, gather KV tensors, use hierarchical communication, or employ another attention algorithm. A ring-based method can stream remote KV blocks while accumulating attention without materializing the full global score matrix on every rank. Exact memory, communication and numerical behavior are implementation-specific.

For non-causal attention, every query may need keys from all sequence partitions. For sliding-window or block-sparse patterns, only a subset may be required. The communication pattern follows the attention mask; a CP strategy that ignores the mask can produce wrong outputs or unnecessary traffic.

CP does not automatically reduce total attention computation. It distributes work and may lower per-rank activation/score residency, while introducing inter-rank data movement and synchronization.

## 4. Causal boundaries, positions, and masks

When a sequence is partitioned, local index zero on a rank may correspond to a nonzero global token position. Position IDs, rotary embeddings, relative position calculations and causal masks must use the intended global sequence coordinates. Resetting positions at each rank boundary changes the model's input semantics unless the architecture explicitly uses local positions.

Boundary validation should test:

- a query at the first token of each shard;
- a query near shard end;
- cross-shard causal visibility;
- padding at beginning/end and uneven shard lengths;
- sequence packing boundaries and independent-example masks;
- global position IDs across all ranks;
- loss labels assigned to each token exactly once.

Use unique sentinel values in each sequence segment to verify which keys are visible to queries. Confirm that future tokens never affect causal outputs and that allowed earlier tokens across ranks do.

## 5. Per-rank sequence example

For `T=8,192` and `p_c=4`, each equally partitioned rank owns `8,192/4=2,048` positions. Across the four ranks, the logical sequence still contains 8,192 positions; CP has not created four independent copies of the example or multiplied the data batch by four.

If each position has a loss-bearing next-token target, the global objective must include each valid target once across the ranks, with correct cross-boundary next-token alignment. The first position or final position may have special handling according to the sequence boundary and trainer convention. Padding, ignored prompt tokens and packed-example boundaries change the valid target count.

The sum of local valid targets should match the global reference count. If a target token is omitted or duplicated at a shard boundary, loss and gradient differ even if local tensor shapes appear correct.

## 6. Communication and memory tradeoffs

Context parallelism exchanges activations, KV blocks or partial attention state among ranks. Communication volume and latency depend on sequence length, batch, heads, head dimension, dtype, attention pattern, algorithm and topology. A high-bandwidth intra-node fabric may support a different design than a cross-node network.

Potential benefits:

- lower per-rank sequence-dependent activation storage;
- ability to process contexts that exceed one rank's memory;
- reduced local attention-score residency in implementations that stream blocks.

Potential costs:

- KV/activation communication and synchronization;
- extra buffers and scheduling state;
- longer exposed latency if communication is not overlapped;
- complexity in masks, position IDs, checkpointing and failure handling;
- reduced effective data-parallel degree at fixed world size.

A CP memory estimate must include local activations plus communication buffers and any gathered/staged tensors. Do not assume per-rank peak falls exactly by `p_c`; some state is replicated and some workspaces can scale differently.

## 7. Combine with tensor, pipeline, and data parallelism

A hybrid job can have degrees `D_p`, `T_p`, `P_p`, and `C_p` for data, tensor, pipeline and context dimensions. The product equals world size only when these are independent, non-overlapping factors and no additional replication or expert dimension exists. In a more complex topology, group membership can reuse or overlap axes.

For a simple independent product of 32 devices with `T_p=2`, `P_p=4`, `C_p=2`, the remaining data degree is `D_p=32/(2*4*2)=2`. This is an arithmetic illustration, not a recommended topology. The global data batch grows by the data-parallel degree, not by all devices.

Draw global-rank coordinates and process groups. Validate every collective group from runtime logs. A correct product with incorrect rank ordering can still produce deadlocks or cross-wire data.

## 8. When to use context parallelism

Use CP when long sequence/context activations or attention state are the measured memory bottleneck and the system has an efficient communication path for the required attention algorithm. Compare against alternatives such as smaller microbatch, activation checkpointing, memory-efficient attention, sequence packing, or a different context limit.

The right choice depends on whether the constraint is per-rank activation memory, attention compute, optimizer state, total latency, or throughput. CP will not fix a weight/optimizer-state OOM unless combined with a strategy that shards that state.

Benchmark quality and throughput at target context lengths. Include short and long sequences because communication and compute balance can differ substantially. Report effective data batch and per-rank memory for the full hybrid configuration.

## 9. Correctness validation

Before large-scale runs, compare CP output and gradients to a single-device or non-CP reference for a small sequence that fits. Test causal and non-causal masks separately if both are supported. Include shard-boundary positions, padding, packed samples, non-divisible lengths, position embeddings, dropout behavior, and loss normalization.

Core invariants:

- concatenating local token shards reconstructs the original logical sequence in the correct order;
- every valid global position is owned exactly once unless explicitly replicated;
- attention visibility matches the global mask, including cross-shard context;
- positional IDs follow the global sequence contract;
- labels and target counts match the non-CP reference;
- output/gradient differences remain within a defined numerical tolerance;
- checkpoint save/resume preserves shard placement or performs an explicit validated reshard.

For stochastic attention/dropout, compare deterministic settings or use statistical tolerances appropriate to the test. Do not require bitwise equality if communication/reduction order differs, but define an acceptable error bound.

## 10. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| CP output differs only near shard boundary | Wrong causal mask, global position IDs or KV block ordering | Sentinel test across every rank boundary | Correct boundary mapping and add parity tests per shard edge |
| Memory does not fall as expected | Replicated activations, gathered KV, workspaces or buffer overlap | Capture per-rank memory by layer and communication phase | Identify live component; tune the measured algorithm/window or use another method |
| Longer context causes throughput collapse | Communication volume/latency, poor overlap, imbalance | Profile compute, KV transfer and exposed waits by rank | Tune topology/algorithm or constrain supported context with explicit evaluation |
| Loss count changes with CP degree | Duplicate/missing boundary targets or padding counted | Compare global and summed local target IDs/counts | Fix shard labels/masks; verify against non-CP target set |
| Causal model uses future token | Incorrect global offset or mask orientation | Perturb future shard tokens and compare earlier outputs | Repair mask and test future-invariance across every rank |
| Rank deadlock | Inconsistent group membership or conditional communication call | Log global ranks, CP coordinates and collective order | Fix group/rank mapping and run small all-rank synchronization test |
| Hybrid effective batch is wrong | CP degree counted as data replicas | Recompute independent process-group dimensions and local batch | Correct batch/scheduler accounting before comparing runs |
| Resume changes context outputs | Shard order/position state or checkpoint reshard mismatch | Compare reconstructed sequence/positions and fixed-input logits | Fix mapping and validate checkpoint round-trip |

## 11. Interview and self-check questions

### Q1. What does context parallelism partition?
**Answer:** Sequence/context positions across a cooperating group of ranks.
**Reasoning:** Each rank handles part of the same logical sequence.
**Follow-up:** Does it multiply data batch?
**Answer:** No, not by itself.

### Q2. For length 8,192 over four equal CP ranks, how many positions per rank?
**Answer:** 2,048.
**Reasoning:** `8,192/4=2,048`.
**Follow-up:** How many positions are in the global sequence?
**Answer:** Still 8,192.

### Q3. Why does causal attention need cross-rank communication?
**Answer:** Queries on one rank may need keys/values from earlier positions on other ranks.
**Reasoning:** Causal context spans shard boundaries.
**Follow-up:** What must not be visible?
**Answer:** Future positions and any content excluded by the declared attention mask.

### Q4. Does CP reduce total attention FLOPs?
**Answer:** Not necessarily; it distributes the computation and may reduce per-rank memory, while adding communication.
**Reasoning:** The logical attention relationships remain.
**Follow-up:** What determines speed?
**Answer:** Algorithm, topology, sequence shape, communication overlap and measured utilization.

### Q5. Why preserve global positions across shards?
**Answer:** Position encodings and relative positions depend on the sequence coordinate.
**Reasoning:** Resetting local index changes model inputs.
**Follow-up:** What tests this?
**Answer:** Compare position IDs and outputs at shard boundaries to a global reference.

### Q6. Does per-rank memory divide exactly by CP degree?
**Answer:** No.
**Reasoning:** Some state is replicated; gathered KV, buffers, workspaces and layer lifetimes remain.
**Follow-up:** What validates the budget?
**Answer:** Measured peak timelines at target lengths and exact implementation.

### Q7. In a 32-device independent layout with TP2, PP4, CP2, what is DP degree?
**Answer:** 2.
**Reasoning:** `32/(2*4*2)=2` under the stated independent-factor assumption.
**Follow-up:** Does the arithmetic prove correct groups?
**Answer:** No; inspect runtime membership and rank coordinates.

### Q8. How can CP change the training loss without changing model weights?
**Answer:** Boundary labels, masks, positions, or target counts can be wrong after sharding.
**Reasoning:** Distributed sequence layout changes how data is presented to the loss.
**Follow-up:** What should match a reference?
**Answer:** Global target IDs/counts, outputs and gradients within tolerance.

### Q9. Which problem will CP not solve by itself?
**Answer:** A weight/optimizer-state memory bottleneck.
**Reasoning:** CP shards sequence positions, not necessarily persistent parameter state.
**Follow-up:** Which strategy might address that?
**Answer:** ZeRO/FSDP or another parameter/optimizer-state sharding approach, depending on the measured bottleneck.

### Q10. What should a CP benchmark report?
**Answer:** Target context length, per-rank memory, throughput/latency, communication, global batch, quality, and topology.
**Reasoning:** Memory reduction alone does not establish a useful configuration.
**Follow-up:** Why include short sequences?
**Answer:** Communication overhead may dominate when compute per sequence is small.
