## Learning outcomes

Learners can explain how experts are placed across expert-parallel (EP) ranks; trace token routing and combine across devices; distinguish expert count from EP degree and data-parallel degree; estimate assignment load and per-rank expert placement; identify all-to-all, skew, capacity and rank-order risks; and validate distributed MoE results against a local reference.

## 1. Expert parallelism in a routed layer

Expert parallelism distributes expert networks across devices. A router selects experts for each token; tokens are dispatched to the ranks hosting those experts; each expert processes its assigned tokens; outputs are returned and combined according to the routing weights.

A simplified path is:

```text
token hidden states on source ranks
          ↓ router selects expert IDs
bucket assignments by destination EP rank
          ↓ all-to-all / dispatch
expert ranks compute local expert FFNs
          ↓ return outputs and token IDs
source ranks combine selected expert outputs
```

EP is most commonly used for MoE layers with many experts, but exact implementations vary in placement, routing, capacity, communication backend, shared experts and whether outputs are combined on source or destination ranks. “Top-k” does not define the distributed dispatch contract.

## 2. Expert count, EP degree, and replicas

Let `E` be total distinct experts and `D_e` the expert-parallel group size. If experts are evenly assigned and `E` is divisible by `D_e`, each EP rank owns `E/D_e` experts. This says nothing about how many data-parallel replicas of the expert bank exist, whether experts are replicated, or whether tensor parallelism further shards each expert.

Illustrative mapping: `E=8`, `D_e=4` yields two experts per EP rank under equal static placement. If 128 tokens use top-2 routing, there are `128*2=256` assignments globally. Under perfectly even routing, each expert receives 32 assignments and each EP rank receives 64 assignments. This is only a balanced average; actual router skew creates unequal loads.

EP degree does not itself multiply independent training examples. If EP ranks cooperate to host experts for the same routed tokens, they are part of the same logical example batch. Data-parallel degree controls independent data replicas in a simple hybrid layout.

## 3. Routing to destination ranks

The router emits expert IDs and weights per token. The dispatch layer maps each expert ID to an EP rank and local expert slot. Tokens may be sent to one or several experts; padding, capacity overflow, second-choice routing or dropping policy changes which assignments actually execute.

For each token, preserve a stable identifier containing at minimum the source rank/local batch position and original sequence position. For each assignment, preserve selected expert, routing weight, destination rank and local ordering. After expert computation, the combine path must restore the correct token order and apply the intended weights exactly once.

A wrong local-expert map can route a token to a valid but incorrect expert and produce plausible tensor shapes. Verify mapping tables and expert parameter identities, not only collective completion.

## 4. All-to-all communication

A common EP dispatch uses all-to-all communication: each source rank partitions its token assignments by destination rank; every rank sends/receives variable-sized buckets; expert ranks compute; a return communication sends outputs to their source locations. Some implementations fuse, overlap, compress, pad or use hierarchical collectives.

Communication depends on token count, top-k, hidden width, activation dtype, expert placement, capacity padding, routing skew and network topology. If every token has `k` assignments and hidden width `d` with `b` bytes/value, a simple unpadded forward dispatch payload estimate is proportional to `T*k*d*b` bytes globally, before protocol overhead and return traffic. Actual network bytes may be larger due to padding and may be distributed differently across links/ranks.

Latency depends on message count, synchronization, all-to-all implementation and topology. Small workloads can be latency-bound; a few hot destinations can cause stragglers even when total bytes are moderate. Profile per-rank send/receive bytes, time, queueing, expert compute and idle intervals.

## 5. Placement and load balance

Expert placement determines which EP rank hosts each expert. A placement can be static and contiguous or topology-aware; tensor-parallel sharding can place one expert across multiple devices. The mapping should account for network locality and balance expert compute/memory.

Routing load is dynamic. Average assignments per expert are `T*k/E`, but the maximum determines capacity and straggler risk. Aggregate balance across the cluster can hide a rank that hosts multiple hot experts. Track both per-expert and per-rank loads, capacity utilization, token overflow/drop rate, and all-to-all tail latency.

Balancing losses and routing constraints can help utilization but can change expert specialization and task quality. Measure the tradeoff instead of optimizing utilization alone.

## 6. Capacity and overflow in distributed execution

Capacity limits may be defined per expert per device, per EP group, per batch, or using a padded static bucket. Capacity policy affects buffer size, communication volume and which tokens are processed. An expert overloaded on one rank can stall that rank while other ranks wait at collectives.

Illustrative capacity: `T=128`, `k=2`, `E=8`, capacity factor `1.25`, and a simple per-expert formula gives average 32 assignments and capacity 40 per expert. An EP group with four ranks and two experts/rank has nominal aggregate capacity 320 assignment slots. This does not guarantee no overflow: skew can overload one expert even when aggregate capacity exceeds 256 assignments.

The framework may drop excess assignments, reroute to another expert, pad buckets, or use a different capacity rule. Record the exact behavior and test with deliberately skewed routing. Do not silently infer semantics from the capacity factor name.

## 7. Memory and computation

Expert weights are distributed across EP ranks if each expert is placed once per group; total expert parameters remain the same, while per-rank resident expert weight storage can decrease roughly with the number of EP ranks under equal placement. Replication, tensor sharding, shared experts, router parameters, non-expert layers and temporary buffers change this estimate.

For each token, compute runs only for selected experts under sparse routing, but communication and expert utilization affect throughput. If EP ranks have unequal token loads, some devices become stragglers. If a token is sent to multiple experts, all selected outputs and assignments must be processed or handled under the stated overflow policy.

Memory accounting should separate router, local expert weights, optimizer/gradient state, routed activations, padded capacity buffers, all-to-all staging buffers, non-expert layers and runtime. A lower per-rank parameter count does not guarantee a lower peak memory when padded buckets or overlapping buffers dominate.

## 8. Combine EP with other parallel dimensions

A model can combine EP with TP, PP, CP, DP, and state sharding. Dimensions can be independent factors, nested subgroups, or overlapping groups. Do not multiply all degrees without a rank-coordinate definition.

For a simple 32-device layout with `TP=2`, `PP=2`, `EP=4`, the remaining `DP=2` only if these factors are independent and each device belongs to one coordinate in the Cartesian product: `2*2*4*2=32`. In this example, EP ranks distribute experts for the same routed batch; DP degree 2 supplies separate data replicas. Adding CP would require a new topology and rank-product decision, not an assumed extra multiplier.

Verify that router/dispatch communication uses the intended EP group and not the entire world or TP group. Record global rank, EP rank, local experts, DP replica, pipeline stage and tensor shard.

## 9. Correctness and performance validation

Build a tiny reference with distinguishable expert functions and explicit token IDs. Compare router selection, destination mapping, expert outputs, return ordering and weighted combination to a single-process implementation. Include top-k ties, multiple assignments, empty expert bins, uneven loads, capacity overflow, padding, and rank-boundary cases.

For performance, measure full training/inference step at target batch, sequence, expert count, routing distribution and topology. Separate router, bucketization, dispatch, expert compute, return, combine and synchronization. Report per-rank and tail latency, not only aggregate tokens/sec.

Checkpoint tests should preserve expert identity and placement metadata. Resharding or changing EP degree needs an explicit, tested conversion. A model that loads but maps expert IDs differently is not compatible.

## 10. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| One EP rank is a persistent straggler | Hot experts co-located; skewed router; uneven expert sizes | Per-expert/per-rank token and compute histograms | Rebalance placement or routing under measured quality/communication constraints |
| All-to-all dominates step | Poor topology; many small messages; padding; low overlap | Per-rank communication bytes/time and exposed wait | Tune placement/backend/buckets or reject EP for this workload |
| Outputs correspond to wrong tokens | Dispatch permutation or inverse-map corruption | Unique token IDs through send/compute/return | Fix mapping and make reference parity a blocking test |
| Some experts never receive tokens | Router collapse; map/config error; masks or capacity | Router logits, selected IDs, local expert map and histogram | Identify routing vs implementation defect; do not mask with random reassignment without evaluation |
| OOM despite sharded experts | Padded capacity buffers, staging buffers, activations or optimizer state | Peak memory around dispatch/all-to-all/expert step | Budget measured buffers; change capacity or overlap only with quality/performance validation |
| Token loss changes with EP degree | Dropped/duplicated assignments; global reduction or mask mismatch | Compare assignment IDs and valid targets against reference | Correct dispatch/overflow/loss path and repeat numerical check |
| Collective deadlock | Inconsistent EP membership or variable-count protocol mismatch | Trace rank maps and collective order/counts | Fix all-rank protocol; test empty and skewed buckets |
| Checkpoint quality changes after reshard | Expert-ID mapping or optimizer shard mismatch | Compare expert tensors, router IDs and fixed-input logits | Repair metadata/conversion and add reshard parity tests |

## 11. Interview and self-check questions

### Q1. What does expert parallelism distribute?
**Answer:** Expert networks across a cooperating group of ranks, with routed tokens sent to the ranks hosting selected experts.
**Reasoning:** Experts are conditional compute components in a MoE layer.
**Follow-up:** Does EP multiply independent batch size?
**Answer:** No; EP ranks serve the same logical routed examples.

### Q2. Eight experts over four EP ranks: experts per rank?
**Answer:** Two under equal static placement.
**Reasoning:** `8/4=2`.
**Follow-up:** Does that prove equal work?
**Answer:** No; routing load may be skewed.

### Q3. For 128 tokens and top-2 routing, how many assignments?
**Answer:** 256 before capacity handling.
**Reasoning:** `128*2=256`.
**Follow-up:** What is balanced average per expert with eight experts?
**Answer:** 32, but maximum load can exceed the average.

### Q4. Why preserve token IDs through dispatch?
**Answer:** To return each expert output to the correct original token and sequence position.
**Reasoning:** Collective bucketing reorders assignments.
**Follow-up:** How test it?
**Answer:** Use unique IDs and distinguishable expert outputs in a tiny deterministic reference.

### Q5. What is the primary communication pattern in many EP systems?
**Answer:** All-to-all token dispatch to expert ranks and return of expert outputs.
**Reasoning:** Different source ranks route tokens to different destinations.
**Follow-up:** Does total payload determine latency?
**Answer:** No; message count, topology, skew and synchronization matter.

### Q6. Why can aggregate capacity be enough while one expert overflows?
**Answer:** Assignment distribution can be skewed across experts.
**Reasoning:** Aggregate slots do not constrain each expert's maximum load.
**Follow-up:** What should be logged?
**Answer:** Per-expert loads, per-rank loads, capacity and overflow/drop/reroute counts.

### Q7. How does EP affect memory?
**Answer:** Expert weights/state can be distributed across ranks, but routed activations, staging buffers, padding and other model state remain.
**Reasoning:** Weight sharding is only one component of peak memory.
**Follow-up:** What determines actual peak?
**Answer:** Placement, dtype, capacity, buffer overlap, optimizer state and workload shape.

### Q8. How combine EP with DP?
**Answer:** EP ranks host experts for a routed batch; DP replicas process separate batches under an explicit group layout.
**Reasoning:** They represent different axes.
**Follow-up:** What does a degree product require?
**Answer:** Independent group factors and a validated rank-coordinate map.

### Q9. When can EP be slower than dense computation?
**Answer:** Dispatch/all-to-all, skew, small expert batches, padding and synchronization can outweigh sparse arithmetic.
**Reasoning:** End-to-end step includes routing and communication.
**Follow-up:** What comparator matters?
**Answer:** Matched full workload, quality, latency, throughput and cost against a dense baseline.

### Q10. What must a checkpoint preserve?
**Answer:** Expert identity, tensor mapping, placement/resharding metadata and optimizer state as required.
**Reasoning:** Expert index semantics are part of the model.
**Follow-up:** How validate resharding?
**Answer:** Compare expert tensors and fixed-input outputs/gradients before and after conversion.
