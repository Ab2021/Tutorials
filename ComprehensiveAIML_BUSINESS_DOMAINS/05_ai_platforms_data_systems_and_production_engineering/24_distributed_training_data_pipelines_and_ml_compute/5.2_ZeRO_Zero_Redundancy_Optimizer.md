## Learning outcomes

Learners can describe replicated data-parallel state and ZeRO sharding stages; estimate per-rank optimizer, gradient and parameter storage under explicit assumptions; explain parameter gather/reduce-scatter communication and transient memory; and choose a sharding strategy using measured memory, throughput, and complexity rather than stage labels alone.

## 1. Redundant state in replicated data parallelism

In classic data parallelism, each rank holds a model replica, computes gradients on local data, participates in gradient reduction, and updates its own model/optimizer state. Weights, gradients and optimizer states can therefore be replicated across ranks. Replication simplifies local access but uses memory redundantly.

ZeRO (Zero Redundancy Optimizer) partitions selected training states across a data-parallel group to reduce per-rank memory. The common stage names indicate which categories are partitioned:

- **Stage 1:** optimizer states are partitioned;
- **Stage 2:** optimizer states and gradients are partitioned;
- **Stage 3:** optimizer states, gradients and parameters are partitioned.

Exact implementations may include communication overlap, persistence thresholds, offload, subgroups, parameter prefetch, bucket sizes and other policies. The stage number does not fully specify runtime behavior.

## 2. State categories and sharding factor

Let `D_p` be the ZeRO/data-parallel sharding group size. Let:

- `M_w` = weight storage for all parameters;
- `M_g` = gradient storage;
- `M_o` = optimizer-state storage (for example, moments and optional master weights);
- `M_a` = activations and other non-sharded or separately managed memory.

Under ideal equal sharding and ignoring temporary buffers:

```text
Stage 0 replicated state/rank: M_w + M_g + M_o
Stage 1 state/rank:             M_w + M_g + M_o/D_p
Stage 2 state/rank:             M_w + (M_g + M_o)/D_p
Stage 3 state/rank:             (M_w + M_g + M_o)/D_p
```

This simplified accounting assumes every listed state is sharded across the same group, all ranks have equal partitions, and no state is replicated or kept persistent. It excludes activations, parameter/gradient communication buffers, runtime overhead, alignment, fragmentation, temporary copies and any non-sharded state. Stage 3 may gather parameters as needed, so instantaneous peak can exceed the ideal partitioned-state term.

The formulas describe state placement, not total device memory or step-time. A sharding plan must add `M_a`, buffers, temporary gather windows and headroom, then measure per-rank peak on the real workload.

## 3. Stage behavior and communication

### Stage 1: optimizer-state sharding

Optimizer state is partitioned across ranks. Each rank updates its owned state shard. Gradients/parameters remain replicated under the simplified model. The implementation must coordinate updates so all ranks end with consistent model parameters. This can reduce persistent optimizer memory without sharding the forward weights.

### Stage 2: gradient and optimizer-state sharding

Gradients are partitioned in addition to optimizer state, often using reduce-scatter-like operations. This reduces persistent per-rank gradient storage but adds or changes communication. The model weights remain replicated in the simplified stage description.

### Stage 3: parameter, gradient, and optimizer-state sharding

Parameters are partitioned as well. A rank gathers the parameter shards needed for computation, performs relevant operations, and releases or reshares gathered values according to the implementation. This can reduce persistent parameter memory but increases communication and may create transient gathered-parameter peaks.

Communication implementation may overlap with computation; overlap can reduce exposed latency but use extra buffers and require careful scheduling. A setting that lowers steady-state memory may still OOM during prefetch, gather, optimizer, checkpoint, or evaluation.

## 4. Illustrative state calculation

Suppose one rank would otherwise hold 16 GB of optimizer states, and the state is evenly partitioned over `D_p=4` ranks at Stage 1. The ideal optimizer-state portion is `16/4=4 GB per rank`, saving 12 GB relative to replicated optimizer state. This does not include weights, gradients, activations, communication buffers, or runtime memory; it does not imply a 4-GB total model footprint.

If weights and gradients are each 2 GB per rank before sharding, Stage 0 simplified state is `2+2+16=20 GB`. Stage 1 simplified state is `2+2+4=8 GB`. Stage 2 with gradients and optimizer partitioned gives `2+(2+16)/4=6.5 GB`. Stage 3 ideal persistent state gives `(2+2+16)/4=5 GB` per rank. Actual Stage 2/3 peak can be higher due to reduction and parameter-gather buffers.

These quantities are illustrative. The source brief's 16 GB is an unsharded optimizer-state input, not a measured optimizer layout. Confirm state dtype, trainable parameter count, group size, sharding policy, and implementation before estimating a real job.

## 5. Group size and multidimensional topology

A ZeRO sharding factor is the size of the relevant data-parallel/sharding group, not necessarily total GPUs. With tensor or pipeline parallelism, processes may belong to several groups. Some dimensions partition tensors for one batch; others replicate data; some sharded states may be scoped to the data-parallel group only.

For a simple topology of 32 GPUs, tensor degree 2 and pipeline degree 4, a data-parallel degree of 4 follows only if the dimensions form an independent, fully utilized product: `2*4*4=32`. This arithmetic does not define process-group membership. Use the launcher/framework's actual rank map and verify it at runtime.

If context or expert parallelism is added, do not multiply all degrees automatically. Determine whether each dimension subdivides, reuses, overlaps, or multiplies an existing group. Incorrect group products can produce impossible rank counts, duplicated shards, missing parameters, or deadlocks.

## 6. Choosing a stage

| Constraint | Lower sharding stage tendency | Higher sharding stage tendency | Evidence needed |
|---|---|---|---|
| Per-rank persistent memory | More replicated state | Less replicated weight/gradient/optimizer state | State bytes per rank and peak timeline |
| Parameter access | Local replicated weights | Parameter gathers/prefetch may be needed | Gather traffic and peak buffers |
| Communication | Often fewer parameter gathers | More parameter/gradient communication | Collective bytes, exposed time, topology |
| Compute overlap | Fewer resharding steps | More scheduling/overlap opportunity and complexity | Profile by stage and bucket |
| Debugging simplicity | More familiar replica semantics | More state ownership and lifecycle complexity | Failure recovery and rank-consistency tests |
| Model fit | May not fit persistent states | May fit state but fail on activations/workspace | Full end-to-end peak memory |

Use the simplest strategy that satisfies measured per-rank memory and throughput constraints. If Stage 1 meets capacity, moving to Stage 3 may add complexity and communication without useful benefit. If Stage 3 is required, budget for transient gathers and validate checkpoint/restart behavior.

## 7. Offload and persistence

Some systems offload optimizer states or parameters to CPU/NVMe, or retain frequently used parameters on device. Offload trades device memory for host memory, PCIe/NVLink/network traffic, synchronization and latency. It can be appropriate when capacity is binding, but it is not free capacity.

Parameter persistence thresholds and prefetch policies trade memory for fewer transfers or better overlap. Record offload target, pinned-memory use, transfer bandwidth, prefetch window, bucket size, and where optimizer updates occur. Measure end-to-end throughput and peak memory rather than relying on configured theoretical savings.

## 8. Checkpointing and state ownership

A sharded model checkpoint can store rank-local state or consolidate it into a representation for inference/transfer. Checkpoint format, metadata, optimizer state and mapping between old and new group sizes must be understood. Saving a distributed checkpoint can itself create temporary memory and communication peaks.

Recovery requires consistent mapping of parameter/optimizer shards to ranks, versioned configuration, and a defined procedure when world size changes. Do not load a partial shard set or infer missing shard ownership from file ordering. Validate by round-tripping a small model and comparing parameters, optimizer state and one resumed update.

## 9. Correctness invariants

Before long training, validate:

- every trainable parameter and state tensor has one intended owner or replica set;
- every rank can access the parameter values needed for its forward/backward work;
- gradient reduce-scatter/all-gather and optimizer updates preserve the intended global gradient;
- sharded parameters are gathered before use and released/resharded according to policy;
- all ranks agree on step and parameter version before the next computation;
- checkpoint save/load preserves shard identities and optimizer state;
- failure on one rank cannot leave inconsistent partial updates treated as a valid step;
- model outputs and gradients match a small unsharded reference within stated numerical tolerance.

Correctness checks should run before performance tuning. A memory saving is not useful if parameter ownership or gradient aggregation is wrong.

## 10. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Stage 1 memory barely changes | Optimizer state smaller than assumed; group size 1; state replicated by config | Inspect optimizer tensor ownership and sharding group at runtime | Correct group/config or revise estimate from observed state |
| Stage 3 OOM during forward | Parameter gather window, prefetch or workspace peak | Capture per-rank timeline around all-gather and layer use | Reduce measured gather window or adjust partitioning/overlap with throughput checks |
| Training slower after sharding | Communication, poor overlap, small buckets, topology mismatch | Profile collectives, exposed waits, transfers and compute | Tune measured communication bottleneck or choose a simpler feasible stage |
| Parameters diverge across ranks | Incorrect reduce-scatter/all-gather/update ownership | Compare reconstructed parameters and gradients to reference | Fix ownership/reduction; stop before checkpoint promotion |
| Checkpoint loads but output changes | Missing/misordered shards, wrong metadata or dtype conversion | Round-trip checksums and logits on fixed inputs | Repair mapping and add artifact-level tests |
| Stage formulas predict fit but run OOMs | Activations, buffers, temporary gathers, runtime or fragmentation omitted | Compare formula with measured peak categories | Expand budget with measured overhead and reserve headroom |
| One process group deadlocks | Mismatched group membership or collective call order | Log rank/group maps and collective sequence | Correct topology/call order; test all ranks with a small deterministic collective |
| Offload saves memory but throughput collapses | Transfer bottleneck, pageable memory, synchronization | Profile transfer bytes/time and compute overlap | Reevaluate offload target/window or reject under latency constraint |

## 11. Interview and self-check questions

### Q1. What does ZeRO Stage 1 shard?
**Answer:** Optimizer states across the sharding/data-parallel group under the standard stage description.
**Reasoning:** Weights and gradients remain replicated in the simplified accounting.
**Follow-up:** Does that mean total per-rank memory is optimizer state divided by group size only?
**Answer:** No; weights, gradients, activations, buffers and runtime remain.

### Q2. What additional states are sharded at Stage 2?
**Answer:** Gradients, along with optimizer states.
**Reasoning:** Stage 2 adds gradient partitioning beyond Stage 1.
**Follow-up:** What may change operationally?
**Answer:** Gradient communication/reduction and transient buffer behavior.

### Q3. What additional state is sharded at Stage 3?
**Answer:** Model parameters/weights as well as gradients and optimizer states.
**Reasoning:** The persistent parameter copy is partitioned; parameters may be gathered for computation.
**Follow-up:** Why can peak exceed the ideal partitioned formula?
**Answer:** Parameter prefetch/gather buffers and other transient allocations.

### Q4. Four-way shard of 16 GB optimizer state: what is the ideal per-rank state?
**Answer:** 4 GB.
**Reasoning:** `16/4=4` under equal partitioning.
**Follow-up:** Is total training memory 4 GB?
**Answer:** No; weights, gradients, activations, buffers and runtime remain.

### Q5. How do you choose the ZeRO group size in a hybrid topology?
**Answer:** Use the actual process group that owns/partitions those states, not total GPU count by default.
**Reasoning:** Tensor and pipeline groups can use devices for the same data examples.
**Follow-up:** What verifies it?
**Answer:** Runtime rank map, group membership and state ownership logs.

### Q6. Why may Stage 3 communicate more than Stage 1?
**Answer:** It partitions parameters and may gather them around computation, in addition to gradient/state handling.
**Reasoning:** Memory savings require data movement and synchronization.
**Follow-up:** What decides if it is worthwhile?
**Answer:** Measured memory fit, communication/compute overlap, throughput and cost.

### Q7. What is offload's tradeoff?
**Answer:** It moves state off device but adds transfer, host memory and synchronization costs.
**Reasoning:** State is still needed for computation and updates.
**Follow-up:** What should be measured?
**Answer:** End-to-end throughput, transfer time, peak host/device memory and latency.

### Q8. Can the Stage 3 formula guarantee a model fits?
**Answer:** No; it excludes activations, transient gathers, buffers, runtime and allocator headroom.
**Reasoning:** It estimates only ideal persistent state under assumptions.
**Follow-up:** What confirms fit?
**Answer:** Representative end-to-end peak-memory run at worst-case shapes and operations.

### Q9. What must a sharded checkpoint preserve?
**Answer:** Parameter/shard identity, metadata, optimizer state as needed, dtype and topology mapping.
**Reasoning:** File order alone does not define ownership.
**Follow-up:** How validate a conversion?
**Answer:** Round-trip parameters/logits and compare a resumed update to a reference.

### Q10. Why start with the lowest feasible sharding stage?
**Answer:** It avoids unnecessary communication and complexity when a simpler design meets memory and throughput constraints.
**Reasoning:** Higher stages trade replication for more coordination.
**Follow-up:** When move higher?
**Answer:** When measured per-rank memory requires it and the communication/performance tradeoff is acceptable.

|---|---|---|
| 0 | None (replicated data parallel) | `M_w+M_g+M_o` |

| Decision check | Rule |
|---|---|

| Peak memory | Add gathers, activations, buffers, runtime and headroom. |

| Correctness | Compare sharded outputs/gradients and checkpoint round-trip to reference. |
| Evidence | All numeric savings illustrative; no distributed run measured. |
