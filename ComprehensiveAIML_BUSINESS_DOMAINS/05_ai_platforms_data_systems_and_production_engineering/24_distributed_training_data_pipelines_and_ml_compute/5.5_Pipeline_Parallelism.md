## Learning outcomes

Learners can explain layer-wise pipeline partitioning; describe microbatch fill/steady/drain behavior; calculate ideal bubble fractions for a stated schedule; reason about stage balance, activation memory and inter-stage communication; and validate forward/backward ordering, gradients and checkpoint ownership across pipeline stages.

## 1. What pipeline parallelism partitions

Pipeline parallelism (PP) partitions model layers into ordered stages placed on different devices or device groups. A batch is split into microbatches. Each stage processes a microbatch and sends activations forward; during backward, it receives activation gradients and sends gradients to the preceding stage.

The model is distributed by depth: different pipeline stages own different layer ranges. Unlike tensor parallelism, which shards operations within layers, pipeline parallelism assigns whole layers or layer blocks to stages. Unlike data parallelism, stages cooperate on the same microbatch; pipeline schedule determines when each stage is active or idle.

Pipeline communication generally transfers activation tensors and their gradients between adjacent stages. Stage boundary placement affects tensor sizes, normalization/residual placement, embeddings/output head, and memory ownership.

## 2. Microbatches and pipeline schedule

A pipeline schedule overlaps work on multiple microbatches. It has a **fill** period while stages become active, a **steady state** where different stages process different microbatches, and a **drain** period as remaining forward/backward work completes.

Common schedules include:

- **GPipe-style flush:** run forward microbatches through the pipeline, then backward microbatches; all microbatches in a batch complete before the optimizer update.
- **1F1B (one-forward-one-backward):** after warmup, alternate forward and backward work to reduce activation residency while maintaining pipeline utilization.
- **Interleaved/chunked schedules:** assign multiple virtual chunks per physical stage to improve balance/utilization at added complexity.

Exact schedule semantics differ across frameworks. State the schedule, number of physical stages, virtual stages/chunks, microbatches, activation policy, optimizer-step boundary and whether updates are synchronous.

## 3. Idealized bubble fraction

For a simple flushed schedule with `p` equally fast stages and `m` microbatches, assume one stage-time unit per forward/backward work slot and a balanced pipeline. The idealized total slots are proportional to `m+p-1`; `m` slots per stage can perform useful work while `(p-1)` slots represent fill/drain bubble for the simplified schedule.

```text
FORMULA [PP-01]: utilization_ideal = m / (m+p-1)
                 bubble_fraction_ideal = (p-1)/(m+p-1)
WHERE: p = pipeline stages; m = microbatches; equal stage times and simplified flushed schedule.
CONSTRAINT: excludes stage imbalance, communication, memory stalls, schedule variants, and differing forward/backward costs.
NUMERICAL EXAMPLE: p=4 stages, m=8 microbatches.
                   bubble fraction = (4-1)/(8+4-1)=3/11≈27.27%.
                   ideal utilization = 8/11≈72.73%.
INTERPRETATION: more microbatches reduce the ideal fill/drain fraction for this schedule, but increase scheduling/activation considerations and do not remove communication.
```

Independent check: `3/11+8/11=1`. This simplified formula is not a universal utilization estimator. 1F1B and interleaved schedules have different memory and timing behavior; use the framework schedule model and a measured timeline.

## 4. Stage partition and load balance

A pipeline is limited by its slowest stage. Equal layer counts do not guarantee equal compute or memory: embedding/output layers, attention/MLP dimensions, sequence shapes, recomputation, communication, and kernel efficiency vary.

Partition by measured stage time and memory at the target workload. Record per-stage layer ownership, parameter/optimizer/activation memory, forward/backward time, send/receive time, and idle/bubble time. A stage with significantly more work creates backpressure and leaves other stages idle.

Balance can change with batch size, sequence length, precision, model architecture, or data-dependent routing. A plan based on one sequence length can fail on longer sequences or expert-heavy tokens.

## 5. Activation memory and schedules

Pipeline schedules affect how many microbatch activations remain live until their backward pass. GPipe-style all-forward-then-backward can retain activations for many microbatches, increasing memory. 1F1B schedules can reduce the number of outstanding activations per stage, depending on implementation and stage count. Activation checkpointing/recomputation changes memory/compute tradeoffs but is a separate mechanism.

Do not assume more microbatches always improve the system. More microbatches can reduce bubble fraction but may increase scheduling overhead or alter per-microbatch kernel efficiency; schedule and activation policies affect memory. Verify the peak-live activation count for the actual implementation.

A microbatch size is per stage/device and can differ across stages in some systems. Track per-stage token counts and ensure loss normalization is correct if microbatch sizes or valid target counts vary.

## 6. Forward activations and backward gradients

At a stage boundary, the upstream stage sends activations to the downstream stage. In backward, the downstream stage returns gradients with respect to those activations. Tensor shape and dtype at the boundary determine communication volume.

For boundary tensor shape `[B_micro,T,d]` and `b` bytes per value, one activation payload is `B_micro*T*d*b` bytes. Backward may send a similarly shaped gradient payload. Actual traffic can include headers, padding, compression, repeated transfers, buffers and topology effects.

Communication can overlap with compute if dependencies permit. A stage cannot process a microbatch until its required input arrives, and the previous stage cannot complete the corresponding backward until the gradient returns. Measure exposed communication, not only bytes or link bandwidth.

## 7. Optimizer updates and gradient semantics

A pipeline microbatch is not necessarily an optimizer update. For synchronous batch training, accumulated gradients across all microbatches in the intended global batch contribute to one update. Parameters should not change halfway through a pipeline batch unless the algorithm explicitly defines asynchronous/stale updates.

Loss scaling and gradient reduction must preserve the intended global objective. If microbatches carry different numbers of valid targets, average-by-microbatch can differ from token-mean loss. Ensure the pipeline engine's reduction and accumulation semantics match the declared objective.

Schedulers typically advance per optimizer update or consumed token budget, not per pipeline slot. Verify how gradient clipping, weight decay and optimizer-state updates interact with the schedule.

## 8. Combine PP with other parallel dimensions

Pipeline degree `P_p` is the number of sequential model stages. Tensor degree partitions within each stage; data degree replicates the full pipeline for different examples; context degree partitions sequence positions; expert degree distributes routed experts. The product equals world size only under independent, non-overlapping factors.

For an illustrative 32-device job with TP2, PP4 and DP4, `2*4*4=32`. The pipeline has four stages; each stage may itself use two TP ranks; four DP replicas process distinct data. Global data batch is multiplied by DP degree, not by PP or TP degree.

The exact group topology, rank coordinates, and collective order must be read from the runtime configuration. A mathematically valid degree product does not establish correct group membership.

## 9. When pipeline parallelism is useful

PP can distribute model layers when a model does not fit on a single device and TP/ZeRO alone are insufficient or inefficient. It can reduce per-device layer-state and activation residency, but introduces stage dependencies, bubble time, activation transfers and more complex checkpoint/recovery.

The preferred combination depends on model depth/width, sequence length, interconnect, stage balance, microbatch availability and target throughput. Compare against a simpler feasible configuration. Pipeline parallelism is less effective when the workload has too few microbatches to keep stages busy or stage times are highly imbalanced.

## 10. Correctness and recovery checks

Before long runs, verify:

- each layer belongs to exactly the intended stage and stage order is preserved;
- forward activations and backward gradients cross boundaries with correct shapes and dtypes;
- microbatches are ordered and associated with correct sample/target IDs;
- every intended target contributes exactly once to the global loss;
- gradient accumulation/update cadence matches the configured global batch;
- all stages agree on optimizer step and checkpoint boundary;
- stage partition and checkpoint metadata reconstruct the same logical model;
- rank failure or communication failure does not silently advance only some stages.

Use a small model with known weights to compare a pipeline update to a single-device reference. Test multiple microbatches, boundary stages, uneven sequence lengths, partial final batches, and checkpoint/resume.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| High idle time across stages | Too few microbatches; fill/drain bubbles; stage imbalance | Timeline per stage and schedule slot | Increase usable microbatches or rebalance based on measured work, preserving batch semantics |
| One stage is always bottleneck | Unequal layer compute/memory; slow kernel; communication | Stage-level forward/backward/transfer profile | Repartition or optimize measured stage; recheck memory and checkpoint mapping |
| OOM despite model sharding | Activation retention in schedule; stage imbalance; boundary buffers | Peak live activations and memory per stage | Change schedule/checkpoint policy with throughput and numerical tests |
| Pipeline outputs differ from reference | Wrong stage order, activation shape, loss/gradient route | Compare intermediate boundary tensors and gradients | Correct stage mapping and add deterministic parity test |
| Global batch/loss changes with microbatch count | Mis-scaled loss; update at wrong boundary; partial window | Track sample IDs, target counts, optimizer steps and denominator | Fix aggregation semantics and rerun controlled comparison |
| Deadlock at stage boundary | Mismatched send/receive order, group mismatch, rank failure | Trace matching stage/rank communication calls | Correct communication schedule and test failure/timeouts |
| Schedule uses memory unexpectedly | Wrong activation-retention assumption or virtual-stage policy | Inspect engine schedule and saved activations by microbatch | Recalculate actual live activation count and choose validated schedule |
| Resume produces inconsistent layers | Shard/stage mapping not restored; checkpoint incomplete | Compare per-stage tensors and full reconstructed logits | Repair checkpoint metadata and require round-trip test |

## 12. Interview and self-check questions

### Q1. What does pipeline parallelism partition?
**Answer:** Model layers into sequential stages, usually across devices or device groups.
**Reasoning:** Different stages own different layer ranges and exchange activations/gradients.
**Follow-up:** Does pipeline degree increase independent data batch?
**Answer:** No, pipeline stages cooperate on the same microbatch.

### Q2. For four stages and eight microbatches, what is the simplified GPipe bubble fraction?
**Answer:** `3/11`, about 27.27%.
**Reasoning:** `(p-1)/(m+p-1)=3/(8+3)`.
**Follow-up:** Is that measured utilization?
**Answer:** No; it ignores imbalance, communication and implementation details.

### Q3. Why can equal layer counts create imbalance?
**Answer:** Layers differ in compute, memory, kernel efficiency and communication.
**Reasoning:** Stage time, not layer count, controls pipeline throughput.
**Follow-up:** What should guide partitioning?
**Answer:** Measured per-stage time and peak memory at the target workload.

### Q4. Why does GPipe-style scheduling retain many activations?
**Answer:** It runs multiple forwards before corresponding backwards, so activations wait for gradient computation.
**Reasoning:** Backward consumes saved intermediate values.
**Follow-up:** What schedule can reduce outstanding activations?
**Answer:** 1F1B often reduces them, subject to implementation and stage count.

### Q5. What travels between pipeline stages?
**Answer:** Forward activations and backward gradients, plus protocol/control data.
**Reasoning:** Adjacent stages are sequential parts of one model.
**Follow-up:** How estimate payload bytes?
**Answer:** Multiply boundary tensor elements by bytes per element, then account for actual buffers/overlap.

### Q6. What is the global data batch in TP2, PP4, DP4?
**Answer:** Local batch times accumulation times 4 data replicas.
**Reasoning:** TP/PP ranks cooperate on the same examples.
**Follow-up:** Do 32 devices imply batch multiplier 32?
**Answer:** No; use data-parallel degree.

### Q7. When should pipeline optimizer updates occur?
**Answer:** At the intended complete batch/update boundary unless the algorithm explicitly defines otherwise.
**Reasoning:** Updating mid-batch changes which weights later microbatches see.
**Follow-up:** What must be compared to a single-device reference?
**Answer:** Loss, gradients, update cadence and target normalization.

### Q8. Why can increasing microbatch count hurt memory or efficiency?
**Answer:** It can change activation retention, scheduling overhead and per-microbatch kernel efficiency.
**Reasoning:** Lower ideal bubble fraction is not a free systems gain.
**Follow-up:** What is the right measurement?
**Answer:** End-to-end throughput, stage utilization and peak per-stage memory.

### Q9. Why is the stage partition part of checkpoint metadata?
**Answer:** Parameters are owned by layers/stages; reconstruction depends on mapping.
**Reasoning:** A checkpoint without stage identity can load tensors incorrectly.
**Follow-up:** How verify a reshard?
**Answer:** Reconstruct model outputs and compare logits/gradients against reference.

### Q10. What makes a pipeline failure unsafe?
**Answer:** Some stages advance weights or optimizer state while others fail, leaving an inconsistent model state.
**Reasoning:** The logical update spans all stages.
**Follow-up:** What should happen?
**Answer:** Fail the step coherently and recover from a consistent checkpoint boundary.
