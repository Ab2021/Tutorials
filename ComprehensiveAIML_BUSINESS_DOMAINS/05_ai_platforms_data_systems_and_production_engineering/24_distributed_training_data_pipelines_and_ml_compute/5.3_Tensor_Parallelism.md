## Learning outcomes

Learners can explain intra-layer tensor sharding; derive basic column- and row-parallel linear shapes; track when activations are sharded or replicated; identify collectives required by a layer layout; estimate per-rank weight storage under ideal partitioning; and diagnose communication, divisibility and process-group errors.

## 1. What tensor parallelism partitions

Tensor parallelism (TP) partitions operations and parameter tensors within a model layer across a group of devices. Each rank computes part of a layer's linear algebra; ranks exchange or combine intermediate values so the next operation receives the required representation.

Unlike data parallelism, TP ranks generally cooperate on the same examples and sequence positions. Increasing TP degree does not, by itself, multiply the number of independent data examples in the global batch. Its main purpose is to distribute large layer tensors and computation, subject to communication and memory tradeoffs.

A TP group must have explicit rank membership and collective order. A process may simultaneously belong to TP, pipeline and data-parallel groups; total world size alone does not define the TP group.

## 2. Column-parallel linear projection

Consider a linear transform with input `X` of shape `[B,T,d_in]` and weight `W` of shape `[d_in,d_out]`, using row-vector convention `Y=XW`. In column parallelism, split the output dimension across `p` TP ranks. Rank `r` owns `W_r` with shape `[d_in,d_out/p]` and computes `Y_r=XW_r` of shape `[B,T,d_out/p]`.

The input `X` is commonly replicated across the TP group in this conceptual layout; outputs are sharded by output features. If the next operation can consume the sharded output, an all-gather may be deferred. If a later operation needs a full output, ranks exchange shards.

Validity: `d_out` divisible by `p` for equal shards; replicated input and the stated row-vector convention. Bias handling and uneven partitions are implementation-specific.

```text
FORMULA [TP-01]: W_r shape = [d_in, d_out/p]
                 Y_r = X W_r, shape [B,T,d_out/p]
WHERE: p = tensor-parallel group size; B = batch; T = sequence length.
CONSTRAINT: equal output sharding; input X replicated; d_out divisible by p.
NUMERICAL EXAMPLE: B=2, T=16, d_in=8, d_out=12, p=3.
                   Full W has 8*12=96 weights; each rank holds 8*4=32.
                   X shape [2,16,8]; each local output has shape [2,16,4].
INTERPRETATION: feature computation and weight storage are partitioned; batch and sequence are not split by this tensor layout.
```

## 3. Row-parallel linear projection

In row parallelism, split the input dimension of `W` across TP ranks. Each rank receives or holds the matching input shard `X_r` and computes a partial output `Z_r=X_r W_r`, with `W_r` shape `[d_in/p,d_out]`. The partial outputs have shape `[B,T,d_out]` and must be summed across ranks to produce the full result.

Implementations may use all-reduce, reduce-scatter, or another layout transition. Bias should be added once to the combined output, or partitioned/handled so that the final bias is not multiplied by group size. Exact placement is implementation-dependent.

For a two-layer MLP, a common pattern uses a column-parallel expansion followed by a pointwise activation and row-parallel contraction. The expanded hidden dimension is sharded through the activation; the contraction produces partial outputs that are reduced. This can avoid materializing full intermediate activations on every rank, but requires compatible tensor layouts and collectives.

## 4. Attention and head partitioning

Attention projections can be partitioned by heads or feature dimensions. When head count divides TP degree, each rank can own a subset of heads and compute attention for those heads. The output projection commonly combines head outputs across ranks using a compatible row-parallel layout.

Head partitioning details depend on multi-head, grouped-query, multi-query, and latent-attention designs. Query/key/value head counts may differ; a naive equal split can be invalid or leave ranks uneven. Verify tensor shapes and key/value replication for the concrete architecture.

Sequence positions remain available to each TP rank in ordinary intra-layer TP. Context parallelism instead partitions sequence/context and has different communication requirements.

## 5. Communication and layout transitions

Tensor parallelism introduces collectives within or between layers. A projection may produce sharded outputs; a later operation may require a reduction or gather. Communication can be overlapped with computation in some implementations, but synchronization and latency remain.

The number of collectives is not determined by TP degree alone. It depends on layer layout, fusion, activation placement, parallel algorithm and framework. A TP configuration that keeps more operations local may perform better than one that minimizes nominal parameter bytes but communicates frequently.

Communication costs are especially visible when local matrix operations become small or the interconnect is slow. High-bandwidth links within a node can make TP viable at small degrees; extending TP across nodes may incur larger latency and traffic. Measure the actual topology and collective path.

## 6. Parameter and compute distribution

For a dense matrix with `d_in*d_out` parameters split evenly across `p` ranks, each rank stores approximately `d_in*d_out/p` elements for that matrix. This excludes replicated embeddings, norms, biases, optimizer state, temporary gathered values and non-divisible shapes.

TP distributes portions of a layer's arithmetic but does not automatically reduce total model FLOPs; the aggregate computation remains broadly similar, while each rank performs a share and communication is added. Throughput can improve when a model otherwise does not fit or when devices provide more aggregate compute, but synchronization may limit scaling.

Optimizer state may be sharded across TP ranks, replicated, or combined with ZeRO/other partitioning. Do not assume that parameter sharding automatically implies optimizer-state partitioning; inspect the combined strategy.

## 7. Shape and divisibility constraints

Equal sharding commonly requires relevant dimensions to be divisible by TP degree: attention heads, hidden features, intermediate width, or matrix dimensions. Some frameworks support uneven shards, padding or replication. These alternatives can cause imbalance and extra communication.

When TP is combined with quantization, fused kernels, grouped-query attention or vocabulary-parallel output heads, additional shape and alignment constraints may apply. Validate actual local shapes and parameter ownership on every rank. A model loading without error is not proof that all heads or vocabulary rows are mapped correctly.

Use a rank diagram that specifies global rank, TP rank, data-parallel rank, pipeline stage, and any other axis. Check that every expected shard exists exactly once per intended group.

## 8. Global batch and multidimensional topology

The tensor-parallel degree is not a factor in effective batch when TP ranks process the same examples. If a 32-GPU job uses TP degree 2, pipeline degree 4 and data degree 4, the product `2*4*4=32` accounts for all GPUs only under independent axes and no extra replication. Global data batch multiplies by degree 4, not 32.

Context and expert parallel dimensions may interact with the axes in nontrivial ways. Never multiply all named degrees without defining whether groups partition, reuse, or replicate ranks. Verify process-group membership from runtime configuration.

Changing TP degree can alter number of data-parallel replicas at fixed world size, thereby changing global batch and data schedule. Keep batch and token budgets explicit when comparing TP configurations.

## 9. When to use tensor parallelism

TP is useful when layer weights or computations are too large for a single device, or when the target system supports efficient intra-layer collectives. It adds code/runtime complexity and communication. Alternatives include model-size reduction, sequence/context parallelism for sequence memory, ZeRO/FSDP for state sharding, pipeline parallelism for layer partitioning, or an appropriate combination.

Select the simplest feasible configuration based on measured per-rank memory, compute, communication, throughput and failure recovery. A larger TP degree is not automatically better. Benchmark the full training path, not only a matrix multiplication microbenchmark.

## 10. Correctness and operational validation

Use a small model where a single-device reference can be run. Compare forward outputs, loss, gradients and one optimizer update across TP layouts within a stated tolerance. Include non-square matrices, batch/sequence boundaries, bias, residual paths, normalization, attention head partitions, and output projection.

Verify:

- each weight shard maps to the correct slice of the reference tensor;
- replicated inputs are identical where required;
- partial outputs are reduced exactly once;
- bias is added once with correct semantics;
- collective ranks and call order match across all participants;
- gradients and optimizer states follow intended partition/replication policy;
- checkpoint save/load reconstructs the same logical model;
- TP rank failures do not produce silently partial valid-looking outputs.

Before scaling out, test initialization, process-group construction, one training step, checkpoint round-trip, and rank-level diagnostics. A deadlock often signals mismatched collective participation or group membership.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Forward output differs from reference | Wrong shard order; missing reduction; bias applied per rank; bad head map | Compare each local shard and intermediate against reference slices | Fix layout mapping and add deterministic parity tests |
| Deadlock in layer collective | Group mismatch; conditional collective path; ranks call in different order | Log TP membership and collective sequence by global rank | Correct group construction/control flow and retest small job |
| TP degree increases memory | Replicated tensors, buffers, padding, optimizer state or all-gather peak | Per-rank tensor inventory and peak timeline | Identify replicated/temporary component before changing degree |
| TP scaling is slower | Communication latency, small local GEMMs, poor overlap, cross-node topology | Profile collective exposed time and local compute per rank | Reduce communication or choose another feasible parallel axis |
| Attention results wrong for some head counts | Head/grouped-query divisibility or K/V replication mismatch | Test local Q/K/V shapes and output on nontrivial head cases | Use architecture-aware partitioning; do not force equal split blindly |
| Global batch unexpectedly shrinks | Fixed world size reallocates ranks from data to TP | Recompute DP group and examples/tokens per update | Match global batch or report changed optimization regime |
| Checkpoint load changes logits | Shard metadata/order/dtype or reshard conversion error | Compare reconstructed tensors and fixed-input logits | Repair conversion and require artifact parity test |
| Only some shapes fail | Uneven dimensions, padding/alignment, fused-kernel constraint | Sweep dimensions around divisibility boundaries | Choose supported dimensions or explicitly validate uneven policy |

## 12. Interview and self-check questions

### Q1. What does tensor parallelism partition?
**Answer:** Tensors and computations within a layer across a process group.
**Reasoning:** Ranks cooperate on the same examples rather than each processing a separate data shard.
**Follow-up:** Does TP multiply global batch?
**Answer:** No, not by itself.

### Q2. In column parallelism, which matrix dimension is split?
**Answer:** The output-feature dimension, under the row-vector convention used here.
**Reasoning:** Each rank computes a slice of output features.
**Follow-up:** What is local output shape for `[B,T,d_in]` and `p` equal shards?
**Answer:** `[B,T,d_out/p]`.

### Q3. What happens in row-parallel linear projection?
**Answer:** Ranks compute partial outputs from input/weight shards; partial outputs are combined.
**Reasoning:** The input dimension is partitioned.
**Follow-up:** What collective may be used?
**Answer:** An all-reduce or another reduce/gather layout transition, depending on implementation.

### Q4. For a 96-weight matrix split across 3 ranks, how many weights per rank?
**Answer:** 32 under equal partitioning.
**Reasoning:** `96/3=32`.
**Follow-up:** Is the entire model memory divided by three?
**Answer:** Not necessarily; replicated state, optimizer state, buffers and activations may remain.

### Q5. Why do tensor-parallel ranks not count as independent data examples?
**Answer:** They compute different shards for the same batch examples.
**Reasoning:** The examples are distributed across data-parallel groups, not TP groups.
**Follow-up:** What changes global batch in a hybrid setup?
**Answer:** Data-parallel degree, microbatch and accumulation under the configured grouping.

### Q6. Why is divisibility important?
**Answer:** Equal partitions of heads/features often require dimensions divisible by TP degree.
**Reasoning:** Otherwise ranks receive unequal or padded shards.
**Follow-up:** Can uneven partitioning work?
**Answer:** Some implementations support it, but validate balance, alignment and communication.

### Q7. Does TP reduce total model FLOPs?
**Answer:** Not automatically; it distributes computation, and communication is added.
**Reasoning:** The same logical layer computation is still performed across ranks.
**Follow-up:** Why use TP then?
**Answer:** Fit large tensors and use aggregate device compute when communication cost is acceptable.

### Q8. What are common signals of a wrong collective layout?
**Answer:** Forward mismatch, rank divergence, deadlock, wrong bias scaling, or incorrect gradients.
**Reasoning:** Shard/collective contract is violated.
**Follow-up:** What reference test helps?
**Answer:** Compare outputs, loss, gradients and one update against a small unsharded model.

### Q9. How can increasing TP reduce data throughput?
**Answer:** It may reduce data-parallel degree at fixed world size and add intra-layer communication.
**Reasoning:** Fewer independent examples are processed concurrently, and collectives add overhead.
**Follow-up:** What must be matched in a comparison?
**Answer:** Global batch, token budget, model, topology and measured system cost.

### Q10. What must a TP checkpoint preserve?
**Answer:** Shard identity/order, logical tensor mapping, dtype and optimizer-state ownership as applicable.
**Reasoning:** File sequence alone does not define reconstruction.
**Follow-up:** How verify conversion?
**Answer:** Reconstruct tensors and compare fixed-input logits/gradients to the reference.
