## Learning outcomes

Learners can explain replicated data-parallel training; distinguish data-parallel degree from other parallel dimensions; calculate global batch and first-order gradient communication; reason about gradient reduction, synchronization and stragglers; and validate rank topology, data partitioning and numerical equivalence before scaling out.

## 1. Data-parallel training model

In data parallelism, each replica holds a copy of the model parameters and processes a different portion of the global batch. Each replica computes local gradients; a collective operation combines gradients across replicas; all replicas apply the same optimizer update so their parameters remain synchronized.

A simplified synchronous step is:

```text
same model weights on each data-parallel rank
        ↓
rank r processes distinct local examples
        ↓
local forward/backward → local gradients
        ↓
collective reduce/average gradients
        ↓
identical optimizer update on each replica
        ↓
replicas start next step with synchronized weights
```

The central tradeoff: adding replicas can process more examples concurrently, but adds gradient communication, synchronization and input-pipeline work. Ordinary replicated data parallelism does not divide model parameters or optimizer state across data-parallel ranks; every rank generally holds its own copy unless combined with a sharding strategy.

## 2. Process groups and degree

Let `D_p` be the number of data-parallel replicas in a process group. Data-parallel rank identifies one replica in that group. In a hybrid layout, the same process may also belong to tensor, pipeline, context or expert groups. These dimensions have different roles and cannot be inferred from the total device count alone.

The global batch for fixed-size local microbatches can be expressed as:

```text
sequences/update = sequences_per_rank * accumulation_steps * D_p
```

This assumes the microbatch value is per data-parallel rank and that each replica sees distinct examples. If a data-parallel group is nested within other parallel dimensions, use the actual data-parallel group size—not total world size.

For example, 32 GPUs with tensor degree 2 and pipeline degree 4 leave `32/(2*4)=4` data-parallel replicas only if groups are independent, fully utilized, and there are no additional dimensions or replication factors. The group construction still must be verified from the launch configuration.

## 3. Gradient synchronization

Synchronous data-parallel training requires gradients to be combined before replicas update. Common approaches include all-reduce (reduce then distribute the result), or reduce-scatter followed by a later all-gather in a sharded design. The collective and reduction semantics determine whether gradients are summed or averaged and how loss scaling must be applied.

If each rank computes a local mean loss and the collective averages gradients equally, the result matches the global example/token mean only when local denominators are equal or the implementation corrects for unequal counts. Variable-length sequences, masked targets, uneven final batches, or rank-level filtering can make local target counts differ.

Validate the reduction contract with a small known gradient and multiple ranks. Do not assume that identical loss scalar values on all ranks imply correct global weighting.

## 4. Global batch and accumulation example

Illustrative setup: 2 sequences per rank per microbatch, 8 accumulation steps, 4 data-parallel replicas. Global effective sequences/update are `2*8*4=64`. At fixed length 2,048, nominal positions/update are `64*2,048=131,072` before padding or target masks.

If the training objective is token-mean and ranks have different valid-token counts, the intended global gradient is:

```text
∇L_global = (sum over ranks and microbatches of ∇(summed token losses))
            / (sum over ranks and microbatches of valid target tokens)
```

An equal average of rank-level means can differ when denominators are unequal. Inspect the framework's distributed loss reduction and any gradient-accumulation scaling.

A larger global batch changes optimization behavior, not merely throughput. Learning-rate schedule, number of updates, token budget, gradient noise, data order and warmup units may all change when replica count changes.

## 5. Communication volume and first-order scaling

For `P` gradient elements and `b` bytes per element, gradient tensor size is `S=P*b` bytes. In an ideal ring all-reduce over `D_p` ranks, a common bandwidth-volume approximation for bytes sent per rank is:

```text
V_sent_per_rank ≈ 2*(D_p-1)/D_p * S
```

This approximation captures a standard reduce-scatter plus all-gather ring schedule under large-message assumptions. It excludes latency, protocol overhead, topology, overlap, compression, multiple buckets, retransmission and concurrent traffic. The actual collective may use a different algorithm.

Illustrative example: `P=1e9` gradient elements, 2 bytes/element, `D_p=8` gives `S=2 GB` and `V_sent≈2*(7/8)*2=3.5 GB per rank` under this approximation. This is communication volume, not wall time. Effective time depends on network bandwidth/latency and collective implementation; receive traffic and link-level bytes depend on the topology and accounting convention.

A useful communication-to-compute analysis measures both: gradient bytes, collective time, forward/backward time, overlap, and exposed synchronization. More GPUs do not guarantee linear speedup.

## 6. Replicated memory and sharding distinction

Classic data parallelism replicates model weights, gradients and optimizer state on each data-parallel rank. It can increase total system memory by adding replicas without increasing the model size that fits on one rank. It also replicates optimizer work, although each rank handles distinct examples.

Sharded optimizer/gradient/parameter approaches change this memory behavior and communication pattern. They are distinct mechanisms covered by ZeRO or fully sharded training strategies. Do not attribute their memory savings to data parallelism alone.

A memory plan should list, per rank, weight, gradient, optimizer, activation, workspace and communication-buffer allocations. A system-wide sum can conceal a per-rank OOM; per-rank fit is the constraint for replicated training.

## 7. Input distribution and synchronization

Each replica must receive the intended shard of the data. A sampler may partition examples by rank and epoch, shuffle deterministically, drop/pad final batches, or repeat data to equalize work. These choices affect sample exposure and reproducibility.

Synchronous training waits for all participating ranks at collectives. A slow data loader, straggling device, uneven sequence lengths, filesystem hotspot, or overloaded network path can stall every rank. Measure rank-level input wait, compute, communication and step time; averages can hide a slow tail rank.

Log rank, step, sampler state, example/token IDs or privacy-safe references, and number of valid targets. Avoid duplicate or missing samples when resuming or changing world size unless the data schedule explicitly permits it.

## 8. Scaling efficiency

Strong scaling keeps the global work roughly fixed while adding resources, reducing work per rank. Weak scaling keeps work per rank roughly fixed, increasing total global work as resources are added. Report which regime a benchmark uses.

Speedup is `T_1/T_D` relative to a specified baseline; parallel efficiency is often `speedup/D_p` for a pure data-parallel scale-up, but interpretation needs a matched model, data and budget. Strong-scaling speedup eventually saturates when communication, synchronization or input overhead dominates.

Benchmark end-to-end training at realistic sequence lengths, batch, data loader, evaluation/checkpoint cadence, and network topology. Report tokens/sec, examples/sec, time-to-target-quality, accelerator-hours and cost. Raw step time or theoretical FLOPs alone is insufficient.

## 9. Rank and data correctness invariants

Before a long run, validate:

- every process has the intended global rank and belongs to the correct data-parallel group;
- all replicas start from compatible parameter values and use matching model/configuration;
- each global batch contains the expected distinct examples or tokens;
- the collective reduces the intended gradients exactly once per update;
- loss normalization accounts for local target counts and distributed averaging;
- replicas remain synchronized after each optimizer step within numerical tolerance;
- sampler state and data sharding are deterministic under the documented seed/world size;
- failure or rank loss does not silently allow only some replicas to update;
- checkpoints record enough state to resume the same distributed topology or document conversion.

Use small synthetic data and a simple model where the expected gradient can be computed directly. Compare one multi-rank update with a single-process reference on the concatenated global batch.

## 10. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Loss differs across replicas after update | Wrong process group; missed/duplicate reduction; inconsistent optimizer state | Compare parameter checksums and gradient norms by rank | Correct group/reduction and assert synchronization before continuing |
| Global batch smaller than configured | World size misread; accumulation reset; incomplete final window | Log per-rank microbatch, accumulation and optimizer-step count | Correct topology arithmetic and remainder behavior |
| Speedup plateaus with more GPUs | Communication, input wait, straggler, synchronization or small local work | Per-rank timeline: input/compute/collective/step | Optimize measured bottleneck or stop scaling if cost/quality worsens |
| Same loss but wrong sample exposure | Duplicated shards, missing ranks, repeated sampler tail | Audit global example IDs and counts across ranks/epochs | Fix sampler partitioning and replay accounting |
| One rank OOMs while others idle | Per-rank shape imbalance, uneven data, workspace difference | Gather rank-level shapes and peak memory | Balance or bound workload; retain explicit worst-case capacity |
| Gradient scale changes with world size | Sum/mean convention or local denominator mismatch | Compare gradients against global single-process oracle | Correct normalization and rerun deterministic parity check |
| Resume changes data order or learning rate | Sampler, RNG, scheduler or world-size state not restored | Compare rank state and consumed-token counters | Restore compatible state or record a new run boundary |
| Communication volume is low but step is slow | Latency, synchronization, poor overlap, network contention | Profile exposed collective time and link utilization | Diagnose collective algorithm/topology; avoid inferring from bytes alone |

## 11. Interview and self-check questions

### Q1. What is replicated in ordinary data parallelism?
**Answer:** Each data-parallel replica typically has a copy of model parameters and optimizer state and processes different data.
**Reasoning:** Gradient synchronization keeps replica updates aligned.
**Follow-up:** Does adding data-parallel ranks shard optimizer state?
**Answer:** Not in classic replicated data parallelism; sharded methods are separate.

### Q2. Compute global sequences/update for microbatch 2, accumulation 8, data-parallel degree 4.
**Answer:** 64 sequences/update.
**Reasoning:** `2*8*4=64`.
**Follow-up:** Do tensor-parallel ranks multiply this count?
**Answer:** Not as independent data replicas under the common topology.

### Q3. Why can averaging local mean gradients be wrong?
**Answer:** Local means may have different numbers of valid targets.
**Reasoning:** Equal averaging weights ranks equally, not tokens equally.
**Follow-up:** What fixes token-mean weighting?
**Answer:** Aggregate summed token-loss gradients and divide by the global valid-target count, or use an equivalent framework-supported reduction.

### Q4. Estimate ring all-reduce bytes sent per rank for 2 GB tensor and 8 ranks.
**Answer:** Approximately 3.5 GB under the stated idealized formula.
**Reasoning:** `2*(8-1)/8*2=3.5` GB.
**Follow-up:** Does this yield runtime?
**Answer:** No; bandwidth, latency, topology, algorithm and overlap matter.

### Q5. Why might eight GPUs provide less than eight-times speedup?
**Answer:** Gradient communication, input stalls, synchronization, stragglers and kernel inefficiencies consume time.
**Reasoning:** Parallel work is not perfectly divisible or communication-free.
**Follow-up:** What should a profile separate?
**Answer:** Input, forward/backward, collective, optimizer and exposed wait time by rank.

### Q6. What is strong scaling?
**Answer:** Increasing resources while holding total work approximately fixed.
**Reasoning:** Work per rank decreases as replicas grow.
**Follow-up:** What limits it?
**Answer:** Communication and coordination overhead eventually dominate.

### Q7. Why test replica synchronization?
**Answer:** A wrong group or reduction can leave parameters different across ranks.
**Reasoning:** Training assumes each next step starts from consistent weights.
**Follow-up:** What simple check helps?
**Answer:** Compare parameter checksums or values after a controlled update.

### Q8. Why is a global example count insufficient for token objectives?
**Answer:** Examples may contain different lengths, padding and masked-target counts.
**Reasoning:** The loss denominator can vary independently of sequence count.
**Follow-up:** What should be logged?
**Answer:** Actual valid target tokens per rank and globally.

### Q9. What should be considered when changing world size on resume?
**Answer:** Sampler partition, batch, optimizer/scheduler state, RNG, gradient reduction and checkpoint conversion.
**Reasoning:** A changed topology can change sample order and update semantics.
**Follow-up:** Is the continuation identical by default?
**Answer:** No; validate or document the run boundary.

### Q10. What metrics support a scale-out decision?
**Answer:** End-to-end throughput, time-to-target quality, collective/compute/input breakdown, per-rank memory, accelerator-hours and cost.
**Reasoning:** Step time or bandwidth alone misses system and quality effects.
**Follow-up:** What benchmark regime must be stated?
**Answer:** Strong or weak scaling, workload, batch, sequence and budget definition.
