## Learning outcomes

Learners can profile before optimizing; distinguish launch-, compute-, bandwidth-, and synchronization-bound kernels; reason about coalescing, tiling, data reuse, occupancy and fusion; estimate idealized global-memory traffic; and validate numerical correctness and end-to-end performance after a kernel change.

## 1. Optimize a measured bottleneck

Kernel optimization should begin with a concrete workload and profile. The objective is to improve a user-visible metric such as training step time, inference latency, throughput, energy or cost while preserving the required numerical behavior.

A disciplined loop:

1. Pin workload, hardware, software, precision and baseline revision.
2. Verify output/gradient correctness before timing.
3. Profile end-to-end to identify where time is spent.
4. Inspect kernel-level metrics relevant to the suspected bottleneck.
5. Form one falsifiable hypothesis.
6. Change one thing and benchmark representative shapes.
7. Compare end-to-end as well as isolated-kernel results.
8. Retain the change only if improvement is repeatable and within tolerance.

Optimizing a kernel that contributes little to total runtime cannot produce a large end-to-end gain. If a fraction `f` of runtime is accelerated by factor `s`, idealized total speedup is `1/((1-f)+f/s)` (Amdahl's law), before integration overhead.

## 2. Kernel launch and work granularity

A kernel launch has nonzero overhead. Many tiny kernels can spend more time scheduling than doing useful arithmetic, especially for small tensors or short sequences. Larger fused work can reduce launches and intermediate materialization, but may increase register pressure or reduce shape specialization.

Work granularity must expose enough independent blocks/tiles to use the device while avoiding excessively small work units. Too few blocks leave compute units idle; too many tiny blocks can increase scheduling and memory overhead. The best configuration depends on shape and hardware.

Host API timing may measure launch enqueue rather than device completion because execution is asynchronous. Use correct synchronization or device events, warm up first, and avoid unnecessary synchronization inside the timed loop.

## 3. Memory access and coalescing

Adjacent threads accessing adjacent addresses can often be serviced efficiently by coalesced memory transactions. Strided, irregular or poorly aligned access can require more transactions than useful bytes. Tensor layout and indexing therefore affect performance even when arithmetic is unchanged.

Check:

- strides and contiguity assumptions;
- alignment and vectorization;
- read/write transaction efficiency;
- reuse of values across threads/operations;
- cache behavior and redundant loads;
- writes that create unnecessary intermediate tensors.

A layout conversion may improve a later kernel but costs time and memory itself. Measure the whole sequence rather than assuming one layout is always best.

## 4. Tiling and on-chip reuse

Tiling divides a larger operation into chunks that fit in registers or shared/on-chip memory. Reusing a loaded tile can reduce global-memory traffic, particularly for matrix multiplication and attention. Tile size affects parallelism, register/shared-memory use, synchronization and edge handling.

Larger tiles can improve reuse but reduce the number of resident blocks or trigger spills. Smaller tiles may increase overhead and duplicate loads. Tile selection is a constrained tradeoff across hardware resources and shape.

For non-multiple dimensions, edge tiles require masks or padding. Validate tail handling and ensure masked elements do not corrupt outputs or gradients.

## 5. Fusion and intermediate traffic

Fusion combines compatible operations into one kernel, potentially removing launch overhead and global-memory writes/reads for intermediate tensors. A fused kernel can be faster when operations share data and the fused resource use remains efficient.

Fusion may lose when it increases register pressure, reduces occupancy, prevents use of a tuned library kernel, increases code size/compile time, introduces synchronization, or behaves poorly for some shapes. Fusion also changes arithmetic ordering and may alter floating-point results.

Fusion is not “always faster.” Benchmark the full fused region and verify correctness under target dtypes and shapes.

## 6. Idealized elementwise traffic example

Consider `y = relu(a*x + b)` with per-element arrays `a`, `x`, and `b`, 4-byte values, and one output `y`. Suppose an unfused implementation materializes each intermediate in device memory, and ignore cache reuse and write allocation.

- Separate multiply: read `a,x` (8 bytes), write temporary (4): 12 bytes/element.
- Separate add: read temporary and `b` (8), write next temporary (4): 12 bytes/element.
- Separate ReLU: read temporary (4), write `y` (4): 8 bytes/element.
- Total idealized traffic: 32 bytes/element.
- Fused kernel: read `a,x,b` (12), write `y` (4): 16 bytes/element.

This simplified model gives a 50% reduction in modeled bytes. It assumes intermediates reach device memory and no cache reuse; a real compiler may fuse automatically, retain intermediates in registers/cache, or introduce different traffic. The model is a hypothesis generator, not a measured result.

If we count multiply, add and max as three scalar operations, idealized arithmetic intensity changes from `3/32=0.09375` to `3/16=0.1875 FLOP/byte`. This operation count is illustrative; conventions may count FMA as one or two FLOPs, and ReLU instruction accounting varies.

## 7. Register pressure and occupancy tradeoff

Fusion and tiling increase live values. More registers per thread can reduce active warps or blocks; spills can send values to slower memory. Occupancy is useful diagnostic data but not the objective: a kernel with lower occupancy may win through data reuse or fewer instructions.

Inspect compiler resource reports and profiler evidence for register count, spills, shared-memory usage, active blocks, memory stalls and instruction throughput. A change that raises occupancy but increases memory traffic may regress.

Unrolling can remove loop overhead and expose instructions, but can also increase code size and register usage. Specializing by shape can improve hot paths but increases compilation and maintenance complexity. Keep specializations only when workloads are stable and measured.

## 8. Numerical equivalence and precision

Floating-point operations are not associative. Fusion can change rounding because intermediate values may remain in higher precision or because operation order changes. Fused multiply-add (FMA), reduction trees, atomics and parallel summation can produce small differences from a reference.

Define acceptable tolerances based on the model/task and compare both forward outputs and gradients. Test representative and adversarial values: zeros, large/small magnitudes, NaN/Inf policy, boundary conditions and cancellation. A lower maximum error on one sample does not prove training stability.

For a training kernel, validate parameter updates and downstream loss behavior where relevant. A numerically faster kernel that silently changes masks, reductions or gradient scaling is not equivalent.

## 9. Benchmark design

Benchmark the production shape distribution and include warmup, synchronization, repetitions and isolated measurement conditions. Report median and tail latency where relevant, throughput, memory use, compile time and correctness tolerance.

Compare:

- kernel-only latency;
- full operator/sequence latency including launch and layout conversion;
- end-to-end step or request latency with real preprocessing and synchronization;
- performance across batch, sequence, hidden size, dtype and edge dimensions;
- behavior under realistic concurrency and device clocks/power policy.

Do not report the best observed microsecond as a stable improvement. Re-run with enough repetitions to quantify variability and verify no competing workload or thermal/clock shift explains the result.

## 10. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Kernel optimization does not improve full step | Kernel is not critical path; launch/communication/data input dominates | End-to-end trace and Amdahl fraction | Optimize actual dominant stage or stop the kernel work |
| Fusion increases runtime | Register pressure, poor tile, library path lost, larger code | Compare registers/spills, occupancy, library baselines and shape timings | Split fusion or specialize only validated shape regimes |
| Memory traffic exceeds estimate | Cache misses, write allocation, spills, duplicated loads, layout conversion | Profiler bytes/transactions and resource report | Fix measured traffic source; revise model assumptions |
| Performance differs on edge shapes | Tail masking, alignment, small grid or uncoalesced access | Sweep around tile/vector width boundaries | Add correct tail path and benchmark it explicitly |
| Output differs after fusion | Reordered arithmetic, FMA, precision or masking error | Reference comparison with max/relative error and gradients | Identify intended tolerance or fix correctness defect before shipping |
| Timing appears implausibly low | Asynchronous launch measured without synchronization | Device event/timeline comparison | Correct timing and repeat with warmup |
| More occupancy but slower kernel | Worse data reuse, extra instructions or bandwidth | Compare memory/compute counters and end-to-end time | Prefer measured outcome over occupancy target |
| Compile time/runtime cache grows excessively | Too many shape specializations or code variants | Track compilation counts and cache hit/miss | Reduce specialization surface or use a robust generic path |

## 11. Interview and self-check questions

### Q1. Why profile before rewriting a kernel?
**Answer:** The suspected kernel may not be the critical path.
**Reasoning:** End-to-end speedup is limited by the fraction of time actually improved.
**Follow-up:** What principle quantifies the limit?
**Answer:** Amdahl's law.

### Q2. What is a benefit of fusion?
**Answer:** It can reduce launch overhead and intermediate memory traffic.
**Reasoning:** Compatible operations may share values in registers and write only final outputs.
**Follow-up:** What can make it slower?
**Answer:** Register pressure, lost library optimization, code size, or poor shape behavior.

### Q3. In the idealized example, what is separate versus fused traffic per element?
**Answer:** 32 versus 16 bytes under the stated assumptions.
**Reasoning:** Separate intermediates are written/read; fused path reads three arrays and writes one.
**Follow-up:** Is 50% reduction a measured speedup?
**Answer:** No; it is a simplified traffic estimate.

### Q4. Why can coalescing matter?
**Answer:** Poor access patterns can require more memory transactions for the same useful bytes.
**Reasoning:** Hardware services aligned segments rather than arbitrary scalar requests independently.
**Follow-up:** What should be inspected?
**Answer:** Strides, alignment, transaction efficiency and profiler memory metrics.

### Q5. Does higher occupancy guarantee faster execution?
**Answer:** No.
**Reasoning:** Reuse, instruction efficiency and memory behavior can dominate.
**Follow-up:** What can high register usage cause?
**Answer:** Fewer resident blocks or spills.

### Q6. Why use tiling?
**Answer:** To reuse data on-chip and reduce device-memory traffic.
**Reasoning:** Repeated global loads can be replaced by local reuse.
**Follow-up:** What is a tile-size tradeoff?
**Answer:** Reuse and parallelism versus registers/shared memory and edge overhead.

### Q7. Why can fused output differ numerically?
**Answer:** Operation order, intermediate rounding and FMA behavior can change.
**Reasoning:** Floating-point arithmetic is not associative.
**Follow-up:** What should be tested?
**Answer:** Forward and gradient differences on representative and edge values under a declared tolerance.

### Q8. Why synchronize for timing?
**Answer:** GPU calls are asynchronous; unsynchronized host timing may measure only enqueue latency.
**Reasoning:** Device execution can continue after host return.
**Follow-up:** What else matters?
**Answer:** Warmup, repeated samples, isolation and full workload scope.

### Q9. What does arithmetic intensity help diagnose?
**Answer:** Whether compute or memory bandwidth is a plausible upper-bound bottleneck.
**Reasoning:** It relates work to transferred bytes.
**Follow-up:** Does it predict exact kernel time?
**Answer:** No; launch, latency, occupancy, dependencies and instructions also matter.

### Q10. When retain a kernel change?
**Answer:** When correctness is within requirements and repeatable end-to-end improvement exists for supported workloads.
**Reasoning:** A local microbenchmark win can regress the application.
**Follow-up:** What if only one shape improves?
**Answer:** Keep a bounded specialization only if its workload frequency and maintenance cost justify it.

## Quick reference card

| Optimization | Main opportunity | Main risk |
|---|---|---|
| Coalescing | Fewer memory transactions | Layout conversion cost or unsupported shape assumptions |
| Tiling | On-chip data reuse | Register/shared-memory pressure and edge handling |
| Fusion | Fewer launches/intermediate traffic | Resource pressure, lost library path, numerical drift |
| Unrolling | Less loop overhead/exposed instructions | Code size and register growth |
| Specialization | Optimize hot shape | Compile/cache and maintenance complexity |
| Profiling | Find actual bottleneck | Misread metrics or unrepresentative workload |
| Validation | Preserve outputs/gradients | Tolerance too loose or test too narrow |
| Timing | Compare repeatably | Async enqueue, clock/concurrency noise |
| Success | End-to-end gain under correctness limits | Kernel-only speedup mistaken for application gain |
| Evidence | No kernel measured | Traffic values are idealized |
