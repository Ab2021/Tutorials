## Learning outcomes

Given a workload and numerical requirements, learners can distinguish representable range from precision; choose where lower-precision operands and higher-precision accumulators are appropriate; explain FP16 loss scaling and its limits; diagnose overflow, underflow and precision drift; and specify validation before comparing speed or memory use.

## 1. Precision is a policy, not a dtype toggle

Mixed precision uses different numeric formats at different points in a computation. A typical matrix operation may read weights and activations in a compact format, accumulate products in a wider format, and keep optimizer state in FP32. The exact policy depends on kernels and framework behavior; “the model is BF16” is not a complete description.

Record at least:

- parameter storage dtype and whether a separate master copy exists;
- activation and saved-activation dtypes;
- matrix operand dtype, multiply mode, and accumulation dtype;
- reduction, normalization, softmax and loss calculation dtypes;
- gradient storage dtype and any scaling/unscaling;
- optimizer moment and update dtypes;
- autocast/operator allowlist and explicit casts;
- checkpoint/export dtype and conversion policy.

Lower-precision values can reduce storage and memory traffic and may use accelerated hardware paths. They also quantize values, narrow representable range for some formats, and can change rounding. Faster arithmetic is workload- and hardware-dependent, and does not establish a faster end-to-end step. A sound policy protects sensitive operations and validates the complete update, not merely a forward pass.

## 2. Range and precision are different

A binary floating-point number has sign, exponent and significand fields. Increasing exponent range allows larger and smaller magnitudes; increasing significand precision makes representable values more closely spaced at a given magnitude. A format can have broad range but coarse spacing, or finer precision but narrower range.

For common IEEE encodings, the following are representative format limits. Exact subnormal handling, rounding modes and accelerator instructions must be confirmed for the implementation in use.

| Format | Exponent bits | Fraction bits | Approximate max finite | Precision implication |
|---|---:|---:|---:|---|
| FP16 (binary16) | 5 | 10 | 65,504 | More significand bits than BF16, but much narrower exponent range |
| BF16 (bfloat16) | 8 | 7 | 3.39 × 10^38 | FP32-like exponent width; fewer significand bits and coarser spacing |
| FP32 (binary32) | 8 | 23 | 3.40 × 10^38 | Wider significand than either 16-bit format; often used for accumulation/state |

FP16's smallest positive normal is approximately 6.10 × 10^-5; gradual underflow can represent smaller positive subnormals down to approximately 5.96 × 10^-8, unless the execution path flushes them. BF16's exponent range is much wider, but a small update can still round away when added to a much larger parameter. Range alone does not prevent cancellation or precision loss.

## 3. Where wider accumulation helps—and where it does not

For a dot product, lower-precision inputs may be multiplied and the partial sums accumulated in FP32. Wider accumulation reduces accumulation error relative to summing every product at the narrow input precision, but it cannot restore information already lost when inputs were rounded to the narrow format. Nor does it guarantee the final result is representable if it is cast back to a narrow format.

A policy should separately examine:

1. **Input quantization:** Were weights/activations rounded before the operation? Are small features or residuals erased?
2. **Product behavior:** Which multiplication instructions and rounding modes are used?
3. **Accumulator behavior:** Is accumulation FP32, and can partial sums overflow or suffer cancellation?
4. **Output cast:** Is the accumulated result narrowed? Could it overflow, underflow or lose needed increments?
5. **Backward path:** Do activation derivatives or reductions create smaller/larger values than the forward path?
6. **State/update:** Are gradients, optimizer moments and parameter updates kept at sufficient precision?

Normalization statistics, reductions, attention scores/softmax, loss computation and optimizer updates are common candidates for explicit wider arithmetic, depending on tested kernels. There is no universal list: framework autocast rules and fused kernels evolve, so inspect actual operator behavior and test the model's sensitive paths.

## 4. FP16 loss scaling

Loss scaling multiplies the scalar loss by a positive scale `S` before backpropagation. By the chain rule, each resulting gradient is also multiplied by `S`; before applying the optimizer, gradients must be divided by the same scale. The aim is to move small gradients into a more representable range during low-precision backward operations. Scaling does not improve the precision of forward activations, fix an unstable model, or make a gradient that is too large representable.

```text
FORMULA [MP-01]: L_scaled = S * L; g_scaled = S * g; g = g_scaled / S
WHERE: L [loss]; g [unscaled gradient]; S [dimensionless positive scale].
CONSTRAINT: same finite scale is applied to the loss and all relevant gradients;
            unscale before clipping, finite checks intended for true gradients,
            and optimizer update. Scale changes require matching unscale.
NUMERICAL EXAMPLE: g = 2.0e-7, S = 1024;
                   g_scaled = 2.048e-4; g_scaled/S = 2.0e-7.
INTERPRETATION: scaling can move a small value above FP16's smallest normal,
                but it does not guarantee downstream arithmetic remains finite.
```

The illustrative multiplication is exact in decimal arithmetic; real FP16/BF16/FP32 operations round at each cast or operation. The final value still has its original magnitude after unscaling. If `S*g` overflows, scaling creates an Inf; dynamic loss scaling responds by skipping that update and reducing `S`. If gradients remain finite for a chosen growth interval, it may increase `S` to reduce underflow risk. This control loop is implementation-specific; inspect the framework's scaler state and skipped-update behavior.

Gradient clipping must normally be computed on unscaled gradients: clipping scaled gradients against an unchanged threshold changes the effective threshold by `S`. Likewise, gradient-norm logs should specify whether they are pre- or post-unscale. In distributed training, all ranks must agree on overflow handling and optimizer-step advancement; a rank-local skipped step can desynchronize training state.

## 5. Worked range and scale checks

### FP16 range boundary

The FP16 maximum finite value is 65,504. A finite FP32 gradient `g=100` multiplied by scale `S=1024` gives `102,400`, exceeding the FP16 maximum. If an intermediate is stored as FP16, it overflows even though the unscaled gradient was ordinary. An FP32 accumulator later in the graph cannot recover from an FP16 infinity already created at an earlier cast.

For the small-gradient example, `g=2.0e-7` is below FP16's smallest normal but above its smallest subnormal; it may be representable as a subnormal on a gradual-underflow path, yet can be lost if subnormals are flushed. Scaling by 1024 yields `2.048e-4`, above the smallest normal. These comparisons motivate a scale but do not select a safe training scale: real gradients have a distribution and backward intermediates can have different ranges.

### Scale rollback invariant

Suppose a step uses `S=1024`; gradients are unscaled and checked. If any gradient is non-finite, do not apply that optimizer update, lower the scale according to the scaler policy, and retry a subsequent batch/update. Do not reuse already-overflowed gradients as if reducing the scale could repair them. State progression (scheduler, EMA, global-step counter, distributed collectives) must follow the training framework's documented skipped-update semantics.

**Independent checks:** `100 × 1024 = 102,400 > 65,504`; `2.0e-7 × 1024 = 2.048e-4`; dividing the latter by 1024 returns `2.0e-7`. The thresholds are magnitude checks, not evidence that a specific kernel preserves these values. Confirm casts and subnormal behavior on the target path.

## 6. Choosing FP16, BF16 and FP32 roles

| Situation | Candidate policy | Reason and caveat |
|---|---|---|
| Wide activation/gradient magnitude range; supported accelerated path | BF16 operands with wider accumulation/state | Wider exponent range can reduce overflow/underflow exposure; fewer significand bits than FP16 can increase rounding drift |
| Small gradients and suitable scaling support; measured kernel advantage | FP16 operands, FP32 accumulation/state, dynamic loss scaling as needed | More fraction bits than BF16 but narrower range; scaling must handle both overflow and underflow |
| Sensitive reductions, loss, normalization or optimizer update | Explicit FP32 or validated higher-precision path | Wider precision may improve robustness but can cost bandwidth/compute and still cannot repair earlier quantization |
| Strict numerical reproducibility or unstable convergence | Establish FP32 reference and compare alternatives | FP32 is a baseline, not a guarantee of bitwise determinism across kernels, devices or reduction orders |

Decision order: establish an FP32 reference and acceptance criteria; inspect the actual hardware-supported formats and kernels; select an initial candidate; run forward, backward and update checks; measure convergence and throughput over comparable work; then use the least costly policy that meets quality and stability requirements. Do not choose solely by dtype name, peak throughput claims, or a single minibatch.

## 7. Error measurement and acceptance

For reference values `x_ref` and candidate `x`, useful measures include maximum absolute error `max |x-x_ref|`, relative error with a documented denominator floor, cosine similarity for vectors, and task-level loss/quality over a fixed evaluation set. Each measure has blind spots: relative error is unstable near zero; cosine similarity can hide magnitude error; a small activation error can alter a sensitive optimization trajectory.

Validate several layers of behavior:

- representative and adversarial tensor magnitudes, including near-zero values and large logits;
- forward outputs and loss against the reference;
- backward gradients, finite-value counts, and gradient norms before/after unscale;
- one-step parameter updates and optimizer-state finiteness;
- multi-step loss/convergence and task metrics over a fixed seed/data policy;
- overflow counts, skipped updates and dynamic-scale trajectory;
- peak allocated/reserved memory and end-to-end step time at equal global batch, sequence length and completed optimizer updates.

Use tolerances selected for the task and report absolute/relative norms, evaluated population, dtype path, hardware/software and seed. Do not treat a close forward output as proof of equivalent gradients or learning behavior. A precision policy that lowers memory but causes frequent skipped steps may increase wall-clock time to a quality target.

## 8. Failure diagnostics

| Symptom | Competing causes | Discriminating check | Bounded response and verification |
|---|---|---|---|
| NaN/Inf loss or gradients | Overflow in cast/matmul; too-large loss scale; unstable model/data; invalid mask | Locate first non-finite tensor; inspect scale and per-layer magnitudes; compare FP32 on same batch | Reduce scale or isolate unstable operation; rerun same batch and confirm finite intermediates and expected update behavior |
| Many skipped FP16 updates | Scale too high; genuine instability; outlier batch; overflow during reduction | Correlate skip events with batch, layer and scaler value; compare unscaled FP32 gradients | Lower or bound scale per framework policy; do not conceal persistent model instability; confirm accepted updates resume |
| Loss-scale collapse or tiny gradients vanish | Scale too low; flushed subnormals; gradient underflow before scaling; aggressive clipping | Compare pre-scale/reference gradients and identify first low-precision cast | Protect sensitive path or adjust policy; verify gradient norms and learning signal, not merely finite values |
| BF16 converges differently from FP16 | Coarser significand; range behavior; different kernel/autocast path; seed/data drift | Fix seed/data and compare per-layer outputs, gradients, and exact op/dtype trace | Test a controlled dtype change; use wider precision selectively only when quality recovers under repeatable evaluation |
| Training is finite but quality regresses | Small systematic rounding drift; clipping/normalization changes; too few updates; altered effective batch | Compare completed optimizer steps, update norms, evaluation curve and preprocessing | Match work and training configuration; adjust precision policy only after isolating error; verify on held-out task metrics |
| Loss scaler reports no overflow but gradients are wrong | Unscale ordering error; clipping before unscale; stale/mismatched scale; silent underflow | Audit scale/unscale location and gradient norm against reference | Correct ordering; unit-check one scaled gradient; verify optimizer receives the intended unscaled update |
| Memory did not decrease | Master weights/optimizer states dominate; saved activations unchanged; buffers/caching; allocator reservation | Inspect per-component peak memory and allocated versus reserved bytes | Attribute memory before changing dtype; measure same peak and workload after one policy change |
| Microbenchmark improves but training slows | More skipped updates, cast overhead, noncritical operator, communication or input bottleneck | Profile full step and time-to-quality at equal completed updates | Retain only if end-to-end objective improves repeatably without quality regression |

## 9. A bounded precision-policy decision

**Decision scope:** one fixed model, sequence-length regime, hardware/software stack and training objective. This lesson does not select a universal dtype or claim a production outcome.

1. Freeze a reproducible FP32 baseline: data order, seeds, optimizer, effective batch, schedule and evaluation set.
2. Record model quality, loss curve, gradient/update diagnostics, peak memory and end-to-end step time.
3. Candidate A: use supported BF16 operands with explicitly documented accumulation and state dtypes; candidate B: use FP16 with a framework-supported dynamic scaler; retain FP32 for the reference and any operations identified as sensitive.
4. Run identical batches through forward/backward/update checks; log the first divergence, finite counts and scaling transitions.
5. Train candidates for equal completed optimizer steps and, separately, compare wall-clock to the same predeclared quality threshold. Record skipped steps rather than counting attempted batches as updates.
6. Select a candidate only when quality is within the declared tolerance, stability criteria hold, and the measured operational objective improves. Otherwise retain the reference or test a narrowly isolated precision change.

No hardware run has been performed for this draft. A production decision requires recorded device model, library/framework versions, kernel path, workload shapes, precision configuration, repetitions, memory measurement method and uncertainty.

## 10. Interview and self-check questions

### Q1. What is the difference between numerical range and precision?
**Answer:** Range describes magnitude limits; precision describes spacing/rounding within that range.
**Reasoning:** BF16 covers a broad exponent range but has fewer fraction bits than FP16.
**Follow-up:** Which may reduce overflow risk but increase rounding drift?
**Answer:** BF16, depending on workload and implementation.

### Q2. Why can FP32 accumulation not repair a bad FP16 input cast?
**Answer:** The information lost or overflowed at the input conversion is absent before accumulation begins.
**Reasoning:** Wider summation only processes represented operands.
**Follow-up:** Name one way to locate the loss.
**Answer:** Inspect/capture the tensor immediately before and after the cast.

### Q3. A gradient is 2.0e-7 and scale is 1024. What is the scaled gradient?
**Answer:** 2.048e-4.
**Reasoning:** Multiply the gradient by the dimensionless scale.
**Follow-up:** What happens before the optimizer step?
**Answer:** Divide by the same scale and check finiteness.

### Q4. Does loss scaling make an oversized gradient safer?
**Answer:** No; it makes its magnitude larger and can trigger overflow.
**Reasoning:** Scaling targets underflow risk, not excessive magnitude.
**Follow-up:** What does dynamic scaling do after overflow?
**Answer:** Typically skips that update and reduces the scale; exact policy is framework-specific.

### Q5. Why perform gradient clipping after unscale?
**Answer:** The intended norm threshold applies to true gradients; clipping scaled gradients with the same threshold changes the effective threshold.
**Reasoning:** Scaling multiplies every gradient and its norm by `S`.
**Follow-up:** What must logs disclose?
**Answer:** Whether reported norms are scaled or unscaled.

### Q6. Can BF16 always be preferred because its range resembles FP32?
**Answer:** No.
**Reasoning:** Its significand is coarser, kernels differ, and task-level convergence must be tested.
**Follow-up:** What baseline is useful?
**Answer:** A reproducible FP32 run with fixed workload and evaluation criteria.

### Q7. How can a finite training run still be numerically wrong?
**Answer:** Rounding drift, incorrect unscale/clip order, silent underflow or altered operator path can change updates without NaN/Inf.
**Reasoning:** Finiteness is necessary but not sufficient for correctness.
**Follow-up:** What should be compared?
**Answer:** Gradients, optimizer updates, convergence and task metrics.

### Q8. Why count completed optimizer updates rather than input batches?
**Answer:** Overflow handling may skip updates, so attempted batches can overstate training progress.
**Reasoning:** The scheduler and optimizer state may advance differently under skipped-step policies.
**Follow-up:** What policy-specific behavior should be recorded?
**Answer:** Whether scheduler, EMA and counters advance on a skipped update.

### Q9. Memory usage is unchanged after switching activations to BF16. Give two checks.
**Answer:** Inspect per-component peak memory and determine whether optimizer/master state dominates; distinguish allocated from reserved memory.
**Reasoning:** Changing one tensor class does not necessarily change total peak or allocator reservation.
**Follow-up:** How compare fairly?
**Answer:** Same model, batch, sequence, optimizer state and measurement method.

### Q10. A kernel is faster but time-to-quality is worse. What is the decision?
**Answer:** Reject it for the time-to-quality objective unless a repeatable equal-quality benefit appears.
**Reasoning:** Kernel speed is not the training objective; skipped steps or degraded convergence can erase throughput gains.
**Follow-up:** What is the next diagnostic?
**Answer:** Compare quality curves per completed update and per wall-clock time, with overflow and update-norm logs.

## 11. Quick reference

| Question | Check |
|---|---|
| Is the format's range adequate? | Compare observed operand/gradient magnitudes with format limits; inspect casts and subnormal behavior |
| Is the precision adequate? | Compare forward values, gradients, updates and task quality against a fixed reference |
| Is accumulation wide enough? | Confirm actual operator accumulation dtype and reduction path |
| Is loss scaling correct? | Scale loss, unscale gradients once, check finite values, then clip/update per framework semantics |
| Are skipped updates handled consistently? | Track optimizer, scheduler, EMA, counters and distributed ranks |
| Is the change beneficial? | Compare peak memory and end-to-end time at equal completed work and quality |
