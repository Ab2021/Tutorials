## Learning outcomes

Learners can derive the memory cost of materializing attention scores; explain tiled exact attention and online-softmax state; update running maximum, normalization sum and output across score blocks; distinguish reduced HBM traffic from reduced attention arithmetic; and validate output, gradients, masking, precision and end-to-end performance against a reference.

## 1. Standard scaled dot-product attention

For query `Q`, key `K`, and value `V`, scaled dot-product attention computes:

```text
S = Q K^T / sqrt(d_k) + mask
P = softmax(S, axis=keys)
O = P V
```

For batch `B`, heads `H`, sequence length `T`, and head width `d_k`, `S` and `P` have shape `[B,H,T,T]`. The score matrix has quadratic elements in `T`. A conventional implementation may materialize scores and probabilities in device memory before multiplying by `V`.

Attention arithmetic remains quadratic in sequence length for dense attention. FlashAttention's core contribution is an IO-aware algorithm: tile the computation so that large score/probability matrices need not be written to and reread from high-bandwidth memory (HBM) in full. It is algorithmically exact in real arithmetic for the stated attention function; floating-point execution can differ from a reference due to operation ordering and precision.

## 2. Materialized score-memory estimate

For `B=1`, `H=16`, `T=4,096`, and 2-byte score values, a single dense score tensor has:

```text
N_scores = B*H*T*T
M_scores = N_scores*2 bytes
```

Calculation: `1*16*4,096*4,096=268,435,456` scores. At 2 bytes each, this is `536,870,912` bytes = 512 MiB (binary), or approximately 537 MB (decimal). This is only one score tensor. A materialized implementation may also hold probabilities, masks, gradients, temporary workspaces and other activations; actual peak depends on fusion, lifetime reuse and backward strategy.

The estimate does not say FlashAttention's total memory is zero or constant. It avoids storing the full `[B,H,T,T]` matrix in HBM in the same way, but still stores Q/K/V, output and tiled intermediate state; those and other model activations consume memory.

## 3. Tiled attention and IO awareness

FlashAttention divides query and key/value sequences into blocks sized to fit available on-chip resources. It loads a query tile and one key/value tile, computes tile scores, updates a running softmax summary, and accumulates the corresponding weighted value output. It then advances through key/value blocks without retaining the entire score matrix in HBM.

Tiling aims to reuse Q/K/V data while resident on-chip and reduce HBM reads/writes. Tile size depends on hardware resources, head dimension, dtype, sequence shape and kernel implementation. Bigger tiles can increase reuse but consume more registers/shared memory; smaller tiles can increase loop/communication overhead.

A fused implementation can combine score calculation, masking, softmax state update and value accumulation. Kernel schedule, synchronization, causal masking, dropout and backward recomputation are implementation-specific. “FlashAttention” refers to a family of IO-aware attention methods and implementations, not one invariant kernel configuration.

## 4. Online softmax state

For one query row, let the score values in a processed set of keys be `s_i`, and corresponding values be vectors `v_i`. Define running state:

- `m`: maximum score seen so far;
- `l = sum_i exp(s_i - m)`: numerically stabilized normalization sum;
- `o = sum_i exp(s_i - m) * v_i`: unnormalized weighted output accumulator.

The final attention output for this query is `o/l`. Keeping `(m,l,o)` allows blocks to be merged without storing every score or probability.

For a new score block with maximum `m_b`, local sum `l_b=sum_j exp(s_j-m_b)`, and local weighted output `o_b=sum_j exp(s_j-m_b)*v_j`, update:

```text
m_new = max(m, m_b)
alpha = exp(m - m_new)
beta  = exp(m_b - m_new)
l_new = alpha*l + beta*l_b
o_new = alpha*o + beta*o_b
```

The rescaling factors put both previous and new block summaries under the same maximum. This is mathematically equivalent to a single stabilized softmax over the union of processed scores, assuming masks and score scaling are consistent.

For the first block, initialize from its own `(m_b,l_b,o_b)` or use a well-defined empty state. Never evaluate `exp(-infinity - -infinity)` for an empty initial state without explicit handling.

## 5. Worked online-softmax update for score blocks [1,2] and [3,4]

Use scalar scores `[1,2]` in block 1 and `[3,4]` in block 2. For the first block:

```text
m_1 = max(1,2) = 2
l_1 = exp(1-2)+exp(2-2) = exp(-1)+1 ≈ 1.367879
```

For the second block, local summary is:

```text
m_2 = max(3,4) = 4
l_2 = exp(3-4)+exp(4-4) = exp(-1)+1 ≈ 1.367879
```

Merge the first and second blocks using `m_new=max(2,4)=4`:

```text
alpha = exp(2-4) = exp(-2) ≈ 0.135335
beta  = exp(4-4) = 1
l_new = alpha*l_1 + beta*l_2
      ≈ 0.135335*1.367879 + 1.367879
      ≈ 1.553002
```

Independent check: direct stabilized sum over all scores is `exp(1-4)+exp(2-4)+exp(3-4)+exp(4-4) = exp(-3)+exp(-2)+exp(-1)+1 ≈ 1.553002`, matching the online update.

For the output accumulator, use the same coefficients: `o_new=alpha*o_1+beta*o_2`. Dividing by `l_new` yields the weighted value average. The score-only calculation above verifies normalization; a complete attention result also requires the corresponding value vectors.

## 6. Exactness, numerical behavior, and dropout

The tiled online-softmax recurrence is algebraically equivalent to full softmax attention when all required keys are included and masks/scale are identical. Floating-point arithmetic is not associative, so output differences from a reference can arise from reduction order, accumulation precision, exponential approximation, tile sequence and fused operations.

Exactness claims should specify whether they mean the same mathematical attention function or bitwise-identical floating-point output. Bitwise identity is generally not guaranteed across implementations or hardware.

Dropout, causal masks, padding masks, relative biases, attention sinks and other score modifications must be applied at the correct point in the tile computation. A kernel that computes the unmasked recurrence correctly can still be wrong for a particular mask convention. Backward implementations may recompute probabilities or use saved normalization statistics; test gradients too.

## 7. Causal and non-causal attention

For causal attention, query position `i` must not use key positions greater than `i`. A tiled kernel can skip fully masked tiles and mask the diagonal/boundary tile. Off-by-one errors at block boundaries allow future tokens or remove valid context.

For padding or variable lengths, masked keys must have zero probability and fully masked query rows need a defined behavior. Packed examples may need block-diagonal attention to prevent cross-example leakage. The kernel's mask representation must match the model's convention.

Test short lengths, tile boundaries, lengths not divisible by tile size, one-token sequences, fully masked positions, left/right padding, and mixed sequence lengths. Use future-token perturbation tests for causal invariance.

## 8. Memory and performance tradeoffs

FlashAttention can reduce HBM traffic and avoid materializing the full score/probability matrix, often improving memory use and speed for suitable workloads. It does not remove the `O(T^2*d_k)` dense attention arithmetic, Q/K/V/output storage, communication, or all other activations.

The benefit depends on sequence length, head dimension, batch, dtype, hardware, kernel support, layout and backward implementation. For short sequences, launch overhead or another fused kernel may dominate; for unsupported shapes, a fallback may be used. Verify which kernel actually ran.

Measure:

- peak allocated and reserved memory;
- attention forward/backward latency at target shapes;
- total training-step or inference latency;
- throughput and supported sequence lengths;
- output and gradient error against a trusted reference;
- fallback/kernel-selection behavior for edge shapes.

Do not multiply a microbenchmark speedup by overall runtime without accounting for attention's fraction of the total path.

## 9. Kernel selection and fallback

A production system may select among FlashAttention versions, memory-efficient attention, standard attention, or vendor library kernels according to device, dtype, head size, mask, dropout, and layout. Pin software versions and inspect runtime selection. A silent fallback can change performance and memory behavior while preserving correctness.

If a fallback is used, report its shape and trigger. If no exact kernel supports the required semantics, choose a correct supported implementation or constrain the workload; do not silently drop a mask or use a semantically different approximation.

Version upgrades can change numerical tolerance and dispatch heuristics. Maintain reference tests and performance baselines for supported shapes.

## 10. Validation plan

Compare a tiled kernel with a trusted full attention reference on small tensors. Use the same Q/K/V, scaling, masks, dropout state and dtype. Compare forward output and gradients with appropriate absolute/relative tolerances. Include causal and non-causal cases, padding, block boundaries, non-divisible lengths and extreme scores.

For online softmax, test block-by-block state against a direct stable log-sum-exp/softmax computation. Verify final normalization sums to approximately one for valid rows and that outputs are finite. For fully masked rows, assert the documented behavior.

For performance, use warmed-up synchronized timing and memory profiling on the exact target workload. Report fallback status and end-to-end path. Correctness, memory, and speed evidence are separate acceptance dimensions.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| Output differs at tile boundaries | Causal/padding mask off-by-one; wrong global offset | Test lengths around block size and perturb future tokens | Fix mask indexing and make boundary parity blocking |
| Normalization is non-finite | Empty block initialization; all-masked row; unstable rescaling | Inspect per-row `m,l` and mask counts | Handle empty/fully masked rows and retain stable max rescaling |
| Output drift grows with sequence length | Accumulation precision/order; scaling/mask bug | Compare per-tile summaries to FP64/reference on small input | Separate expected rounding from semantic defect; set validated tolerance |
| Memory still quadratic | Fallback materializes scores; another tensor dominates; wrong backend selected | Inspect actual kernel selection and memory timeline | Enable supported kernel or identify non-attention memory source |
| Kernel is not faster | Short sequence, launch overhead, unsupported shape, poor tile | Profile attention fraction, fallback and tile kernel time | Benchmark supported shapes and compare end-to-end |
| Gradients differ while forward agrees | Backward recomputation/mask/dropout or scaling mismatch | Compare dQ/dK/dV with reference and fixed RNG | Correct backward contract and test deterministic gradients |
| Causal leakage appears | Future key included in a tile or mask orientation wrong | Change future tokens and compare earlier outputs | Fix mask and rerun every boundary case |
| Tail latency spikes | Kernel fallback or shape-dependent tile path | Log dispatch choice and per-shape latency | Pin supported shapes or optimize documented fallback |

## 12. Interview and self-check questions

### Q1. What is the main IO-aware idea in FlashAttention?
**Answer:** Tile attention so score/probability matrices are not fully materialized in HBM; maintain online softmax summaries while processing blocks.
**Reasoning:** Reuse on-chip data and reduce HBM reads/writes.
**Follow-up:** Does it eliminate quadratic attention arithmetic?
**Answer:** No; dense attention still computes query-key interactions across sequence positions.

### Q2. How much memory does one 2-byte score tensor need for B=1, H=16, T=4,096?
**Answer:** 512 MiB.
**Reasoning:** `1*16*4096^2*2=536,870,912` bytes.
**Follow-up:** Is that total attention memory?
**Answer:** No; it is one score tensor only.

### Q3. What state does online softmax carry?
**Answer:** Running maximum `m`, stabilized sum `l`, and weighted output accumulator `o`.
**Reasoning:** These summarize all scores/values processed so far.
**Follow-up:** What is final output?
**Answer:** `o/l` for a valid query row.

### Q4. Merge score blocks [1,2] and [3,4]; what is final max?
**Answer:** 4.
**Reasoning:** The maximum over all scores is 4.
**Follow-up:** What is the stabilized normalization sum?
**Answer:** `exp(-3)+exp(-2)+exp(-1)+1≈1.553002`.

### Q5. Why rescale prior and new block summaries?
**Answer:** To express both sums under the new shared maximum before adding them.
**Reasoning:** `alpha=exp(m-m_new)` and `beta=exp(m_b-m_new)` restore equivalent normalized weights.
**Follow-up:** Is the recurrence numerically exact in finite precision?
**Answer:** Algebraically exact, but floating-point order can cause small differences.

### Q6. Does FlashAttention make attention linear in sequence length?
**Answer:** No for dense attention; pairwise query-key arithmetic remains quadratic in sequence length.
**Reasoning:** It reduces IO/materialization, not the number of dense attention relationships.
**Follow-up:** What can be subquadratic in memory traffic/storage?
**Answer:** Avoiding a full HBM-resident score/probability matrix; exact bounds depend on implementation.

### Q7. What must a causal tiled kernel guarantee?
**Answer:** Query position `i` never attends to a future key `j>i`, including tile-boundary and diagonal blocks.
**Reasoning:** Causal mask defines valid context.
**Follow-up:** What is a direct test?
**Answer:** Perturb future tokens and verify earlier outputs are unchanged.

### Q8. Why might a small test pass but production use a fallback?
**Answer:** Kernel support depends on shape, dtype, mask, head dimension, layout, and hardware.
**Reasoning:** Runtime dispatch may choose another implementation for unsupported combinations.
**Follow-up:** What should be recorded?
**Answer:** Actual kernel selection and fallback reason by workload shape.

### Q9. Why compare gradients as well as outputs?
**Answer:** Forward correctness does not validate the backward implementation or mask/scale derivatives.
**Reasoning:** Training updates depend on dQ/dK/dV and parameter gradients.
**Follow-up:** Which gradients are basic checks?
**Answer:** dQ, dK, dV against a trusted reference under matched settings.

### Q10. How should speedup be reported?
**Answer:** With shape, dtype, hardware, warmup, synchronization, memory, fallback status, variability and end-to-end impact.
**Reasoning:** Kernel-only speedup may not improve total training or inference time.
**Follow-up:** What if attention is 20% of runtime and becomes twice as fast?
**Answer:** Idealized total speedup is `1/(0.8+0.2/2)≈1.11x`, before overhead.
