## Learning outcomes

Learners can relate GPU execution and memory hierarchy to ML kernels; distinguish compute-bound, bandwidth-bound and launch/communication-bound behavior; use a first-order roofline estimate; explain occupancy as a resource constraint rather than a performance goal; and ask the right hardware-specific questions before selecting kernels or comparing accelerators.

## 1. GPU as a throughput-oriented processor

A GPU contains many execution units designed to run large numbers of arithmetic operations in parallel. A workload is divided into programs/blocks/threads or analogous vendor-specific units; the hardware schedules groups of threads onto execution resources. GPUs can achieve high throughput when many independent operations are available and data is efficiently reused.

The exact terminology and execution model varies by vendor and architecture. CUDA-specific terms such as streaming multiprocessor, warp, register file and shared memory are useful for NVIDIA systems, but should not be treated as universal GPU names. Map concepts to the target vendor's documentation.

A useful first question is not “how many cores?” but “what is the kernel's bottleneck under this shape, dtype, layout and launch configuration?” Nominal peak capability alone does not predict end-to-end performance.

## 2. Execution hierarchy and scheduling

A typical GPU kernel launch identifies work units that can execute independently. Threads within a block may cooperate using low-latency on-chip memory and barriers; blocks are scheduled onto compute units as resources become available. Groups of threads execute in hardware scheduling units (for example, warps or wavefronts depending on architecture).

Execution efficiency depends on:

- enough independent work to occupy available compute units;
- memory access patterns that enable coalescing or efficient vector transactions;
- register and shared-memory use per block;
- divergence and synchronization within a thread group;
- kernel launch overhead relative to work size;
- dependency chains and instruction mix.

The same kernel can behave differently across hardware generations because register files, caches, execution throughput, memory bandwidth, scheduling policies, and compiler choices change.

## 3. Memory hierarchy and data movement

GPU memory hierarchy may include per-thread registers, shared/local on-chip storage, caches, and high-bandwidth device memory (HBM or another vendor-specific device memory). The hierarchy trades capacity, latency and bandwidth. Registers and on-chip storage are limited; device memory is much larger but slower relative to compute.

ML workloads repeatedly read weights, activations and intermediate state. Reusing data while it is on-chip can reduce device-memory traffic. Poor reuse or access patterns can make a kernel memory-bound even when its arithmetic count appears high.

Distinguish:

- **capacity:** how many bytes can be resident;
- **bandwidth:** bytes transferred per unit time under a defined path;
- **latency:** time to service a dependent access or launch;
- **cache hit rate/reuse:** fraction of requests served from nearer storage;
- **allocation/lifetime:** which tensors are live simultaneously;
- **interconnect:** transfer path between devices or between host and device.

A capacity fit does not guarantee bandwidth efficiency; a bandwidth specification does not guarantee that one workload reaches it.

## 4. Registers, shared memory, and occupancy

Registers hold per-thread values and can be fast, but a kernel using many registers per thread may permit fewer resident warps/blocks on a compute unit. Shared memory or explicit on-chip scratchpad can support cooperative data reuse; high per-block usage can likewise reduce the number of resident blocks.

Occupancy is a ratio or measure of active warps/threads relative to a hardware limit. Higher occupancy can help hide latency, but it is not the objective by itself. A lower-occupancy kernel may still run faster if it has efficient data reuse, fewer instructions, good pipelining, or enough independent work.

Register spilling can move values to a slower storage path and degrade performance. Increasing launch block size, tile size or unrolling can improve reuse while also raising register/shared-memory pressure. Use compiler/resource reports and profiling to understand the tradeoff.

The limits and units are architecture-specific. Do not apply occupancy heuristics from one GPU generation to another without measurement.

## 5. Arithmetic intensity and roofline reasoning

Arithmetic intensity is useful arithmetic work divided by bytes transferred from a specified memory level. A simple roofline upper bound is:

```text
achievable FLOP/s <= min(compute_peak_FLOP/s,
                         arithmetic_intensity_FLOP/byte * bandwidth_byte/s)
```

This model abstracts instruction mix, cache levels, launch overhead, dependency latency, occupancy, synchronization and communication. It helps identify whether compute or memory bandwidth is a plausible limit; it does not predict exact throughput.

Illustrative values: assume a kernel performs `2e12` FLOPs and transfers `4e12` bytes from device memory. Arithmetic intensity is `0.5 FLOP/byte`. If assumed sustained memory bandwidth is `2e12 byte/s` (2 TB/s), the bandwidth roof is `1e12 FLOP/s` (1 TFLOP/s). If the compute ceiling is 60 TFLOP/s, the memory roof is lower, suggesting memory traffic is a likely bottleneck under these assumptions.

The assumed bandwidth is not measured hardware evidence. Actual useful bytes may differ because of cache reuse, write traffic, compression, rereads, spills, or measurement convention. Profile the target kernel and inspect bottleneck counters.

## 6. Kernel launch and fusion implications

Each kernel launch has fixed overhead and may entail scheduling and dependency setup. For tiny operations, launch overhead can dominate arithmetic. Fusing compatible operations can reduce launches and intermediate memory traffic, but can increase register pressure, reduce flexibility, complicate numerical behavior, or make a kernel less efficient for some shapes.

Fusion is a measured optimization. Compare end-to-end time and memory across representative shapes; do not infer speedup from the number of kernels removed. A fused kernel can lose if it reduces occupancy or prevents use of a highly tuned library operation.

Compiler graphs, asynchronous execution and stream dependencies also affect when work is launched and synchronized. Host timing without correct synchronization can measure enqueue time rather than device execution.

## 7. Host-device and device-device interconnects

Data moves between host memory and GPU memory over a host-device path; between GPUs it may move over a peer-to-peer fabric, switch, or network. Performance depends on topology, link count, routing, NUMA placement, peer access, message size, concurrency and software collectives.

A single transfer-bandwidth number does not describe an all-to-all or collective. Small messages can be latency-bound; large transfers can saturate a link; concurrent ranks may contend. Measure the path used by the application and verify whether data is staged through host memory.

For multi-GPU training, model compute, collective communication, input pipeline, checkpointing and synchronization interact. Per-GPU peak FLOPs do not establish cluster scaling efficiency.

## 8. GPU workload bottleneck taxonomy

| Observed pattern | Candidate limit | Evidence to collect |
|---|---|---|
| High arithmetic utilization, memory traffic below roof | Compute/instruction throughput | Kernel duration, instruction mix, active execution-unit metrics |
| Low compute utilization, high device-memory traffic | Memory bandwidth or access efficiency | Bytes, cache behavior, coalescing, memory stalls |
| Low utilization and tiny workloads | Launch or insufficient parallel work | Launch count, grid size, host/device timeline |
| High register use and spills | Register pressure | Compiler reports, spill/local-memory transactions, occupancy |
| Long idle gaps between kernels | Synchronization, host launch, dependency or data pipeline | Timeline with streams and host thread activity |
| Multi-GPU slowdown | Communication, topology, imbalance or synchronization | Per-link traffic, collective timing and rank-level traces |
| Fast isolated kernel, slow application | Integration, launch frequency, transfers or other stages | End-to-end profile and component breakdown |

These patterns are diagnostic hypotheses. More than one bottleneck can coexist, and profiler metrics can be noisy or architecture-specific.

## 9. Benchmarking discipline

A meaningful GPU benchmark states device model, driver/runtime/compiler, library versions, clock/power policy where available, precision, shape, layout, batch/sequence, warmup, repetitions, synchronization, graph/capture mode, concurrency, and whether time includes transfers or preprocessing.

Use warmup to exclude one-time initialization where appropriate; synchronize correctly before reading device timings; report distribution (median and tail) rather than a single best run; isolate competing workloads; and benchmark the exact production shape. Measure both kernel-level and end-to-end behavior.

For accelerator comparisons, match useful work and quality requirements, not only nominal peak FLOPs. Include memory capacity, communication, utilization, software support, energy and cost where relevant.

## 10. Numerical exercise and diagnostic workflow

Given a kernel with `2e12` operations and `4e12` device-memory bytes, intensity is `2e12/4e12=0.5 FLOP/byte`. Under an assumed 2 TB/s bandwidth, the bandwidth-limited ceiling is `0.5*2e12=1e12 FLOP/s`. With a 60 TFLOP/s compute ceiling, the simple roofline selects the lower 1 TFLOP/s bound.

Diagnostic sequence:

1. Verify exact workload shape, dtype, output correctness and warmup.
2. Capture a synchronized device timeline to distinguish launch gaps, compute and transfer.
3. Check kernel resource use: registers, shared memory, occupancy, spills and grid size.
4. Measure memory traffic/cache behavior and compare with an appropriate bandwidth roof.
5. Measure compute/instruction throughput and compare with a matching precision ceiling.
6. Change one resource or kernel choice; retest correctness and end-to-end performance.

If observed performance is far below both ceilings, do not declare “memory-bound” based on low arithmetic intensity alone. Check insufficient parallelism, launch overhead, synchronization, divergence, compilation, clock state, and profiler measurement validity.

## 11. Failure diagnostics

| Symptom | Candidate causes | Discriminating check | Bounded response |
|---|---|---|---|
| GPU utilization appears low | Tiny kernel, host launch bottleneck, input stall or synchronization | Timeline and kernel grid/launch counts | Fix measured gap or increase useful work while respecting latency/memory |
| High theoretical occupancy, poor speed | Memory bottleneck, spills, dependencies or inefficient work | Resource report plus memory/instruction counters | Optimize measured bottleneck; occupancy is not a success metric |
| Kernel latency varies widely | Clock/power state, concurrent jobs, cache effects or insufficient repetitions | Repeat isolated synchronized benchmark and record device state | Control experiment conditions and report distribution |
| Roofline predicts more speed than observed | Wrong byte/FLOP count, spills, low occupancy, launch or dependency overhead | Validate model counts and profile actual counters | Refine bottleneck model and measure specific kernel path |
| Fusion regresses performance | Register pressure, poor tile shape, loss of tuned library kernel | Compare resource usage and end-to-end timing by shape | Keep separate kernels for affected shapes if validated |
| Host timing looks implausibly fast | Asynchronous enqueue measured without device synchronization | Compare synchronized events/device timeline | Correct timing method and rerun benchmark |
| Multi-GPU performance is poor | Interconnect/topology, collectives, rank imbalance | Link/collective profile and per-rank timeline | Fix placement/communication or use simpler topology |
| Correctness changes after kernel switch | Precision/order/fusion semantics or unsupported shape | Compare outputs/gradients against reference with declared tolerances | Reject or constrain kernel until correctness is established |

## 12. Interview and self-check questions

### Q1. Why does GPU core count not predict application speed?
**Answer:** Performance also depends on memory traffic, parallelism, instruction mix, launch overhead, occupancy, synchronization and interconnect.
**Reasoning:** The workload may not reach peak compute.
**Follow-up:** What evidence helps?
**Answer:** Synchronized timeline and kernel/resource/memory profiling on the actual shape.

### Q2. What is arithmetic intensity?
**Answer:** Useful arithmetic operations divided by bytes transferred from a stated memory level.
**Reasoning:** It relates compute demand to data movement.
**Follow-up:** What is 2e12 FLOPs over 4e12 bytes?
**Answer:** 0.5 FLOP/byte.

### Q3. Under 2 TB/s bandwidth, what is the roof for 0.5 FLOP/byte?
**Answer:** 1 TFLOP/s.
**Reasoning:** `0.5*2e12=1e12` FLOP/s.
**Follow-up:** Is this measured throughput?
**Answer:** No; it is an idealized upper bound under the assumptions.

### Q4. Does higher occupancy always mean faster execution?
**Answer:** No.
**Reasoning:** Occupancy is one means to hide latency; reuse, instruction efficiency and dependencies also matter.
**Follow-up:** What is a possible cost of larger tiles?
**Answer:** Higher register/shared-memory use and reduced resident work.

### Q5. Why can kernel fusion improve performance?
**Answer:** It can reduce launch overhead and intermediate reads/writes.
**Reasoning:** Fewer stages may move less data.
**Follow-up:** How can fusion lose?
**Answer:** Increased register pressure, poor shape specialization or loss of a tuned library path.

### Q6. Why synchronize when timing GPU work?
**Answer:** GPU execution is asynchronous; host time may measure enqueue rather than completion.
**Reasoning:** The device may still be running after the host call returns.
**Follow-up:** What else improves timing validity?
**Answer:** Warmups, repetitions, isolation, and reporting the workload/environment.

### Q7. What is the difference between memory capacity and bandwidth?
**Answer:** Capacity is how many bytes can reside; bandwidth is transfer rate.
**Reasoning:** A workload can fit but transfer inefficiently.
**Follow-up:** What is latency?
**Answer:** Time to service an access or operation, distinct from sustained throughput.

### Q8. Why may a multi-GPU collective fail to reach link bandwidth?
**Answer:** Small messages, topology, contention, synchronization, algorithm and rank imbalance affect performance.
**Reasoning:** Aggregate bytes do not determine time alone.
**Follow-up:** What should be profiled?
**Answer:** The actual collective path, link traffic and exposed wait by rank.

### Q9. When is a roofline model useful?
**Answer:** As a first-order bound to distinguish plausible compute versus bandwidth limits.
**Reasoning:** It connects arithmetic intensity and resource ceilings.
**Follow-up:** What does it omit?
**Answer:** Launch/latency, occupancy, dependencies, synchronization, instruction mix and many implementation details.

### Q10. What should an accelerator benchmark report?
**Answer:** Hardware/software versions, shape, precision, warmup, synchronization, timing distribution, transfer scope and end-to-end context.
**Reasoning:** Results are not portable without workload and measurement conditions.
**Follow-up:** Is peak FLOPs enough to select hardware?
**Answer:** No; include memory, software, network, energy and cost for the target workload.

## Quick reference card

| Concept | Use |
|---|---|
| Execution hierarchy | Map work units and hardware scheduling to vendor-specific documentation. |
| Memory hierarchy | Optimize data reuse; capacity, bandwidth and latency are distinct. |
| Occupancy | Diagnostic resource measure, not the performance objective. |
| Roofline | `min(compute ceiling, intensity × bandwidth)`; an upper-bound model. |
| Fusion | Benchmark correctness and end-to-end speed; fewer kernels is not proof. |
| Timing | Warm up, synchronize, isolate, repeat, and include intended transfer scope. |
| Interconnect | Measure actual topology and collective path, not only nominal link rate. |
| Comparison | Match shape, precision, quality, concurrency and system cost. |
| Evidence | All numerical ceilings are hypothetical; no hardware was measured. |
