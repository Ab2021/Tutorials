# Speech-to-Text (STT) Architectural Analysis

This document explores the architectural decisions, trade-offs, and alternatives surrounding the Speech-to-Text (STT) transcription pipeline in the AI Interviewer Agent. Given the strict deployment constraints—a 2 vCPU, 8GB RAM Hostinger VPS with no GPU—the STT engine must be exceptionally lightweight while still providing the low-latency streaming capabilities required for a natural conversation.

## 1. The Role of STT in the Pipeline

The STT engine acts as the primary sensory input for the AI. It is responsible for converting the continuous stream of PCM audio chunks generated by the candidate's microphone into textual transcripts that the LLM can process. 

Because human conversation relies heavily on timing (knowing when someone has finished speaking, identifying interruptions, and recognizing conversational fillers like "um" or "uh"), the STT engine cannot operate in a batch-processing mode. It must operate as an online, real-time streaming recognizer. 

### 1.1 The Latency Imperative
In human-to-human conversation, the average gap between turns is approximately 200 to 500 milliseconds. If the AI takes longer than 1 second to respond after the candidate stops speaking, the interaction feels incredibly jarring and unnatural. Therefore, the STT engine must decode audio as it arrives, providing partial transcripts instantly and finalizing the transcript the moment silence is detected.

## 2. Selected Component: Sherpa-ONNX

After exhaustive evaluation of the 2026 STT landscape, **Sherpa-ONNX** was selected as the primary STT engine. Sherpa-ONNX is a modern implementation of the Kaldi ecosystem, heavily optimized for execution via the ONNX Runtime.

### 2.1 Pros of Sherpa-ONNX
- **Exceptional CPU Efficiency:** Because it utilizes quantized ONNX models (often INT8 precision) and highly optimized C++ inference backends, Sherpa-ONNX can run real-time streaming recognition on a fraction of a single CPU core. This leaves ample compute available for the TTS engine and the FastAPI event loop.
- **Native Streaming API:** Unlike models that require audio to be recorded in full before processing, Sherpa-ONNX is designed fundamentally around the concept of a continuous audio stream. It outputs partial results as the user speaks.
- **Predictable Memory Footprint:** The memory footprint is static and directly tied to the size of the loaded acoustic and language models. It does not suffer from the memory bloat associated with large Python-based transformer models, safely fitting within a 1GB allocation.
- **Built-in Endpointing:** It inherently detects when the user has stopped speaking based on acoustic pauses, simplifying the turn-taking logic on the backend.

### 2.2 Cons of Sherpa-ONNX
- **Accuracy Ceiling:** While highly accurate, Sherpa-ONNX (and similar small-parameter models) cannot match the zero-shot robustness of massive models like Whisper Large-v3. It may struggle with heavy accents, complex technical jargon, or poor-quality microphones.
- **Complex Model Management:** Unlike cloud APIs where the model is managed by a vendor, deploying Sherpa-ONNX requires manually downloading, converting, and managing specific encoder, decoder, and joiner binary files.

## 3. Evaluated Alternatives

The selection of Sherpa-ONNX was made after rejecting several prominent alternatives based on the hardware constraints and latency requirements.

### 3.1 OpenAI Whisper (and Faster-Whisper)
Whisper is the industry standard for accuracy. `faster-whisper`, leveraging CTranslate2, makes CPU inference viable.
- *Pros:* Unmatched accuracy, massive multilingual support, excellent punctuation and capitalization out of the box.
- *Cons:* Whisper is fundamentally an offline, sequence-to-sequence model. While community efforts exist to force it into a streaming paradigm (by chunking audio and running overlapping inferences), this approach is highly CPU-intensive and prone to hallucination at the chunk boundaries. Even the `tiny` or `base` models of Faster-Whisper consume too much CPU to run reliably alongside TTS on a 2 vCPU machine without causing latency spikes.

### 3.2 Vosk API
Vosk was the standard for lightweight offline streaming in the early 2020s.
- *Pros:* Extremely easy to deploy, incredibly low memory footprint (as low as 50MB).
- *Cons:* By 2026, the underlying acoustic models used by Vosk have been surpassed in accuracy by neural transducer models like those used in Sherpa-ONNX and Moonshine. Vosk struggles significantly with modern technical vocabulary without extensive manual language model adaptation.

### 3.3 Cloud STT APIs (Google Cloud Speech, AssemblyAI, Deepgram)
Offloading STT to a specialized cloud provider.
- *Pros:* Near-perfect accuracy, zero CPU utilization on the Hostinger VPS, access to advanced features like speaker diarization and custom vocabularies.
- *Cons:* Introduces a massive network penalty. Audio must travel from the browser, to the VPS, to the cloud provider, and text must travel back. This double-hop introduces variable network latency that destroys the strict sub-second response budget. Furthermore, streaming APIs are billed per minute, which drastically increases the operational cost of the platform compared to running STT locally.

## 4. Voice Activity Detection (VAD) Strategy

Sending continuous audio to the STT engine—even when the candidate is silent—wastes precious CPU cycles on the VPS. To mitigate this, Voice Activity Detection is implemented aggressively.

### 4.1 Client-Side vs. Server-Side VAD
- **Server-Side VAD:** The traditional approach where the server analyzes the incoming stream for speech. While effective, it requires the browser to constantly upload audio data, wasting candidate bandwidth and VPS network I/O.
- **Client-Side VAD (Selected Approach):** Using `onnxruntime-web` to run a lightweight model like Silero VAD directly in the candidate's browser. The browser only opens the WebSocket transmission pipeline when speech is detected and closes it when silence falls.
- *Pros of Client-Side:* Zero wasted bandwidth. Zero wasted server CPU on silence processing. The server is guaranteed to only receive audio containing speech.
- *Cons of Client-Side:* Adds computational overhead to the browser, which could be an issue on very old mobile devices. However, modern smartphones and laptops handle ONNX VAD models effortlessly.

## 5. Error Handling and Resilience

In a real-world environment, the STT pipeline will face degraded conditions. The architecture accounts for these failures.

- **CPU Saturation:** If the Hostinger VPS CPU hits 100% (e.g., due to an OS background task or a traffic spike), STT processing will lag behind real-time. If the STT processing queue depth exceeds a critical threshold, the system is designed to dynamically drop audio frames or switch to a faster, less accurate model variant to catch up.
- **Network Jitter:** Audio chunks transmitted over WebSockets can arrive out of order or experience jitter. The backend implementation uses a rigid jitter buffer to reorder packets based on sequence numbers before passing them to the STT engine, ensuring the acoustic model receives contiguous audio.
