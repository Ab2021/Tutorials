# Text-to-Speech (TTS) Architectural Analysis

This document details the architectural methodology for the Text-to-Speech (TTS) component of the AI Interviewer Agent. The TTS engine is responsible for giving the AI its "voice," converting the text generated by the Large Language Model (LLM) into spoken audio. Because TTS synthesis is highly computationally intensive, selecting the right engine and optimization strategies is critical when constrained to a 2 vCPU Hostinger VPS.

## 1. The Challenge of Conversational TTS

In a conversational agent, TTS cannot be treated as a batch process where an entire paragraph is synthesized before playback begins. Waiting for the LLM to generate 100 words, and then waiting for the TTS engine to synthesize those 100 words, would result in response latencies exceeding 5 to 10 seconds. 

The architecture must support a **streaming synthesis pipeline**, where audio begins playing in the candidate's browser while the LLM is still generating the remainder of the response.

## 2. Selected Component: Kokoro-82M (via ONNX Runtime)

After evaluating the 2026 landscape for open-source, CPU-friendly synthesis, **Kokoro-82M** (running via the ONNX runtime) was chosen as the primary TTS engine.

### 2.1 Pros of Kokoro-82M
- **Unmatched Naturalness:** At approximately 82 million parameters, Kokoro represents a sweet spot in modern TTS. It produces highly natural prosody, accurate inflections, and human-like cadence, which is absolutely vital for an AI Interviewer where a robotic or monotonous voice would alienate the candidate.
- **CPU Inference Speed:** Despite its high quality, when exported to ONNX format and executed on the ONNX Runtime using C++ backends, Kokoro can synthesize audio significantly faster than real-time (RTF < 1.0). This means it generates 1 second of audio in a fraction of a second, even on a basic vCPU.
- **Permissive License:** Released under the Apache 2.0 license, it allows for commercial use without the legal complexities associated with GPL-licensed alternatives or restricted models.

### 2.2 Cons of Kokoro-82M
- **Pronunciation Anomalies:** Like many end-to-end neural TTS models of its size, Kokoro occasionally struggles with homographs (words spelled the same but pronounced differently based on context, like "read"). If the context window provided to the model is too short, it may guess the wrong pronunciation.
- **Memory Footprint:** While lightweight compared to massive transformer TTS models, it still requires several hundred megabytes of RAM to keep the ONNX graph and voice embeddings resident in memory.

## 3. Evaluated Alternatives

Several other TTS solutions were considered and ultimately bypassed in favor of Kokoro.

### 3.1 Piper TTS
Piper is an extremely fast, VITS-based TTS engine designed primarily for edge devices like the Raspberry Pi.
- *Pros:* Phenomenal speed and incredibly low memory footprint. Piper is virtually guaranteed to never cause a CPU bottleneck on a VPS.
- *Cons:* While clear and intelligible, Piper's voices generally sound slightly more synthetic and less expressive than Kokoro. In an interview context where tone and empathy matter, Kokoro's superior prosody justifies its slightly higher compute cost. *Note: Piper is retained in the architecture as a fallback engine in the event of severe CPU contention.*

### 3.2 Cloud TTS APIs (ElevenLabs, OpenAI TTS, Google Cloud)
Offloading synthesis to premium cloud providers.
- *Pros:* Absolute state-of-the-art voice quality. Features like emotional control, massive voice variety, and zero CPU usage on the Hostinger VPS.
- *Cons:* 
  1. **Cost:** Premium TTS APIs are prohibitively expensive for long-form conversations. A 45-minute interview would incur significant per-character charges.
  2. **Latency:** Similar to the STT cloud problem, sending text to an external API and waiting for the audio stream to return adds a network hop that degrades the sub-second latency target.

### 3.3 VITS / FastSpeech2 (Raw PyTorch implementations)
Running traditional TTS research models directly in Python/PyTorch.
- *Pros:* Highly customizable, easy to fine-tune.
- *Cons:* PyTorch overhead is massive. Running these models in eager mode on a CPU is far too slow for real-time interaction. Exporting to ONNX (as Kokoro and Piper do) is mandatory for production CPU deployments.

## 4. The Sentence Chunking Pipeline

The most critical optimization in the TTS architecture is the **Sentence Chunking Strategy**. 

The LLM (Ollama Cloud) streams its response token-by-token. The FastAPI backend buffers these tokens. The moment a sentence boundary is detected (typically a period, question mark, or exclamation point), the backend immediately flushes that complete sentence to the Kokoro TTS engine.

### 4.1 Trade-offs of Sentence Chunking
- **Pros:** Massive latency reduction. The Time-To-First-Byte (TTFB) of audio is reduced from the time it takes the LLM to generate the *entire response* to the time it takes to generate just the *first sentence*. The browser begins playing the first sentence while the LLM and TTS engines process subsequent sentences in the background.
- **Cons:** Loss of global prosody. Because the TTS engine only sees one sentence at a time, it does not know the broader context of the paragraph. This can lead to slightly disjointed inflections across sentence boundaries. For example, the tone of a sentence might differ slightly if the model knew the next sentence was going to be an exclamation.

### 4.2 Handling Sub-Sentence Boundaries
A significant edge case occurs when the LLM generates a massive run-on sentence without punctuation. If the chunker waits for a period that never comes, latency spikes catastrophically. 
To mitigate this, a secondary heuristic is employed: if a buffered clause exceeds a certain word count (e.g., 15 words) and encounters a soft boundary like a comma or semicolon, the chunk is flushed to the TTS engine prematurely.

## 5. Resiliency and "Filler" Audio

In voice interfaces, silence is interpreted as failure. If the LLM takes too long to respond (e.g., due to Ollama Cloud congestion), the TTS engine must step in to manage candidate expectations.

The architecture includes a mechanism for **Pre-synthesized Filler Audio**. 
Upon startup, the system uses Kokoro to synthesize generic filler phrases (e.g., "Hmm, that's an interesting point," or "Give me one second to process that"). The raw PCM bytes for these phrases are cached directly in RAM. 

If the backend detects that the LLM has not produced its first token within 1.5 seconds of the candidate finishing their turn, the FastAPI server instantly pushes a cached filler phrase down the WebSocket. This buys the LLM several seconds to complete its generation without breaking the conversational flow.
